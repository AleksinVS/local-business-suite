# Критическое ревью LBS Factory v3.4 (исходная v3.3 сохранена в Git)

Статус: архитектурная экспертиза предложенной концепции, **не результат внешнего субагента и не нагрузочный тест**. Дата: 2026-10-12.

## 1. Краткое заключение

Общее направление **обоснованно**: использовать существующую модель Wiki и стандартный A2A/MCP/AG-UI ecosystem, отказаться от монолитной общей бизнес-системы и универсального самописного agent runtime.

Риски теперь смещены с монолитности на **переабстрагирование**, **дублирование стейта**, **конфиденциальность знаний** и **динамическую смену identity при делегировании**. Главная оптимизация: стандартизовать результаты и границы доверия, а не внутреннее устройство каждого компонента.

## 2. Находки P0 — нельзя игнорировать

### R01. «Всё опционально» противоречит необходимым гарантиям безопасности

**Ошибка:** если отключаемы identity, audit, artifact store, а агенты продолжат совершать действия — проверки становятся условными. **Исправление:** профиль без серверного IAM допустим только для доверенного локального CLI при ограниченных правах ОС и отсутствии операций от имени корпоративных пользователей. В любом сетевом multi-user профиле нужны authenticated principal, per-object ACL, audit и проверка делегирования. Провайдеры этих функций заменяемы, гарантии — нет. Тест: anonymous Telegram user не получает corporate tool access.

### R02. Существующий канон Git опасен при стираемых и чувствительных данных

**Ошибка:** «любая запись из обследования сразу в Markdown/Git» приведёт к вечным сырым ПДн и секретам в истории. **Исправление:** raw/staging отдельно, проверка классификации *до первого Git-коммита*, accepted pages по review, специальные compartment/erase runbooks. Чувствительные источники — ссылки без Git-копии по умолчанию. Тест: raw секрет не найден в git history даже после удаления страницы.

### R03. A2A не предоставляет бизнес-авторизацию

**Ошибка:** идентификатор инициатора в A2A/Task — это атрибут, а не подтверждённые полномочия. **Исправление:** доверенная service identity + verified subject binding + scope intersection + final domain policy, не принимать claims из произвольных payload. Тест: agent с поддельным `subject_ref` не может читать чужие знания/создать задачу.

### R04. Групповой чат и Wiki могут создавать скрытую утечку между участниками

**Ошибка:** агент с доступом к закрытому Wiki может пересказать секрет в группе, где не все участники имеют допуск. **Исправление:** вычислять audience policy перед retrieval и перед публикацией результатов, использовать уровень комнаты и возможности текущего участника (или ограниченное пересечение допусков), а не права технической учётки агента. Тест: unauthorized group member не получает закрытую цитату и её косвенный пересказ.

### R05. Неограниченная агентная делегация может бесконечно плодить задачи и затраты

**Исправление:** max depth, child tasks, token/cost/time budgets, allowlisted targets, циклическое делегирование запрещено или ограничено политикой, cancellation, retry caps. Тест: два агента не могут бесконечно переадресовывать один запрос.

## 3. Находки P1 — преждевременное усложнение

### R06. Самописный полноценный мультиагентный оркестратор

**Ошибка:** Task API разрастается в workflow DSL, scheduler, graph state, planner, DAG и чекпоинты. **Оптимизация:** внутри runtime использовать Pi/Claude/LangGraph mechanisms. Общее ядро хранит task descriptor/status/artifacts, не внутренний ход мысли и поток токенов. Нужна только одна контрактная модель задачи, а не второй LangGraph.

### R07. Обязательная A2A инфраструктура с первого дня

**Ошибка:** для локального вызова одного агента поднимать сетевой A2A, agent discovery, push callbacks, аутентификацию сервер-сервер. **Оптимизация:** использовать A2A-compatible mapping в проектировании, но реализовать A2A transport только при реальном втором автономном runtime. Брать официальные SDK. Не предполагать, что Pi CLI или Claude Agent SDK «родно» говорят A2A — понадобится проверенный адаптер.

### R08. Единая Event Bus как основа всех обращений

**Ошибка:** Kafka/NATS ради четырёх адаптеров повышает число отказов. **Оптимизация:** локальный direct call и DB-backed job по умолчанию; брокер только при независимых deployments, высокой конкурентности и подтверждённой потребности в fanout.

### R09. Универсальный `KnowledgeProvider` скрывает принципиальные различия

**Ошибка:** попытка свести Wiki, ERP, raw docs, BM25/vector, Git revision и live SQL к одному CRUD/LLM interface. **Оптимизация:** минимальный Knowledge API (search/get/propose/review/history); оригиналы — Source API, живые числа — Task/Business provider. Не унифицировать всё через абстрактную `Document` модель.

### R10. Универсальный registry, manifest и live plugin installer

**Ошибка:** сложная система управления динамически исполняемыми сторонними пакетами; особенно опасно в корпоративном окружении. **Оптимизация:** фиксируемая версия provider в deployment profile, allowlist, проверка зависимостей на build/start, контролируемый rollout; hot-install кода не нужен.

### R11. Смена технического стека ядра до доказанного узкого места

**Ошибка:** перенос Django Core/Memory на Go/Rust одновременно с внедрением agent framework. **Оптимизация:** оставить существующий код, создать тонкие ports/adapters, профилировать, выносить только доказанные bottlenecks. Разделить проекты изменения архитектуры и оптимизации исполнения.

### R12. Графовая БД, self-developed vector engine, claim ontology и универсальный BPMN

**Ошибка:** множество экспериментальных механизмов раньше, чем есть документы и запросы пользователей. **Оптимизация:** accepted Markdown/Git + PostgreSQL FTS, optional vector после золотого набора запросов, простой review; relations остаются аддитивными метаданными. Не активировать `data_store` placeholder/graph runtime в MVP.

### R13. Дублирование workflow задач и AgentTask

**Ошибка:** путаница «задача внедрения для человека», «Bitrix24 work item», «запуск агента», «повторная обработка очереди». **Оптимизация:** четко различать:
- Business Task (истина в Bitrix/OpenProject);
- AgentTask (одно делегирование с результатом в Agent Ledger);
- Job (техническая доставка/повтор);
- Wiki Proposal (неподтверждённая правка знаний).

Связывать ID/correlation refs, не объединять сущности.

### R14. Неправильное ожидание переносимости Pi/Claude/LangGraph

**Ошибка:** один `AgentProvider` не гарантирует бесшовное возобновление сессии, работу с файлами, одни модели/skills/approval semantics. **Оптимизация:** определить минимальный общий интерфейс, явные capability flags, тесты конформности; state остаётся provider-specific. Не обещать миграции внутреннего state или точное повторение каждого ответа.

### R15. AI-генерация индивидуального кода без стабильных рецептов

**Ошибка:** все установки различаются настолько, что сопровождать их дороже, чем базовый продукт. **Оптимизация:** предпочитать готовое ПО и config; recipes + acceptance test packs; generation — только недостающий glue/extension. Сохранять SBOM, версии, fork/patch provenance и upgrade-runbook.

### R16. Преждевременное выделение Wiki в независимый сетевой микросервис

**Ошибка:** раскроет прямые проблемы ACL, Git writer, миграций и восстановления. **Оптимизация:** первое изменение — локальный фасад поверх `apps.memory`. Отдельный процесс только после того, как появится второй реальный независимый потребитель или замеренное ограничение.

### R17. Сохранение старого AI Tool Registry одновременно с новым Capability Registry

**Ошибка:** два источника истины описаний, прав и параметров API. **Оптимизация:** новое API — projection/adapters над существующими `tool_definitions` и source registries на переходном этапе, затем один канон descriptors. Пропускать отдельное публичное развертывание registry до интеграционных тестов.

## 4. Находки P2 — технические долговые зоны

- `memory.remember` синхронно пишет Git и индекс — потенциальная задержка и конкуренция при многих писателях; сначала замерить и ограничить writer concurrency.
- `MemoryExternalConnectorJob` и agent jobs отличаются семантикой, не сливать таблицы без ценности.
- Внешняя модель LLM и Telegram нарушают строгую on-prem классификацию; offline профиль без них обязателен как технически возможная конфигурация, а не маркировка «всё локально» поверх облачных вызовов.
- `source_data` может ссылаться на изменяемые Bitrix/ERP объекты; provenance с `as_of` и hash не гарантирует существование копии исходника; описать политику snapshot vs reference.
- Поиск по видимым сниппетам возможен, но запрет на source title/path leaks также обязателен.
- Лицензии готовых продуктов, dependencies, исходные версии и сетевой egress — предмет проверки каждого solution profile.

## 6. Сложность перехода и риски

| Изменение | Инженерная сложность | Риск данных/безопасности |
|---|---|---|
| Local Task API + один provider | Низкая—средняя | Средний |
| Второй adapter Pi/Claude | Средняя | Средний—высокий (sandbox, секреты) |
| A2A remote peer + identity propagation | Высокая | Очень высокий |
| Включение Wiki в discovery flow | Средняя | Очень высокий (сырая информация/классификация) |
| Вынос `apps.memory` в отдельный service | Высокая | Очень высокий (канон, индексы, ACL) |
| Смена провайдера задач/Bitrix | Средняя | Высокий (двойные записи) |
| Web Group Chat + agents + Wiki | Высокая | Очень высокий (границы участников) |
| Реализация broker/event mesh | Средняя—высокая | Средний; в MVP не оправдан |

## 7. Минимальная целевая конфигурация

**Factory MVP:** один существующий LBS Django процесс для Wiki/Identity/API + один адаптер Pi или LangGraph (по удобству), Telegram optional, DB task ledger, Git wiki, Bitrix24 TaskProvider optional. Нет нового API gateway, брокера, универсального workflow engine, нового vector DB, отдельного Wiki server, Kubernetes.

**Pilot 1 (сознательно маленький):** Telegram → Discovery Agent → **сразу рабочая Wiki** → поиск со статусом → необязательная пометка needs_confirmation. Официальное утверждение отдельного регламента не блокирует обычный процесс.

**Pilot 2:** Lead Agent → External Reviewer по A2A либо адаптеру → результат/артефакт → task completion; инъекция чужого identity и потеря сети обязательны как негативные тесты.

**Pilot 3:** On-prem group chat с двумя пользователями разных прав, одним агентом и закрытым Wiki-документом — подтверждение отсутствия утечки при групповой аудитории.

## 8. Пределы анализа

Основан на исследовании архитектурных документов и выборочных реализаций репозитория, а также спецификаций A2A/MCP/AG-UI; нет реальных метрик latency, доступов production и тестирования всех готовых agent SDK. Количественных обещаний ускорения и сроков нет. Заключение не отменяет существующие security ADR автоматически.

## 9. Дополнительный обзор перехода бизнес-модулей (v3.2)

- **R18/P0 — `Kanban == WorkOrders` — ложное равенство.** Сейчас `WorkOrder.board` является обязательным ForeignKey с `on_delete=CASCADE`; удаление доски потенциально удаляет заявки. Не выделять board UI простым удалением приложения или маршрутов: сначала сохранить доменные операции без доски, протестировать миграции и обратную совместимость.
- **R19/P0 — `disabled` не является авторизацией.** Меню можно скрыть, но URL, API, фоновые workers и AI tools останутся доступными при неполном отключении. Вводить обязательный server-side gate на всех входах.
- **R20/P1 — Django `INSTALLED_APPS`/migrations не равны plugin lifecycle.** Попытка сразу удалять приложения из списка может сломать граф миграций и исторические ссылки. Начать с функционального off; независимая packaging-модель позже.
- **R21/P1 — Waiting List наследует права WorkOrders.** Прямая зависимость `waiting_list.services -> workorders.policies` противоречит автономности. Сделать Waiting List владельцем своих проверок и capabilities, не строить универсальный движок ролей.
- **R22/P0 — транзакционный склад не должен стать distributed transaction.** Физический вынос posting, stock entries и balances по отдельности разрушит консистентность и увеличит сложность. Оставить единый ledger boundary.
- **R23/P1 — внешние TaskProviders и местные WorkOrders не должны одновременно писать одну задачу.** Единый owner и внешние ID, read model для другого provider; идемпотентная синхронизация, если она вообще нужна.
- **R24/P2 — registry DSL может стать самостоятельной тяжёлой платформой.** Использовать ограниченный static descriptor, lifecycle check и существующие Django registries; не добавлять hot-plugging кода, sandbox plugins и необязательные сетевые сервисы заранее.

**Итог:** цель независимой композиции модулей обязательна, а немедленная физическая микросервисная декомпозиция не требуется.

## 10. Дополнительное критическое ревью LBS Access (v3.3)

- **R25/P0 — зависимость authority от WorkOrders.** Сейчас `apps.accounts.services`, `apps.accounts.access_contracts`, `apps.warehouse.policies`, `apps.waiting_list.services` импортируют функции/роли из `apps.workorders.policies`. Если просто выключить WorkOrders, access и другие модули сломаются. **Решение:** нейтральный resolver + compatibility re-export; автоматические golden tests решений до/после.
- **R26/P0 — «AuthorizationProvider отключён» ошибочно приравнивается к свободному доступу.** В multi-user профиле отсутствие провайдера — ошибка запуска/deny, не bypass. Оставить маленькую локальную reference implementation.
- **R27/P0 — новый capability получает grant из существующего wildcard.** Автоматическая выдача новых прав при регистрации модуля нарушает least privilege. Отдельно проверять `*` и значение защищённых ролей; кодовые capability metadata должны быть immutable.
- **R28/P0 — подмена личности агента при A2A/MCP и identity linking.** Telegram ID, текстовая `subject_ref`, `roles` и Bitrix user ID не удостоверяют сами по себе право на действие. Требуются verified principal, installation binding, delegated refs, актуальные проверки и negative e2e.
- **R29/P0 — подтверждённое действие выполняется после отзыва роли.** Долгий AgentTask и approval созданы раньше отзыва доступа; выполнять side effect после проверки только на старте нельзя. Перепроверять конкретную операцию в транзакционном/доменном write path.
- **R30/P0 — групповая аудитория не совпадает с инициатором.** Wiki retrieval и публикация в канал требуют отдельной policy на получателей; Telegram group membership не всегда гарантирует корректную корпоративную аудиторию. При неизвестном составе — не использовать закрытый корпус.
- **R31/P1 — одновременная смена хранилища ролей и архитектуры доступа.** Миграция `role_rules.json` → DB и отделение `apps.accounts` от WorkOrders вместе увеличат риск необратимого изменения прав. Делать разными ADR/PR с данными rollback, не создавать второй editable source-of-truth.
- **R32/P1 — универсальный policy engine раньше потребности.** OpenFGA/OPA/ReBAC/DSL могут быть полезны при сложном sharing, но не нужны для первого профиля. Whole-role semantics и domain selectors важнее «унификации» ценой новой зависимости.
- **R33/P1 — избыточные DB reads при проверках каждой строки.** Проверка свежести пользователя не должна превращаться в N+1 запросы на доске/списке. Использовать bounded snapshots и batch selectors, а перед защищённой записью повторно проверять изменения.
- **R34/P2 — попытка синхронизировать роли Битрикс24 в обе стороны.** Права внешнего объекта остаются у внешнего владельца; совпадение групп не гарантирует одинаковую семантику. Минимизировать маппинг identities и прав, записывать source/constraints.

**Результат ревью:** оставить существующую доменную модель прав как reference provider, выделить её из WorkOrders, стандартизовать контекст и делегирование. **Не** строить отдельный PDP/IAM service, policy DSL и ReBAC infrastructure в MVP. См. `07_ACCESS_ARCHITECTURE.md`, `08_ACCESS_MIGRATION_AND_TESTS.md`.

## 11. Дополнительные находки v3.4

R35/P0: обязательный Wiki review каждой записи блокирует обследование. Решение: прямое рабочее знание + неблокирующий восстанавливаемый реестр.  
R36/P1: OpenFGA как обязательный сервер создаёт вторую authority и точку отказа, когда достаточно локальной ACL. Решение: ResourceRelationshipBackend по реальной потребности.  
R37/P0: если выбран OpenFGA, его отказ не должен открывать ресурс через fallback; один authoritative backend на тип объекта.  
R38/P1: A2A/Task Ledger/Event Bus преждевременны для одного синхронного agent runtime.  
R39/P0: простота не означает отказ от backup, прав на закрытые данные или защиты внешних write-действий.  
R40/P1: выбирать сложность защиты по последствиям, а не по размеру организации.

Нормативные ограничения и триггеры: [09_PROGRESSIVE_COMPLEXITY_AND_OPENFGA.md](09_PROGRESSIVE_COMPLEXITY_AND_OPENFGA.md).

## 12. Найденные privacy-разрывы (v3.4)

- **R41/P0 — файл обнаруживает PII, но индексирует исходный текст.** `inspect_source_object_for_ingestion` возвращает `extracted.text`; `pii_strict` в файловом маршруте не блокирует обнаруженные PII. Одна общая обработка перед финальным upsert.
- **R42/P0 — `adapter_check` обходит безопасную проекцию.** `render_source_object_text` возвращает raw `render_envelope(...).text` после проверки прав. Проверка ACL не заменяет privacy transform.
- **R43/P0 — утекают title/path/id.** Индекс и цитаты включают заголовок/имя файла/путь отдельно от маскируемого тела. Требуются safe fields и allowlist метаданных.
- **R44/P0 — прямой Git writer и внешняя LLM.** Проверка секретов не эквивалентна PII-анонимизации; защитить destination `wiki_git` до первого коммита и отдельно проверять egress.
- **R45/P1 — существующие небезопасные индексы.** Одно исправление кода не удаляет FTS/vector, кэши и содержимое backup/Git. Нужны поисточниковые инвентаризация, ограничение выдачи и reindex.
- **R46/P1 — ложная уверенность.** Regex, HMAC-псевдонимы и `pii_off` не дают гарантии полной анонимности; защищённое использование оригинала отличается от безопасной AI-выдачи.

**Решение:** узкая общая библиотека, не новый privacy-worker или обязательное review каждого документа. Полная спецификация: [10_CONTENT_PRIVACY_PIPELINE.md](10_CONTENT_PRIVACY_PIPELINE.md).
