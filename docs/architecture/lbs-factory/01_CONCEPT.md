# LBS Factory v3.3 — целевая концепция

Статус: proposed architecture / implementation guidance. Дата: 2026-10-12.

## 1. Постановка задачи

LBS — **фреймворк агентного внедрения**, а не универсальная ERP и не обязательный монолит. Агенты обследуют предприятие, устанавливают подтвержденные требования, выбирают готовые решения, подключают действующие ИС, генерируют минимально необходимый код, тестируют, внедряют и сопровождают. Ядро обеспечивает устойчивые договоренности; каждая инсталляция получает только нужные способности.

Целевые свойства:

- функциональная композиция (`capabilities`), независимая от способа размещения;
- заменяемые провайдеры (готовое ПО, облако, локальные службы, custom adapters);
- наращивание сложности внутри возможности через настройки, расширения и при необходимости отдельные службы;
- agent-first процессы с человеческой приемкой и воспроизводимыми результатами;
- knowledge-first: знания обследования сразу входят в LLM-Wiki, но **гипотезы не становятся утвержденными фактами**;
- внутреннее и внешнее взаимодействие агентов через стандартные семантики задачи/результата;
- on-prem и защита корпоративных данных по умолчанию, возможность работать без Telegram и внешних LLM;
- оптимизация без требования полностью переписывать существующий Django.

Не цели: собственный LLM, собственный универсальный orchestration engine, обязательный Kubernetes, общее агентное сознание, синхронизация всех систем друг с другом, полный AI-generated rewrite при каждом внедрении.

## 2. Принцип разделения

```
              Telegram / LBS Web Chat / Bitrix24 / CLI
                               |
                     Channel Adaptors (optional)
                               |
                         LBS Kernel API
                 /         |         |          \
         Agent Dispatch   Trust     Artifacts   Components
                 |         |         |          |
     Pi / Claude /       IAM /     LLM-Wiki      Adapters
     LangGraph / ...     ACL       Knowledge     & Recipes
                 |         |         |          |
                [typed tasks, results, policies, audit]
                                |
             Existing IS / open-source / custom software
```

Здесь линии показывают логические интерфейсы, а не обязательные сетевые hop'ы. Компактное внедрение может состоять из одного серверного приложения и файлового хранилища. Профиль без агентов не запускает Agent Runtime; интерфейсы Task и Artifact можно оставить библиотечными.

## 3. Минимальное ядро

**Внутри microkernel по смыслу, а не как десять Docker-контейнеров:**

1. **Component catalog/loader** — зарегистрированные способности, провайдеры и совместимость версии контракта. Manifest может обрабатываться при сборке/старте. Горячая установка backend-кода не требуется.
2. **Capability resolver** — обнаружение типа провайдера и вызов его типизированного API; расширения регистрируют capability и интерфейс, не меняя код kernel.
3. **Trusted execution context** — удостоверенная идентичность пользователя/сервиса/агента, организация/инсталляция, минимальные полномочия, request correlation, секреты только по ссылкам. Это обязательная гарантия исполнения, но **не** второй собственный IAM/PDP: прикладные права предоставляет подключаемый `AuthorizationProvider` (в частности LBS Access).
4. **Agent interaction contracts** — AgentDescriptor, AgentTask, Result/Artifact, lifecycle, требования подтверждения, возможность adapt to A2A. Запуск полностью внешнего агента не обязателен.
5. **Artifact references** — единая адресация результатов, знания/документы отдельно от технических логов; проверка ACL при открытии, hash/версия.
6. **Configuration and deployment profiles** — декларативное описание выбранных поставщиков и опций, проверка зависимостей и обратимого изменения конфигураций.
7. **Минимальная диагностика и журнал существенных действий** — единые ID, статус, безопасные поля, трасса исполнителя. Не централизованная SIEM/Observability платформа.

### Что НЕ должно быть в ядре

Полноценные Telegram Bot, Bitrix CRM adapter, Wiki server, PostgreSQL vector store, Web Chat, Kanban, LangGraph agent, интеграционная шина/брокер, IAM server, workflow/BPMN, коммерческий оркестратор — это плагины, providers, reference solutions или deployment options.

### Непосредственные зависимости

- Для интерактивного корпоративного доступа обязателен один настроенный `IdentityProvider` (локальный либо внешний), но не конкретный сервер IAM.
- Для межагентных *долгих/асинхронных* задач нужен durable Task Store; лёгкая SQLite/PostgreSQL-реализация по профилю допустима.
- Для Wiki нужны безопасное каноническое хранилище и enforcement доступа; способ запуска независим.
- Для команд и изменений внешних данных проверка прав на **предметной стороне**, независимо от авторизации AgentTask.

## 4. Capabilities — первая продуктовая матрица

| Capability | Первый provider/путь | Альтернативы и оговорки |
|---|---|---|
| `channel.telegram` | Bot API adapter | Не обязателен; коммуникация не означает полномочий |
| `channel.webchat` | LBS on-prem UI, personal/group rooms | Готовый messaging backend допустим после теста API/ACL; не дублировать чаты автоматически |
| `connector.bitrix24` | OAuth/webhook adapter; изолированные tasks/chat/crm/files | API лимиты, версии, учётная запись, scopes; никаких бесконтрольных двусторонних синхронизаций |
| `knowledge.wiki` | Изолируемый рефакторинг `apps.memory` | Markdown/Git canon, metadata/FTS, optional vectors |
| `tasks` | Bitrix24 TaskProvider | Vikunja/OpenProject/LBS Kanban опционально; владелец задач один |
| `identity` | Local / OIDC / LDAP/AD | authentik/Keycloak как варианты, не зависимости ядра |
| `access` | **LBS Access** на базе существующих `apps.accounts` + модульных declarations | Альтернативный AuthorizationProvider возможен; защита прав/аудит обязательны в многопользовательском профиле |
| `agent.langgraph` | Текущий runtime, упрощённый готовым agent SDK | Pi, Claude и другие; соответствующий adapter |
| `integration` | Connector SDK, durable database jobs | NATS/RabbitMQ/независимый worker только по нагрузке |
| `factory.skills` | Версионируемый `SKILL.md` + тесты/рецепты | Продукт-специфичные навыки и внедрения |
| `discovery` | Интервью, requirements, decisions, source evidence | База знаний фиксирует результат, задачи фиксируют процесс |
| `agent.approval` | Минимальная очередь согласований | Контроль значимых side effects; не универсальный BPMN |
| `ops` | CI/tests, logs, backup/restore | Внешние средства мониторинга по требованию |

**Понятие опциональности:** `installed` != `enabled` != `allowed`. Логика доступа не должна опираться только на включённый feature flag. Отключение provider не удаляет канонические данные и не делает вызовы молча успешными.

## 5. Границы данных

- **Solution specification (Git)**: подтверждённые требования, спецификации, ADR, планы и тесты, без секретов и сырых персональных данных.
- **LLM-Wiki (отдельный управляемый канон)**: обобщённые, курируемые знания организации, источники/provenance, историю редакций и права.
- **Source documents**: оригиналы интервью, сканы, внешние выгрузки и иной материал с ограниченными правами и хранением; *не автоматически копировать в Wiki Git*.
- **Business data**: живут в системе-владельце (Битрикс24, 1С, ERP, специальный сервис), а не автоматически в Wiki.
- **Agent task data**: задание/статус/результаты и корреляция; transcript/scratchpads по отдельной retention policy.
- **Access authority**: источник прав выбирается ровно один на зону ответственности; локальные роли/назначения/аудит остаются у LBS Access, если он активен. External identity и Bitrix24 permissions не превращаются автоматически в локальные grants.
- **Messaging data**: комнаты, участники и история; границы видимости сохраняются, Wiki не наследует автоматически все сообщения.

Для каждого объекта: `owner_system`, `classification`, `retention`, `access_scope`, `source_ref`, `version/etag`, при применимости `as_of`.

## 6. Источники истины

1. **Кто владеет?** Только один authorititative owner каждой бизнес-сущности.
2. **Задачи**: если TaskProvider = Bitrix24, Битрикс24 владеет задачами. Локальная таблица — read model/cache, не конкурентный журнал правок.
3. **Знания**: подтверждённые Markdown-концепты в каноне Wiki. Индексы и материализованный граф — производные, их можно пересоздать.
4. **Задания агентам**: локальный Task Ledger — источник истины о состоянии делегирования, а не LangGraph checkpointer или Telegram сообщение; runtime checkpoint остаётся внутри provider.
5. **Критические записи**: операцию исполняет доменная система, агентная цепочка только предлагает команду и получает результат.

## 7. Режимы внедрения

- `discovery-minimal`: Telegram/CLI + выбранный агент + Wiki/проектные артефакты + при необходимости Bitrix24 TaskProvider. Никакого обязательного веб-портала.
- `onprem-collaboration`: LBS Web Chat + Wiki + OIDC/LDAP + любые агенты. Telegram по желанию.
- `enterprise-integrated`: on-prem Web Chat, Bitrix24, внешние ERP, отдельные workers, наблюдаемость, локальный LLM/RAG — только нужное.
- `offline-isolated`: без Telegram и внешних моделей; внутренний чат, локальный provider, локальное хранилище, минимальный Task Store.

## 8. UI и диалоги

Личный чат и групповые комнаты с пользователями/агентами — функциональность CommunicationProvider, не AgentTask. Человек может упомянуть агента в чате; Channel Adapter формирует доверенный AgentTask; результат возвращается в исходную комнату только после проверки разрешённых получателей. Не следует передавать общий полный архив переписки каждой вызываемой модели. Групповой чат может не иметь установленного агента вообще.

AG-UI относится только к взаимодействию клиентского интерфейса с runtime и не является каноном межагентных заданий. UI не должен требовать знания внутреннего state Pi/Claude/LangGraph.

## 9. Миграция существующих бизнес-приложений в подключаемые модули

**Обязательная цель Factory v3.2:** действующие **Kanban (часть `apps.workorders`), Waiting List (`apps.waiting_list`) и Warehouse (`apps.warehouse`)** перестают быть обязательными Django-apps конкретного корпоративного портала и становятся independently enableable компонентами/референсными реализациями. Новая бизнес-функциональность должна поставляться по тому же контракту, а не добавляться напрямую в Kernel.

- Waiting List имеет собственные права/статусы и работает без WorkOrders; конвертация записи в задачу — опциональный адаптер.
- Kanban — опциональное board-представление над TaskProvider/WorkOrders, не самостоятельный обязательный источник истины. Развязать текущую обязательную связь `WorkOrder.board` только через отдельную поэтапную миграцию.
- Warehouse сохраняет автономный журнал движений, единый транзакционный posting и свои инварианты; внешняя WMS/1С может полностью заменять складской функциональный компонент конкретного внедрения.
- На первом этапе `disabled` означает функциональное выключение без удаления данных и без прямых HTTP/MCP/AI вызовов. Физическое отсутствие Django app, независимые БД и сервисные контейнеры — отдельный поздний этап после анализа миграций и зависимостей.
- Kernel, LLM-Wiki, AgentTask, Telegram, Web Chat и интеграции должны запускаться без установленных бизнес-модулей.

**Подробная спецификация, migration gates и задания агентам:** `06_PLUGGABLE_BUSINESS_MODULES.md`.

**Связанное сквозное требование:** отдельная подключаемая система `LBS Access` должна работать при отключённых WorkOrders, Waiting List и Warehouse. Модули регистрируют свои возможности, но хранят/проверяют предметную семантику локально. См. `07_ACCESS_ARCHITECTURE.md` и `08_ACCESS_MIGRATION_AND_TESTS.md`.

## 10. Лицензионные и технологические границы

Готовые поставщики выбираются не по популярности, а по функциональному соответствию, лицензии, on-prem режиму, модели доступа, API, жизненному циклу обновлений и возможности экспорта данных. Никакая библиотека не становится обязательной частью ядра без соответствующей необходимости. Проектная методология и договорённости стабильнее, чем поставщики LLM/agent SDK.

## 11. Метрики успеха

- время от интервью до подтверждённой спецификации;
- доля требований с источниками и тестами;
- доля готовых компонентов против custom-кода;
- повторное использование навыков и рецептов в следующих внедрениях;
- успешность восстановления заданий после отказов;
- число инцидентов с правами/данными (нулевая толерантность для утечек);
- стоимость LLM/task и p95 по ключевым сценариям;
- возможность снять provider без потери данных.

## 12. LBS Access и модульная авторизация (v3.3)

1. **Сохраняем направление существующей реализации.** Плоские роли, `flag/scope/targets`, явные назначения, whole-role evaluation, protected roles, last-superuser guard, предметные ACL и аудиты. Не создавать новую систему политик с нуля.
2. **Разделяем identity и authority.** Local/OIDC/LDAP/AD проверяют пользователя, Telegram/Bitrix24 требуют отдельного подтверждённого linking, а LBS Access или заменяемый AuthorizationProvider принимает решения о прикладных grants.
3. **Регистрации capabilities принадлежат модулям.** Каталог собирается из metadata, но модульность/установка не расширяет полномочия; все HTTP/UI/AI/MCP входы проверяют и `enabled`, и действующий grant, и предметный доступ к объекту.
4. **Роли не принадлежат WorkOrders.** Вынести общее grant resolution и org-scope из `apps.workorders.policies`, убрать прямые импорты WorkOrders из `apps.accounts`, `apps.warehouse.policies`, `apps.waiting_list.services`.
5. **AgentTask не предоставляет привилегии сам по себе.** Доступ зависит от проверенного исходного субъекта, service/agent identity, ограничений задачи, актуальных предметных прав и подтверждений. Изменения доступа через AI-tool базовым профилем запрещены.
6. **Групповой чат и Wiki — разные границы доступа.** Нельзя отвечать закрытыми данными группе только по полномочиям спрашивающего; при неизвестной аудитории — закрытые материалы не использовать. Source/Wiki access должен применяться *до* LLM.
7. **Опционален провайдер, не безопасность.** Сетевой multi-user профиль требует authenticated principal, authorization и audit; никаких внешних OpenFGA/Keycloak/OPA по умолчанию. Отдельный Access HTTP service откладывается.

**Реализационная норма:** начать с adapter поверх Django/текущего `role_rules.json`, покрыть golden matrix, потом refactor. Миграция прав в PostgreSQL — независимое решение с ADR и rollback; не совмещать с module extraction.
