# ADR-0051: CROW как заменяемый модуль организации знаний поверх OKF

**Статус:** Proposed (для согласования; не применяется автоматически к production).
**Дата:** 2026-10-21.
**Основание:** [LBS Factory v3.4](../architecture/lbs-factory/00_README.md), [спецификация интеграции CROW](../architecture/lbs-factory/10_CROW_OKF_INTEGRATION.md).
**Референс CROW:** `crow-hq/llm-wiki-v2`, pinned source `d1e03f4b71cd54b4bd6fad062ca5e488401b95a6`, OKF v0.2.

## Контекст

LBS уже имеет Markdown/Git-канон `apps.memory`, `MemorySourceObject`, безопасность источников, индексы, LBS Access, аудит и необязательное подтверждение рабочего знания (`working` / `needs_confirmation` / `confirmed`). CROW даёт полезную классификацию, консолидацию, маршрутизацию и retrieval, но его штатный `WikiStore` самостоятельно пишет `raw/*.md`, заметки, `index.md` и `log.md`; его дерево не фильтруется по корпоративным ACL.

Проблема не в объёме физического дублирования сама по себе, а в недопустимости двух независимых владельцев одного и того же знания, разрыве контроля доступа и усложнении будущей миграции. Требуется работа CROW почти без изменения upstream, возможность заменить модуль и сразу обеспечить поддержку OKF.

## Решение

1. **Обязательная архитектурная граница.** CROW — заменяемый `KnowledgeOrganizationProvider` за единым LBS Knowledge API. Приложение CROW не получает собственную корпоративную IAM/ACL, пользовательские маршруты записи или независимый постоянный канон.
2. **Один writer на corpus.** На первом этапе CROW штатно читает/пишет **только** выделенный `org/crow/common` OKF-bundle в *действующем* Git-каноне LBS; операции запускает локальный адаптер под общим LBS writer lock. Другие существующие каталоги остаются под `apps.memory`. В пределах одного поддерева запрещены независимые писатели. Зафиксировать явное владение `corpus_id -> provider_code`.
3. **Ограничение доступа.** CROW-bundle на MVP имеет единый допуск на все содержащиеся заметки. Смешанные ACL, персональные/межорганизационные документы и closed `pending` не допускаются. Native UI/HTTP/write CLI не открывать; вся пользовательская выдача — через LBS с повторной проверкой цитат/аудитории.
4. **Native raw остаётся.** CROW получает только текст после проверки LBS privacy, секретов и допустимого egress, сохраняет собственный `raw/`; каталог физически может находиться внутри bundle, но исключён из Git и пользовательской выдачи. Отдельно резервируется. `MemorySourceObject` не заменять и не удалять.
5. **OKF v0.2 с первого этапа.** Все вновь созданные/изменённые CROW-страницы и их индексы/логи соответствуют OKF v0.2. Внешний адаптер сохраняет неизвестные поля Frontmatter, `sources` и стабильный `knowledge_id`, нормализует `confirmation_state`/`lifecycle`. Legacy данные LBS требуют совместимой миграции до импорта в CROW; запрещено заявлять о соответствии всего старого архива без проверки.
6. **Восстановление.** Поскольку CROW изменяет несколько файлов без общей транзакции, внешняя операция LBS имеет журнал/маркер, сериализацию, проверку изменённых путей, предкоммитную валидацию и восстановление незавершённых операций. Git является каноном заметок. Индекс и реестр подтверждений можно пересоздать.
7. **Future-proof без преждевременного рефакторинга.** На старте всегда проставляются `Origin(source, account, id, version)`, ссылка LBS на источник и хеш обработанного текста. Версия учитывает ревизию очистки. Возможность интегрировать Source API **не реализуется в CROW до доказанной необходимости**; после отдельного ADR возможны смена native raw на SourceBackend и миграция алиасов.
8. **Переход к другому провайдеру.** Корпоративный формат OKF и стабильный `knowledge_id` не принадлежат CROW. Отключение CROW прекращает его записи, но LBS сохраняет доступ к документам, индексам и провенансу; альтернативный writer включается только после проверки формата и восстановления.

## Специфические несовместимости, требующие работы при реализации

- В `apps.memory.knowledge_files` текущие страницы не всегда содержат `type`; `status: active` из LBS не соответствует семантике `status: draft|stable|deprecated` OKF v0.2; `log.md` LBS пока не группируется по ISO датам. Нужны проверка/конверсия и обратимый план для legacy.
- `apps.memory._walk_knowledge_files` использует рекурсивный `rglob("*.md")`, поэтому захватит CROW `raw/*.md` даже при `.gitignore`. Исключение raw из обхода и индексации обязательно до подключения модуля.
- `memory_reconcile` сейчас обрабатывает известные `MemoryKnowledgeItem`; новые native CROW файлы необходимо регистрировать через отдельную LBS-проекцию.
- `write_knowledge_item_file` заново формирует Frontmatter и может стереть CROW `sources/id/generated`. Нужен обратимо совместимый нормализатор, сохраняющий неизвестные ключи.
- На Windows штатный CROW `WikiStore.lock` защищает только потоки процесса; внешняя LBS кроссплатформенная блокировка обязательна.
- `raw` вне Git означает: Git alone не воспроизводит старые источники CROW. Нужны отдельный backup и тест восстановления.
- Текущие CROW `Researcher._with_rows` и `revisions.same_document` читают физические `/raw/...`, поэтому простая замена их на `source_ref` без последующего рефакторинга не работает.
- CROW выпущен под **AGPL-3.0-or-later**: перед кодовым включением и распространением требуется проверка соответствия лицензии/варианта коммерческой лицензии.

## Альтернативы

| Вариант | Почему не сейчас |
|---|---|
| Удалить `MemorySourceObject` и заменить CROW raw | Большая миграция внешних ключей/индекса/ACL, не нужна для пилота. Остаётся открытой |
| Сразу переписать CROW `WikiStore` под LBS Source API | Противоречит «почти без изменений», требует переписать ревизии и табличный retrieval |
| Второй постоянный CROW Git-канон + постоянная синхронизация с LBS | Два владельца знания, конфликты версий и удаления |
| Дать CROW писать в общий `data/knowledge_repo` без ограничений | Безопасность: cross-scope leakage и конкурирующие писатели |
| Встроить только `Steps` и отказаться от native CROW | Быстрый путь, но теряются проверяемые end-to-end свойства его ingestion, raw, revisions, plan/split |
| Ввести OpenFGA, broker, S3 и независимый микросервис сразу | Не требуется первым пилотом, увеличивает число отказов |

## Последствия

**Положительные:** максимальное повторное использование CROW, сохранение действующих функций LBS, одинаковый переносимый формат OKF, тестируемая граница доверия, возможность дальнейшей оптимизации raw и замены провайдера без миграции знаний из собственного формата CROW.

**Ограничения:** первый CROW-корпус не видит всё разнородное по ACL пространство Wiki; первоначальные native raw копии остаются; потребуется небольшой связующий код, импортер метаданных, блокировка/восстановление; OKF-приведение legacy не следует считать автоматическим.

**Отложенные решения:** переход с `MemorySourceObject` на raw; прямой Source API внутри CROW; несколько смешанных ACL в одном CROW bundle; физическое выделение CROW в сервис; OpenFGA.

## Условия принятия и отмены

Не включать CROW в production до тестов: OKF-конформности, secret/PII gate, двух пользователей с разными правами, отказа между raw и заметкой, отказа между коммитом и индексом, конкурентной записи, миграции/отключения provider, восстановления raw+Git, лицензии. Любая утечка путей/заголовков или обход legacy pending — no-go.

Для отмены архитектурного решения достаточно оставить LBS MemoryProvider для corpus и сохранить все OKF-страницы, не удаляя `raw`, на которые указывают страницы. Связанные ADR-0011/0018/0030 сохраняют силу в частях, не противоречащих этому **предлагаемому** уточнению. До принятия ADR приоритет у уже действующих ADR и кода.
