# ADR-0051: CROW как заменяемый модуль организации знаний поверх OKF

**Статус:** Proposed (для согласования; не применяется автоматически к production).
**Дата:** 2026-10-21.
**Основание:** [LBS Factory v3.4](../architecture/lbs-factory/00_README.md), [спецификация интеграции CROW](../architecture/lbs-factory/11_CROW_OKF_INTEGRATION.md).
**Единая политика безопасности контента:** [Factory v3.4: `10_CONTENT_PRIVACY_PIPELINE.md`](../architecture/lbs-factory/10_CONTENT_PRIVACY_PIPELINE.md). CROW только получает прошедший этот контур текст; не реализует его заново.
**Референс CROW:** `crow-hq/llm-wiki-v2`, pinned source `d1e03f4b71cd54b4bd6fad062ca5e488401b95a6`, OKF v0.2.

## Контекст

LBS уже имеет код Markdown/Git-канона `apps.memory`, `MemorySourceObject`, политики источников, индексы, LBS Access, аудит и проект необязательного подтверждения рабочего знания (`working` / `needs_confirmation` / `confirmed`). CROW даёт полезную классификацию, консолидацию, маршрутизацию и retrieval, но его штатный `WikiStore` самостоятельно пишет `raw/*.md`, `.archive/*.md`, заметки, `index.md` и `log.md`; его дерево не фильтруется по корпоративным ACL.

Проблема не в объёме физического дублирования сама по себе, а в недопустимости двух независимых владельцев одного и того же знания, разрыве контроля доступа и усложнении возможной будущей смены способа хранения. **Продуктивных внедрений системы знаний нет; переноса исторических данных не требуется.** Требуется работа CROW почти без изменения upstream, возможность заменить модуль и сразу обеспечить поддержку OKF.

## Решение

1. **Обязательная архитектурная граница.** CROW — заменяемый `KnowledgeOrganizationProvider` за единым LBS Knowledge API. Приложение CROW не получает собственную корпоративную IAM/ACL, пользовательские маршруты записи или независимый постоянный канон.
2. **Один writer на физический bundle.** На первом этапе CROW штатно читает/пишет выделенные `org/crow/common`, `org/crow/<department>` и при необходимости более закрытые **соседние** bundles в действующем Git-каноне LBS; операции запускает локальный адаптер под общим writer lock. Каждому логическому `space_id` соответствует набор физических `bundle_id`, выбираемый через LBS Access. Никаких независимых писателей для одного поддерева.
3. **Двухуровневый доступ с первого этапа.** LBS Access — независимый владелец прав; Source API не является AuthorizationProvider. Сразу вводятся **несколько логических пространств** (отдел/проект), затем ACL на отдельные Note **до** CROW `Steps.select` и окончательная проверка при выдаче. Для ограничения write/merge по несовместимым ACL LBS распределяет заметки по физическим CROW OKF bundles (write-partitions), которые могут принадлежать одному логическому пространству. CROW не видит запрещённые заголовки или описания папок. Прямые CROW UI/HTTP/write CLI остаются закрытыми.
4. **Native raw остаётся.** CROW получает только **разрешённое для выбранного корпуса и модели** представление текста после ACL, CredentialGuard и выбранного профиля privacy. **Обязательное PII-извлечение/маскирование для всех raw не утверждено**: доверенный закрытый локальный сценарий может хранить PII согласно политике организации; для внешнего LLM нужна отдельная egress-проверка. CROW сохраняет собственный `raw/`; каталог физически может находиться внутри bundle, но исключён из Git и пользовательской выдачи. Вместе с `.archive/` и `.llmw2/sync/` он отдельно резервируется по retention-политике: Git-копия без них структурно OKF, но не самодостаточна для повторного чтения источников и истории. `MemorySourceObject` не заменять и не удалять.
5. **OKF v0.2 с первого этапа.** Все новые страницы, индексы и логи соответствуют OKF v0.2. Внешний адаптер сохраняет неизвестные поля Frontmatter, `sources` и стабильный `knowledge_id`, нормализует `confirmation_state`/`lifecycle`. Поскольку продуктивных данных Wiki нет, сразу исправить и проверить текущие форматы/валидаторы LBS, а не создавать перенос legacy-архива. Существующие тестовые и демонстрационные материалы можно пересоздать.
6. **Восстановление.** Поскольку CROW изменяет несколько файлов без общей транзакции, внешняя операция LBS имеет журнал/маркер, сериализацию, **барьер чтения CROW-корпуса во время записи**, проверку изменённых путей, предкоммитную валидацию и восстановление незавершённых операций. После commit и до удачной проекции устаревшие кандидаты не выдаются как актуальные. Git является каноном заметок. Индекс и реестр подтверждений можно пересоздать.
7. **Future-proof без преждевременного рефакторинга.** LBS Source Adapters и сама концепция Source API предшествуют CROW (ADR-0018, v3.3); отдельный публичный Source API не требуется на первом этапе. На старте всегда проставляются `Origin(source, account, id, version)`, ссылка LBS на источник и хеш обработанного текста. Версия учитывает ревизию очистки. Возможность интегрировать Source API **не реализуется в CROW до доказанной необходимости**; после отдельного ADR возможны смена native raw на SourceBackend и миграция алиасов.
8. **Переход к другому провайдеру.** Корпоративный формат OKF и стабильный `knowledge_id` не принадлежат CROW. Отключение CROW прекращает его записи, но LBS сохраняет доступ к документам, индексам и провенансу; альтернативный writer включается только после проверки формата и восстановления.

**Эффективность:** снимок `Folder/Note` — объектная структура **в RAM**, не физическая копия документов и не только пути; штатный `WikiStore.load()` читает full Note body, но не raw/архивы. Не выполнять `WikiStore.load()` на каждый вопрос: кэшировать неизменяемый базовый снимок дерева по версии bundle, собирать только лёгкий request-local разрешённый view; при типовых ACL допускается повторное использование view с учётом ревизии прав. При чтении `raw/.archive` используется авторизация **каждого фактически выбранного источника/версии**, не ACL пользователя, помещённые в CROW. `ScopedReadStore` совместим по узкой duck-typed поверхности `load/read`, которую upstream формально не гарантирует как публичный протокол, — требуются pinned version и contract tests. Подробно: [§4.7–4.8](../architecture/lbs-factory/11_CROW_OKF_INTEGRATION.md).

## Альтернативы разграничения доступа

| Подход | Следствие |
|---|---|
| **B — CROW и отдельный защищённый FTS для остальных знаний** | Допустимый резервный вариант, но не соответствует цели единого пользовательского поиска CROW |
| **A — логические пространства LBS и изолированные CROW write-partitions** | Сразу; нет cross-ACL слияния, масштабируется по устойчивым границам |
| **C — разрешённый Folder/Note tree до Steps.select** | **Сразу для чтения**; дешёвая обёртка без изменения CROW. Клонирует Folder/Note в безопасное дерево; `check_select` проверяет идентичность объектов относительно него, final ACL остаётся |
| **D — временные read-only разрешённые bundles** | Экспериментально: upstream почти не меняется, но сложнее LBS и дорого при обновлениях |

**Владение разрешениями:** пользовательские роли, группы и membership — в существующих `accounts`/LBS Access; space→bundle mapping и default policy — в реестре пространств LBS, исключения отдельной Note — в PostgreSQL по стабильному `knowledge_id` (не в `raw` и не в CROW). Дополнительная Note-рестрикция может только сужать доступ к пространству. В OKF Frontmatter остаются native CROW `id/type/title/description/sources`, LBS `knowledge_id`, `sensitivity`, `confirmation_state`; списки пользователей/групп и прямые ACL-grants **не помещать в YAML**. Текущие `scope_tokens` LBS нельзя сохранять как независимую вторую authority, если ACL канонизируется в Access; для новых CROW страниц это только производная проекция либо неиспользуемое поле. Подробнее: [разделы 4.10–4.11](../architecture/lbs-factory/11_CROW_OKF_INTEGRATION.md).

**Рекомендуемый начальный профиль — A + C для чтения, без B как основного пользовательского поиска.** CROW остаётся единым двигателем поиска знаний по разрешённым пространствам; LBS Access определяет corpus и Note-ACL, а локальный адаптер строит scoped дерево **до** `Steps.select`. После отбора LBS повторно проверяет body/citations/See also, и только затем агент строит ответ. Source API по потребности предоставляет версии источников, но не фильтрует Wiki; OpenFGA тоже не заменяет подготовку scoped дерева. См. [§4.4–4.5 спецификации](../architecture/lbs-factory/11_CROW_OKF_INTEGRATION.md).

## Специфические несовместимости, требующие работы при реализации

- В `apps.memory.knowledge_files` текущие страницы не всегда содержат `type`; `status: active` из LBS не соответствует семантике `status: draft|stable|deprecated` OKF v0.2; `log.md` LBS пока не группируется по ISO датам. Нужно **исправить новый формат до первого внедрения** и обновить тесты/фикстуры, без продуктивной миграции. Схемные миграции Django возможны по необходимости.
- `apps.memory._walk_knowledge_files` использует рекурсивный `rglob("*.md")`, поэтому захватит CROW `raw/*.md`, `.archive/*.md` и страницы CROW даже при `.gitignore`. **Весь CROW-managed namespace** необходимо исключить из legacy `org/index.md`, общего `log.md`/обходов, графа и обычного `memory_reconcile`. Иначе возможны раскрытие через общий индекс и некорректное применение OKF `status: stable` к внутреннему LBS `MemoryKnowledgeItem.status: active`. CROW-проектор обрабатывает этот namespace отдельно.
- `memory_reconcile` сейчас обрабатывает известные `MemoryKnowledgeItem`; новые native CROW файлы необходимо регистрировать через отдельную LBS-проекцию, а после регистрации не передавать эти карточки назад в legacy `memory_reconcile`.
- `write_knowledge_item_file` заново формирует Frontmatter и может стереть CROW `sources/id/generated`. Нужен обратимо совместимый нормализатор, сохраняющий неизвестные ключи.
- На Windows штатный CROW `WikiStore.lock` защищает только потоки процесса; внешняя LBS кроссплатформенная блокировка обязательна.
- `raw`/`.archive` вне Git означает: один Git не воспроизводит старые источники и архивные версии CROW. Нужны отдельные backup, retention и тест восстановления.
- Текущие CROW `Researcher._with_rows` и `revisions.same_document` читают физические `/raw/...`, поэтому простая замена их на `source_ref` без последующего рефакторинга не работает.
- Native `Wiki.ask` возвращает готовый ответ и после `select` может читать `raw` и `.archive` без LBS object ACL. **Быстрый `Steps.select` не выполняет `_with_rows`, `_with_history` и `_conflicting`.** Поэтому для итогового агентского контекста предпочтителен штатный `Researcher.ask` **с LBS `ScopedReadStore`** (`load/read` проверяют права и privacy), единственной подменой документированного `Steps.answer`, сохраняющей подготовленный контекст для агента LBS без CROW final-answer LLM. Исходное тело разрешённых Note берётся из кэша (строки переиспользуются по ссылке); metadata-only + `select_and_hydrate` остаётся **опциональной** оптимизацией для больших/сложных корпусов. Это позволяет оставить upstream почти неизменённым. Стандартный `Wiki.ask` с unrestricted store не включать.
- CROW выпущен под **AGPL-3.0-or-later**: перед кодовым включением и распространением требуется проверка соответствия лицензии/варианта коммерческой лицензии.

## Альтернативы

| Вариант | Почему не сейчас |
|---|---|
| Удалить `MemorySourceObject` и заменить CROW raw | Большая миграция внешних ключей/индекса/ACL, не нужна для пилота. Остаётся открытой |
| Сразу переписать CROW `WikiStore` под LBS Source API | Противоречит «почти без изменений», требует переписать ревизии и табличный retrieval |
| Второй постоянный CROW Git-канон + постоянная синхронизация с LBS | Два владельца знания, конфликты версий и удаления |
| Дать CROW писать в общий `data/knowledge_repo` без ограничений | Безопасность: cross-scope leakage и конкурирующие писатели |
| Встроить только `Steps` и отказаться от native CROW | Быстрый путь, но теряются проверяемые end-to-end свойства его ingestion, raw, revisions, plan/split |
| Ввести OpenFGA, broker, S3 и независимый микросервис сразу | Не требуется первым пилотом, увеличивает число отказов |

## Последствия

**Положительные:** максимальное повторное использование CROW, сохранение действующих функций LBS, одинаковый переносимый формат OKF, тестируемая граница доверия, возможность дальнейшей оптимизации raw и замены провайдера без миграции знаний из собственного формата CROW.

**Ограничения:** фильтр `select` решает разграничение чтения, **но не проблему автоматического `ingest/merge/relate/plan/split` через границы ACL**; для этого сохраняются физические write-partitions с совместимым доступом. Native raw копии остаются; потребуется связующий код, проектор новых заметок, блокировка/восстановление; новый формат LBS нужно сделать OKF-совместимым до первого внедрения.

**Отложенные решения:** переход с `MemorySourceObject` на raw; прямой Source API внутри CROW; **полноценный ACL-aware native ingest с перемешанными разрешениями внутри одного write-partition**; физическое выделение CROW в сервис; OpenFGA.

## Условия принятия и отмены

Не включать CROW в production до тестов: OKF-конформности, secret/PII gate, двух пользователей с разными правами, отказа между raw и заметкой, отказа между коммитом и индексом, конкурентной записи, read/write-барьера, миграции/отключения provider, восстановления raw+archive+Git, лицензии. Любая утечка путей/заголовков или обход legacy pending — no-go.

Для отмены архитектурного решения достаточно оставить LBS MemoryProvider для corpus и сохранить все OKF-страницы, не удаляя `raw` и `.archive`, на которые указывают страницы. Базовое чтение OKF-страниц остаётся доступно без исполнения CROW. Связанные ADR-0011/0018/0030 сохраняют силу в частях, не противоречащих этому **предлагаемому** уточнению. До принятия ADR приоритет у уже действующих ADR и кода.
