# Ретроспектива

## Что сработало

- Разделение transport/session/surface позволило переиспользовать один клиент
  без объединения разметки боковой панели и полной страницы.
- Независимая критика выявила подмену prompt при двух prepared runs, отсутствие
  фиксации модели и слабую границу page context до финальной приёмки.
- Реальный Playwright-прогон обнаружил несовпадение имени `prepare_url`, которое
  unit-тесты конфигурации не проявили.
- Профильный прогон выявил выдачу сохранённых tool-сообщений через JSON, хотя в
  серверном HTML их уже не было.
- Финальное Sol-ревью выявило отсутствие серверной сериализации запусков,
  восстановление потерянного `PREPARED`, потерю `command_id` и неполную
  проверку причинного порядка AG-UI; замечания закрыты до приёмки.
- Повторная ручная проверка после исправлений обнаружила, что первый ответ на
  повреждённый поток должен сам содержать синтетический `RUN_STARTED`, а не
  полагаться только на последующее replay.
- Повторное Sol-ревью обнаружило PostgreSQL-специфичный запрет `FOR UPDATE` на
  nullable outer join и риск разного порядка блокировок. Явный порядок
  `ChatSession` → `ChatRun` нужно проверять отдельно от SQLite-тестов.

## Что учитывать дальше

- Для потокового UI проверять не только форму событий, но и причинную связь
  конкретного запуска с конкретным сообщением.
- HTML shell и асинхронная JSON-конфигурация должны тестироваться как единый
  пользовательский контракт.
- Браузерные снимки нужны минимум для широкого и узкого режима: функциональный
  e2e не выявляет неудачную компоновку.
- Вложение файла и анализ его содержимого — разные возможности; ограничение
  нужно показывать пользователю явно.
