# ADR-0048: Типизированные документы настроек и PostgreSQL для рабочих версий

## Статус

Accepted (принят владельцем 2026-08-31 явным запросом на реализацию).

Для ранее неразрешённых документов принято консервативное решение:
`ai.contract.models` и `memory.contract.claims_policy` остаются `git_static`,
пока для них не появится отдельный безопасный процесс изменения. Принятие ADR
разрешает разработку и тестовый cutover, но не означает разрешения менять
production-данные без отдельного операционного окна.

## Дата

2026-08-31.

## Контекст

В проекте есть четыре разных вида конфигурации, которые исторически представлены
похожими JSON-файлами и дескрипторами:

- параметры развёртывания и секреты;
- Git-дефолты бизнес-контрактов;
- изменяемые через Центр настроек рабочие версии контрактов;
- справочники и порождаемые runtime-артефакты.

На 2026-08-31 в `contracts/` и `data/contracts/` находится по 29 JSON-документов
значений, не считая схем и метаданных. Реестр Центра настроек содержит 33
дескриптора: 18 рабочих контрактов, из которых 17 редактируются, 12 переменных
окружения, две Django-модели и одну ссылку на секрет.

Файловый подход ADR-0031 решил межпроцессную несогласованность для четырёх
контрактов через `apps.core.contract_store`, но не стал единым путём чтения:

- `contract_store` обслуживает только роли, workflow и два контракта цветов;
- AI, memory, FileHub и часть analytics продолжают читать payload-константы,
  загруженные в `config/settings.py` при старте процесса;
- agent-runtime имеет собственный файловый resolver и кэш;
- перечни путей и валидаторов повторяются в `config/settings.py`, доменных
  дескрипторах, `contract_store`, сервисе дрейфа и agent-runtime.

Запись файла и журнала `SettingsChange` не может быть одной транзакцией. Поэтому
существующий writer создаёт `pending`-запись в PostgreSQL, атомарно заменяет файл,
повторно читает его и затем завершает журнал. Для сбоев между этапами существуют
состояния `inconsistent`, reconciliation-команда, глобальная файловая блокировка
и запрет выполнять writer внутри транзакции БД. Эта сложность вызвана двумя
хранилищами одной операции, а не бизнес-требованием.

После ADR-0029 основной production target уже использует PostgreSQL. Условие
пересмотра файлового хранилища из ADR-0031 — рост числа контрактов и частоты
изменений — приблизилось, а довод «основной runtime без БД» больше не относится
к production main.

Контрольный запуск `validate_architecture_contracts` 2026-08-31 показал
фактическую цену зеркальных копий: из 18 зарегистрированных контрактов 10
совпали с Git-дефолтом, 7 имели рабочие отличия, а `core.contract.role_rules`
был отмечен кандидатом на миграцию из-за отсутствующих в runtime ключей
`$defaults` и `viewer`. Этот сигнал не говорит, какая сторона правильная, и
поэтому не может исправляться автоматическим merge, особенно для access policy.

При этом само количество документов не является дефектом. Роли, workflow,
источники памяти и цветовые палитры имеют разные инварианты и не должны
механически объединяться ради меньшего числа файлов. Отображение нескольких
настроек на одной странице не требует общей единицы хранения.

## Решение

### 1. Разделить классы конфигурации

Ввести явную классификацию:

- `deployment_env` — параметры конкретной установки; остаются в окружении и
  приватном deployment-репозитории;
- `secret_handle` — только ссылки на внешнее хранилище секретов;
- `git_static` — неизменяемый во время работы контракт или справочник, читается
  непосредственно из `contracts/`;
- `database_override` — Git-дефолт плюс управляемая рабочая версия в PostgreSQL;
- `generated_file` — порождаемый или многофайловый runtime-артефакт, которому
  действительно требуется файловое хранение.

`data/contracts/*.json` перестаёт быть универсальной рабочей копией всех
Git-дефолтов. После миграции там остаются только явно классифицированные
`generated_file` и временно ещё не переведённые legacy-документы.

Текущий признак `write_policy=editable` не является автоматическим основанием
для `database_override`. В частности, AI registry, tool catalog и task types
содержат identity, code parity, allowlisted tools и confirmation policy; целевая
классификация для них — `git_static`, пока безопасно редактируемая часть не
выделена отдельным доменным контрактом. Общий JSON editor не должен менять
исполняемый/security contract.

### 2. Один доменно-регистрируемый каталог документов

В общем транспортном слое создаётся `ConfigDocumentSpec` со стабильным
`document_id` (существующий `setting_id`), классом хранения, путём Git-дефолта,
версией схемы, валидатором, политикой сбоя, правом изменения и признаками
restart/reindex.

Смысл и валидатор остаются в доменном приложении. Общий реестр только собирает
спецификации и проверяет их непротиворечивость. Центр настроек строит runtime-
дескриптор из `ConfigDocumentSpec`, а не повторяет путь и имя валидатора строками.
Дескрипторы переменных окружения, моделей и ссылок на секреты сохраняются как
отдельные виды, поскольку не являются документами конфигурации.

### 3. Рабочая версия как документ PostgreSQL

Для `database_override` вводится модель `RuntimeSettingDocument`:

- `document_id` — первичный ключ;
- `schema_version`;
- `payload` — `JSONField`/PostgreSQL `jsonb`;
- `revision` — монотонная версия;
- `content_hash` — канонический SHA-256 и ETag;
- `default_hash` — хеш Git-дефолта, относительно которого создана версия;
- `updated_by`, `created_at`, `updated_at`.

Отсутствие строки означает использование актуального Git-дефолта. Строка
содержит полный проверенный снимок, а не частичный рекурсивный override. Это
исключает неоднозначность `null`, удаления ключей и порядка слияния.

Отдельная таблица версий не вводится: существующий `SettingsChange` уже хранит
до/после-снимки, хеши, автора и тип операции. Rollback создаёт новую ревизию
текущего документа и новую audit-запись, не переписывая историю.

### 4. Транзакционный writer и оптимистическая конкуренция

Запись выполняется коротким `transaction.atomic()`:

1. получить transaction-level advisory locks для всех затрагиваемых
   `document_id` в сортированном порядке;
2. получить и заблокировать существующие строки документов;
3. сравнить ожидаемые `revision` и `content_hash`;
4. построить и проверить кандидат, включая доменную и кросс-документную
   валидацию;
5. обновить документ и создать применённый `SettingsChange` в той же транзакции;
6. после commit выполнить только некритичные уведомления/инвалидацию.

Advisory lock нужен, потому что отсутствующую строку override невозможно
заблокировать через `SELECT FOR UPDATE`: два процесса могли бы одновременно
создавать первую версию или валидировать пару default/override по разным
снимкам. Ключ блокировки детерминированно получается из `document_id`, lock живёт
только до конца транзакции; hash collision может лишь избыточно сериализовать две
редкие записи, но не нарушить данные. Existing rows дополнительно блокируются
`SELECT FOR UPDATE`.

Для пары ролей и workflow документы блокируются в детерминированном порядке. Для
изменения определения роли сохраняются существующие специализированные доменные
команды, privilege ceiling и подписанный preview; общий document writer не
становится обходным путём полномочий.

Для DB-документов больше не нужны файловая блокировка, промежуточный `pending`,
`file_written_at` и reconciliation между файлом и БД. Legacy-поля и команда
сохраняются до завершения миграции файловых документов.

Включение backend отделено от выпуска кода и миграции схемы. Переменная
`LOCAL_BUSINESS_SETTINGS_DOCUMENT_DB_ALLOWLIST` по умолчанию пуста, не
поддерживает wildcard и содержит только явно выпущенные в коде document ID.
Реестр проверяет, что выбран полный связный срез. Непустое значение требует
PostgreSQL и одновременного restart всех web/worker процессов; смешанный парк
legacy/DB запрещён. Первый выпущенный тестовый срез содержит только
`waiting_list.contract.status_colors`. Его production-включение этим ADR не
разрешается автоматически.

### 5. Один путь чтения без payload-констант Django

Вводится репозиторий со стабильным API вида
`get_document(document_id, request=None)`. Он:

- получает спецификацию из единого реестра;
- читает рабочую строку PostgreSQL либо Git-дефолт;
- проверяет версию схемы и хеш;
- возвращает глубокую копию/неизменяемый снимок;
- при наличии `request` повторно использует один снимок до конца запроса.

Кэш между процессами, Redis и PostgreSQL `LISTEN/NOTIFY` в первом срезе не
вводятся. Один индексированный запрос на документ и снимок уровня HTTP-запроса
предпочтительнее нового протокола инвалидации. Кэш добавляется только после
измерения.

Payload-константы `settings.LOCAL_BUSINESS_*` и прямые чтения файлов для
переведённых документов удаляются. `config/settings.py` больше не загружает
бизнес-документы при импорте.

Политика сбоя задаётся спецификацией:

- security/privacy-документы завершают операцию закрытым отказом и выставляют
  видимый health-сигнал;
- некритичная presentation-настройка может явно откатиться на Git-дефолт с
  видимой деградацией;
- тихий откат без health/audit запрещён.

### 6. Доставка в agent-runtime через Django gateway

Agent-runtime не получает прямой доступ к PostgreSQL и не монтирует рабочие
настройки как общий read-write volume. Django gateway отдаёт разрешённый набор
документов с `document_id`, `schema_version`, `revision`, `payload` и сильным
`ETag`. Повторное чтение использует условный HTTP-запрос. Это завершает целевой
шаг 2 ADR-0031 и оставляет Django единственным источником полномочий и аудита.

### 7. Версии схемы и обновление дефолтов

Каждая управляемая спецификация имеет целочисленный `schema_version`.
Рекурсивного автоматического слияния старой рабочей версии с новым дефолтом нет.
Несовместимое изменение требует явного мигратора документа и проверки
`--plan`/`--apply`. До миграции health/check показывает состояние
`migration_required`; security-критичный потребитель не использует частично
понятный документ.

### 8. Граница документа и интерфейс независимы

Документы объединяются только если у значений совпадают владелец, права,
валидатор, жизненный цикл, политика сбоя и граница rollback. Категория или одна
страница интерфейса не являются достаточным основанием.

Поэтому цвета Доски и Листа ожидания можно показывать рядом на странице
«Оформление статусов», но хранить и откатывать отдельно. Аналогично Центр
настроек может давать единый тематический экран поверх нескольких документов.

### 9. YAML не является каноническим runtime-форматом

JSON и JSON Schema остаются каноническими форматами машинных документов. YAML
не вводится как второе рабочее хранилище и не заменяет PostgreSQL. В будущем
допускается отдельный безопасный импорт/экспорт YAML для редких Git-authored
настроек: YAML 1.2, safe loader, запрет custom tags/aliases/duplicate keys,
преобразование в обычные JSON-типы и та же валидация. Комментарии YAML не должны
быть источником обязательных метаданных.

## Миграция

Переход выполняется по документам, без постоянной двойной записи:

1. построить инвентарь и единый реестр без изменения поведения;
2. добавить модель, repository и migration-команду;
3. классифицировать legacy runtime-файл:
   - совпадает с Git-дефолтом — строка override не создаётся;
   - отличается и его хеш подтверждён применённым `SettingsChange` — импортируется;
   - отличается без audit-доказательства или имеет старую схему — требует
     ручного решения;
   - security-контракт имеет missing/default-only keys — блокировать cutover до
     отдельной сверки бизнес-смысла, даже если общий migrator мог бы добавить
     ключи технически;
4. до schema migration сохранить и проверить независимые PostgreSQL и legacy
   backups; новую schema сначала развернуть при пустом allowlist;
5. в короткое окно запретить запись конкретного документа, повторить `--plan`,
   сохранить pre-cutover export, импортировать только при необходимости,
   переключить reader/writer и выполнить smoke;
6. окно наблюдения проводить без записи документа, чтобы сохранить возможность
   безопасного backend rollback при доказанном отсутствии DB row;
7. после окна наблюдения архивировать legacy-файл в backup, но не удалять до
   общей приёмки;
8. мигрировать по срезам: независимый pilot цветов листа ожидания, затем доменные документы,
   access/workflow, AI вместе с gateway, memory/FileHub;
9. отдельно классифицировать analytics/integrations и не объявлять их
   пользовательскими настройками без владельца и write workflow.

Backend rollback выполняется обратным переключением reader на сохранённый
legacy-файл только в пределах read-only окна, при доказанном отсутствии DB row
и совпадении хешей; schema migration назад не откатывается. Откат содержимого
активного DB-документа создаёт новую revision и audit event. После появления DB
row простая очистка allowlist запрещена: возврат к файлу требует экспортировать
текущую DB revision в совместимый legacy-файл и выполнить новый управляемый
cutover; молчаливо терять изменения запрещено.

## Рассмотренные альтернативы

### Оставить файловую схему и только расширить `contract_store`

Уменьшает объём миграции, но сохраняет два хранилища одной операции, staged
audit/reconciliation, файловые блокировки, default/runtime drift и доставку
файлов в отдельные процессы. Допустимо как краткосрочная доводка, но не как
целевая схема после перехода production на PostgreSQL.

### Перевести JSON-файлы в YAML

Отклонено. YAML улучшает ручное чтение, но не решает согласованность процессов,
конкурентную запись, audit и множество реестров. Дополнительно появляется более
сложная модель типов и требования безопасного parser-а.

### Один общий `portal.yaml` или `portal.json`

Отклонено. Создаёт общую блокировку, общий rollback и большой blast radius для
несвязанных прав, workflow, AI и presentation-настроек.

### Одна строка БД на каждое простое поле

Отклонено. Теряются типизированная структура и атомарная кросс-полевая
валидация, увеличиваются количество запросов и сложность версионирования.

### Перенести в PostgreSQL вообще все файлы `contracts/`

Отклонено. Git остаётся подходящим источником схем, дефолтов, справочников и
рецензируемых системных контрактов. В БД попадает только рабочее состояние,
которое действительно меняется через runtime workflow.

### Добавить Redis/pub-sub для инвалидации файлового кэша

Отклонено до появления измеренной потребности. Это новый runtime-сервис, который
не устраняет двойственность file+DB и требует отдельного ADR/deployment-контура.

## Последствия

Положительные:

- один источник рабочей версии и одна транзакция для значения и аудита;
- одинаковое актуальное значение во всех Django workers;
- исчезают default/runtime file drift и staged file/DB reconciliation для
  мигрированных документов;
- единый реестр вместо повторяющихся списков путей и валидаторов;
- agent-runtime получает ту же ревизию, что Django;
- интерфейс можно упрощать независимо от физических границ документов.

Отрицательные:

- миграция затрагивает security-критичный role/workflow read path;
- требуется явное версионирование схем и миграция рабочих документов;
- dev-запуск переводимого runtime workflow требует PostgreSQL, что соответствует
  ADR-0029, но отличается от старой file-first модели;
- Git diff больше не показывает текущую рабочую версию напрямую; её обеспечивают
  audit-снимки и безопасный export;
- agent-runtime временно зависит от доступности Django gateway; нужен
  ограниченный last-known-good кэш и закрытый отказ для несовместимой версии.

## Условия принятия ADR

До смены статуса на `Accepted` должны быть утверждены:

- инвентарь и классификация всех 29 документов;
- точная матрица первой миграционной волны;
- модель закрытого отказа для role/workflow и AI gateway;
- окно cutover/rollback и место backup legacy-файлов;
- e2e-матрица ролей, multi-worker, rollback и agent-runtime;
- обновление backup/restore для `RuntimeSettingDocument` и `SettingsChange`.

Само принятие ADR не означает автоматическую миграцию production. Каждый
cutover выполняется отдельным task packet и фиксируется executor/acceptance
отчётами.
