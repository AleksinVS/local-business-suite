# ADR-0045: Закрытый доступ без роли и роль новых пользователей по умолчанию

- Статус: Accepted
- Дата: 2026-08-26
- Связанные решения: ADR-0039, ADR-0040, ADR-0043

## Контекст

ADR-0039 временно давал активному пользователю без роли совместимый профиль
`default_board_viewer`. До завершения миграции ADR-0043 рабочий контракт может
не содержать явную роль `viewer`, поэтому новый пользователь получает просмотр
канбана и связанных медизделий до назначения роли. Общая навигация также
показывает часть разделов без проверки эффективных ролевых правил, а браузерное
«Избранное» может сохранять ссылку от другого пользователя.

Для эксплуатации системы безопаснее, чтобы отсутствие роли означало отсутствие
продуктового доступа. Одновременно владельцу нужна управляемая политика создания
учётных записей: оставить пользователя без роли либо сразу назначить выбранную
контрактную роль.

## Решение

1. Неявный профиль `default_board_viewer` больше не участвует в runtime-проверках.
   Активный пользователь без контрактной роли получает пустой набор ролевых правил.
2. Навигация по канбану, медизделиям и ИИ-чату строится из эффективного доступа.
   Браузерное «Избранное» фильтруется серверным списком разрешённых пунктов.
3. Контракт `role_rules.json` получает служебный блок `$defaults` с полем
   `new_user_role`. Значение `null` означает «не назначать роль» и является
   безопасным значением по умолчанию. Строковое значение обязано ссылаться на
   существующую контрактную роль.
4. Изменять роль новых пользователей может только активный суперпользователь
   через единый раздел «Доступ». Запись выполняется атомарно в
   `data/contracts/role_rules.json`, с optimistic lock и `SettingsChange`.
5. Локальное создание и автоматическое создание внешнего пользователя читают
   настройку под общей access-блокировкой. Если роль настроена, её группа
   назначается в той же транзакции и создаётся `AccessAssignmentAudit`.
6. Настройка влияет только на новые учётные записи. Существующие пользователи
   без роли не изменяются автоматически.

## Рассмотренные альтернативы

- Оставить `default_board_viewer` до отдельной миграции. Отклонено: новый
  пользователь продолжает получать доступ до явного решения администратора.
- Хранить роль в переменной окружения. Отклонено: это бизнес-политика доступа,
  которую нужно менять атомарно через управляемый runtime-контракт и аудит.
- Назначать роль всем существующим пользователям без роли. Отклонено: массовое
  изменение доступа требует отдельного явного решения и предварительного отчёта.

## Последствия

- После обновления пользователи без роли перестают видеть и открывать рабочие
  разделы, основанные на ролевом доступе.
- При `new_user_role = null` новый пользователь остаётся без продуктовых прав.
- Ошибка конфигурации или отсутствующая группа роли останавливает создание
  пользователя без частичной записи.
- Совместимые функции миграции ADR-0043 могут оставаться для разбора старых
  журналов, но не являются источником runtime-доступа.
