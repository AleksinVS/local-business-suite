# LBS Factory v3.4 — прогрессивная сложность и OpenFGA

**Статус:** предлагаемые требования к будущей реализации, НЕ уже работающая функция.  
**Дата:** 2026-10-21.  
**Приоритет:** при расхождениях с проектными требованиями v3.3 этот документ определяет новую целевую семантику простой реализации. Он не меняет текущие принятые ADR и runtime без отдельного согласованного изменения кода.

## 1. Обязательная модульность без обязательной распределённости

1. У каждой возможности (Wiki, коммуникации, задачи/канбан, склад, Waiting List, авторизация, агент, интеграции) есть предметная ответственность, владелец данных и явный интерфейс.
2. Любой предметный модуль можно независимо включить/отключить для внедрения. Серверный запрет относится и к HTTP/API, и к AI tools, и к фоновым заданиям. Отключение не удаляет данные.
3. Один Django runtime, одна PostgreSQL и один Docker Compose допустимы для простого внедрения. Микросервисы, отдельный брокер, самостоятельный IAM, hot-install стороннего кода не обязательны.
4. Достаточно **одного работающего провайдера** и предусмотренной точки замены. Не писать несколько реализаций заранее.
5. Сложность наращивается по отдельным возможностям после подтверждения потребности. Перед вводом нового компонента описать проблему, простую альтернативу, новый отказный сценарий, проверку и обратимый переход.

## 2. Рабочая Wiki без блокирующего review

**Новое базовое правило:** безопасные рабочие знания из интервью/документов агент сразу сохраняет в существующей Markdown/Git Wiki. Знание немедленно доступно уполномоченным пользователям и агентам; оно НЕ обязательно является официально утверждённым регламентом.

Отдельно от имеющегося lifecycle вводится необязательный для старых страниц confirmation_state:

| Состояние | Доступно обычному разрешённому поиску | Нужен просмотр человеком до записи |
|---|---|---|
| working | Да | Нет |
| needs_confirmation | Да, с пометкой о сомнении | Нет |
| confirmed | Да, со следом подтверждения | Подтверждение произведено по инициативе владельца/правил |

Существующие legacy-страницы lifecycle=pending **не раскрывать автоматически**: они могли быть закрыты по иным основаниям. Для новой рабочей записи предполагается lifecycle=current и отдельный confirmation_state. Редакция frontmatter — совместимая миграция с проверкой действующих валидаторов и клиентов. Отсутствие поля в исторической записи не означает подтверждения человеком.

### Реестр знаний, требующих подтверждения

**Knowledge Confirmation Register** — видимый список страниц со статусом needs_confirmation, **а не дополнительная обязательная очередь выпуска**. Поля: ссылка на страницу, причина, источник (если указан), ответственный (необязательно), дата изменения. Действия: открыть, уточнить, подтвердить, снять отметку, архивировать.

Реестр — **перестраиваемая проекция Wiki-канона**, без второй редактируемой таблицы истины. Если реестр или поиск отказал, Wiki всё ещё записывает и открывает канонические страницы; список восстанавливается при сверке.

Отметку может поставить агент при существенном противоречии, неясном источнике, устаревании или подготовке официального регламента. **Не нужно отмечать каждую страницу и назначать проверяющего каждому интервью**. Руководитель небольшой организации может периодически просматривать список по своему расписанию. Сам review необязателен для обычных рабочих сведений и обязателен только для специально определённой категории или официального выпуска.

Обычный ответ агента отличает working/needs_confirmation от confirmed и указывает источник, если он известен. Не позволять модели представлять гипотезу как официальное распоряжение. При исправлении рабочей записи сохраняется история Git.

**Не упрощать:** атомарную запись, Git-историю, проверенные резервные копии/восстановление, простые права, защиту секретов от попадания в историю Git, отделение сырых чувствительных документов/интервью от Wiki, запрет выдачи закрытого текста модели без проверки доступа.

## 3. Минимальные правила безопасности без корпоративной бюрократии

| Риск | Небольшое внедрение | Усложнение только при необходимости |
|---|---|---|
| Потеря данных | Автоматический backup на отдельном носителе + проверка восстановления | HA/репликация |
| Угон учётки | Индивидуальный логин, безопасные пароли, HTTPS/VPN, MFA администраторам и удалённым пользователям | SSO/SCIM |
| Утечка документов | Общий и закрытый корпуса, простая ACL, личный чат для закрытых ответов | Пер-документные отношения/компартменты |
| Ошибка агента | Read-only по умолчанию, опасные записи через проверенное действие/подтверждение | Многоступенчатые approvals |
| Недостоверные знания | Статус working + источник и необязательный реестр вопросов | Строгий review официальных категорий |
| Авария интеграции | Таймаут, понятная ошибка, идемпотентный write | Отдельная шина и DLQ |
| Ошибка обновления | Версии и простая инструкция rollback | Blue/green deployment |

Размер компании **не равен уровню риска**: небольшой медцентр может нуждаться в сильной защите медицинских данных. Организационные меры (назначить одного ответственного за Wiki, периодически просматривать вопросы, согласовывать реальные регламенты) часто лучше нового сложного software workflow, но не заменяют backup, аутентификацию или ограничения на опасные действия.

## 4. Развитие по уровням: каждая возможность отдельно

- **L0 / простой профиль:** одна инсталляция, один writer Wiki, PostgreSQL FTS, один агент или без агентов, простые роли, прямые интеграции, функциональная модульность.
- **L1 / сотрудничество:** групповые комнаты, Telegram и Битрикс24 по необходимости; дополнительные простые группы, фоновый worker для долгих работ.
- **L2 / сложный совместный доступ:** индивидуальное sharing, вложенные ресурсы и связанные комнаты/проекты; по необходимости OpenFGA, A2A для независимых агентов и специализированный поиск.
- **L3 / специальные условия:** отдельные сервисы, расширенная авторизация, контроль регулируемых данных, более строгая эксплуатация.

Это НЕ четыре разных кодовых продукта, не тарифы и не классификация организаций. У одной организации могут быть Wiki с L2 ACL и другие функции на L0.

## 5. OpenFGA: полезность и границы

OpenFGA — open-source ReBAC authorization engine с API Check, BatchCheck, ListObjects и моделью relation tuples (subject–relation–resource). Работает on-prem, поддерживает PostgreSQL, но добавляет сетевой вызов, хранилище прав и отдельный сценарий отказа.

**Когда полезен, даже в маленькой организации:** отдельные страницы Wiki делят несколько пересекающихся проектных команд; доступ наследуется от пространства/папки; участники комнат и проекты имеют сложные связи; становится трудно поддерживать собственные проверки отношений нескольких доменов.

**Когда избыточен:** viewer/editor/admin, свои/чужие подразделения, один общий и один закрытый корпус, простые чаты без выборочного обмена документами. Нынешняя LBS Access с flat roles и domain ACL достаточна.

### Архитектурное решение

**Сейчас предусмотреть порт, но не включать OpenFGA в обязательный runtime.** Для ресурсных отношений использовать LocalResourceACL как default. В будущем можно подключить OpenFGAResourceACL **к одному определённому типу ресурса**, например пространствам/страницам Wiki.

~~~python
class ResourceRelationshipBackend:
    def can_access(self, subject_ref, relation, resource_ref, context) -> bool: ...
    def list_permitted(self, subject_ref, relation, resource_type, context): ...
    def set_relation(self, actor, subject_ref, relation, resource_ref, allowed): ...
~~~

Это логический контракт, НЕ требование немедленно реализовать сетевой сервис или общий policy DSL.

- **LBS Access** остаётся владельцем роли, capability и защищённых системных полномочий.
- **ResourceRelationshipBackend** владеет конкретными предметными связями; на один тип ресурса ровно один активный writable backend, без постоянной двойной записи.
- **DomainPolicy** проверяет бизнес-инварианты и фактическую операцию. Права на данные Битрикс24 и 1С остаются у этих систем.
- Подделанный Telegram ID, имя, роль или заявление агентного Task не создают grant.
- Если подключённый OpenFGA недоступен, соответствующие закрытые ресурсы дают deny/контролируемую деградацию, но **не silent fallback allow**. Другие модули на local ACL работают самостоятельно.

### Когда делать первый пилот

Реализовать OpenFGA-адаптер, если подтверждено хотя бы одно: частые индивидуальные выдачи доступа к страницам/комнатам; сложное наследование прав по иерархии; систематическое дублирование связной логики ACL между несколькими модулями; реальный pilot показал более простой код при приемлемом p95 и возможности восстановления.

**Пилот только на одном ресурсном типе:** model/version/store, стабильные IDs, golden positive/negative тесты; backfill отношений; read-only сравнение решений LocalACL/OpenFGA; явное cutover и rollback. В production — PostgreSQL, защищённое подключение и тест отказа. In-memory режим OpenFGA — только разработка: данные в нём теряются при остановке.

Не включать экспериментальные динамические условия OpenFGA без отдельного требования; проверить реальную политику кэширования/согласованности отзывов, избегать удалённой проверки каждой строки списка.

## 6. Roadmap и критерии приёмки

**S0:** тест текущих grants, Wiki и backup+restore; не менять одновременно хранилище ролей.  
**S1:** агент записывает серию безопасных рабочих сведений без обязательного review; часть отмечает needs_confirmation; реестр не тормозит поиск/пополнение; legacy pending закрыт.  
**S2:** один агент и нужные каналы, прямые API-интеграции, подтверждение опасных записей.  
**S3:** независимо включаемые Kanban/WorkOrders, Waiting List, Warehouse без потери данных и обхода disabled gate.  
**S4 / условно:** OpenFGA, A2A, отдельные services, embeddings и broker — только при подтверждённых требованиях и отдельных ADR.

**Stop/no-go:** потеря канонической Wiki-страницы, невозможность восстановления, утечка закрытых источников, обязательная human review-очередь обычного Discovery, две независимые authority одной ресурсной связи, silent allow при отказе внешней авторизации, независимый бизнес-модуль нельзя отключить без поломки ядра.

**Связанные документы:** 01_CONCEPT.md, 03_LLM_WIKI.md, 04_CRITICAL_REVIEW.md, 05_ROADMAP_AND_ACCEPTANCE.md, 07_ACCESS_ARCHITECTURE.md, 08_ACCESS_MIGRATION_AND_TESTS.md. Перед code change оформить/согласовать корректирующий ADR к существующим решениям о Wiki и LBS Access; эта концепция сама по себе не меняет действующий код.

## 7. Контентная приватность в минимальном профиле L0

Wiki-first/Review-optional сохраняется, но **до сохранения и выдачи** обязательна единая библиотечная подготовка разрешённой версии текста и метаданных. Реальные источники подключаются только после устранения обходов file ingestion/`adapter_check` и контроля старых индексов. `pii_off` для узкого внутреннего использования остаётся возможным, но не разрешает raw во внешний LLM. Оригиналы доступны через авторизованный доменный `original_read`, не через безопасный поиск. Никакого обязательного DLP-сервиса, сложной privacy-очереди или review всех знаний.

Практический план: [10_CONTENT_PRIVACY_PIPELINE.md](10_CONTENT_PRIVACY_PIPELINE.md).


## 8. Эволюционная интеграция CROW и OKF v0.2

OKF v0.2 — формат корпоративных знаний независимо от реализации. CROW — опциональный заменяемый модуль; первый этап использует его штатные алгоритмы, `raw`, индексы и ревизии через LBS-адаптер, выделенную область Git-канона и единственный writer. `MemorySourceObject` остаётся, прямой Source API внутри CROW — условный будущий этап.

До CROW выполняется единый [Content Privacy Pipeline](10_CONTENT_PRIVACY_PIPELINE.md), в том числе для запросов к внешнему LLM/classifier. Несколько логических CROW-пространств разрешаются LBS Access. Внутри разрешённого bundle LBS формирует отфильтрованное дерево `Folder/Note` **до штатного `Steps.select`**, без изменений алгоритма CROW; при несовместимых write-ACL отдельные CROW write-partitions предотвращают cross-ACL merge. Запрещённые raw доступны только после отдельной проверки прав источника; не включать второй контролирующий editor/registry. `working` записывается сразу; `needs_confirmation` не блокирует ingest. Legacy `pending` остаётся закрытым. Новые страницы соответствуют OKF сразу; поскольку продуктивных внедрений Wiki нет, перенос старых данных не требуется.

Полная спецификация: [11_CROW_OKF_INTEGRATION.md](11_CROW_OKF_INTEGRATION.md), [инженерный план](12_CROW_IMPLEMENTATION_PLAN.md), [ADR-0051](../../adr/ADR-0051-crow-pluggable-okf-knowledge-provider.md) (Proposed).
