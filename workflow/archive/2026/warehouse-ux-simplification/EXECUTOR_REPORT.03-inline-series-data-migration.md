# Отчёт исполнения 03: inline-серия и миграция данных

## Результат

Завершён целевой переход от самостоятельной `StockLot` к серии как снимку
складского движения. Рабочие модели, проведение, сторно, проекция, отчёты и
legacy-импорт больше не требуют таблицу партий. Финальная миграция удаляет
`StockLot` только после автоматических сверок и явной операторской контрольной
точки для непустой базы.

Система хранения складских runtime-настроек не изменялась: настройки продолжают
читаться через типизированный документ `warehouse.settings` с политикой
`database_override` и валидатором домена.

## Модель и инварианты

- `StockDocumentLine`, `StockEntry` и `StockBalance` хранят прямую ссылку на
  позицию, отображаемую `series`, нормализованный `series_key`, `expires_on` и
  `incomplete_reason`.
- Нормализация: Unicode NFC, удаление внешних и повторных пробелов, `casefold`
  только для ключа; исходный регистр отображаемой серии сохраняется.
- Новый ключ остатка:
  `department + warehouse + location + item + series_key + expires_on + funding_source`.
- Проведение и сторно копируют поля серии в неизменяемую проводку. Проекция
  остаётся восстанавливаемой из проводок.
- Одинаковая непустая нормализованная серия одной позиции с разными сроками
  блокируется при проведении. Перед повторной проверкой проведение блокирует
  строки всех затронутых `WarehouseItem` в порядке первичного ключа, поэтому
  конкурентные приходы одной позиции сериализуются в PostgreSQL. Миграция также
  останавливается до изменения схемы и не выбирает срок самостоятельно.
- Legacy-проверка создаёт критическую проблему `series_expiry_conflict`; commit
  импорта при такой проблеме запрещён.
- Ссылки legacy на позицию и источник разрешаются сначала по явному коду
  (`code`/`legacy_key`), а при его отсутствии — только по однозначному имени.
  Отображаемое имя больше не используется как целевой код при наличии кода.
- Проекционные SHA-256 во всех трёх миграциях и runtime-сверке используют один
  порядок: числовые идентификаторы как числа, затем `series_key`, заданные сроки
  по дате, `NULL` последним и идентификатор источника.

## Последовательность миграции

1. `0003_inline_series_expand` добавляет nullable-поля, переносит данные из
   `StockLot`, проверяет соответствие позиции, конфликт сроков и равенство
   журнала/проекции. Дополнительно сверяет для каждой проводки документ,
   `document_line`, `line.lot`, `entry.lot` и товар серии; несогласованный снимок
   прерывает миграцию атомарно. До продолжения записывает контрольные суммы
   проводок, строк документов и агрегированной проекции в складской аудит.
2. `0004_inline_series_switch_projection` проверяет контрольную сумму журнала,
   пересобирает и объединяет остатки по новому ключу, делает целевые поля
   обязательными и добавляет индексы/уникальность. Этот шаг обратим: обратная
   функция восстанавливает старую проекцию по `lot_id` из неизменяемых проводок.
3. Для непустой базы в состоянии `0004` обязательна команда:

   ```text
   python manage.py warehouse_reconcile_inline_series --actor <superuser> --record-checkpoint
   ```

   Команда повторно сверяет журнал и проекцию, ищет конфликты сроков, считает
   стабильные SHA-256 и пишет атрибутированную контрольную точку аудита.
4. `0005_inline_series_contract` сверяет автоматические и операторскую
   контрольные точки с текущими данными, затем удаляет три внешних ключа и
   таблицу `StockLot`. Для пустой новой базы операторская точка не требуется.
   Contract-шаг намеренно необратим средствами схемы; откат после него требует
   резервной копии. Безопасный обратимый рубеж — `0004`.

## Остаточные замечания

- Уникальность nullable-срока на уровне БД использует PostgreSQL-семантику
  `nulls_distinct=False`, а конкурентный барьер — `SELECT ... FOR UPDATE`.
  SQLite не реализует обе гарантии. Поэтому SQLite допустим только как
  однописательская аварийная/тестовая среда; гарантия конкурентного проведения
  относится к production PostgreSQL.
- Инструкции deployment/operations с остановкой на `0004` и обязательной
  операторской сверкой обновлены ведущим агентом вне write scope этого пакета.
- Полный набор проекта не запускался исполнителем согласно ограничению пакета;
  итоговая межмодульная приёмка остаётся за ведущим агентом.
