# LBS Factory v3.3 — пакет архитектурных решений

Статус: **предлагаемая концепция для согласования; НЕ инструкция немедленно менять production**.
Дата: 2026-10-12.
База ревью исходников: `AleksinVS/local-business-suite`, `main`, SHA `4ea22b2dcbd6ce5e101b26064b8bfc02a501dfe3` (проверенный снимок; повторно сверить перед работами).

## Назначение

LBS Factory — agent-first набор инструментов обследования, проектирования, сборки, внедрения и сопровождения корпоративных информационных сред. Конкретное решение составляется из существующих ИС, open-source продуктов, конфигураций, навыков и только необходимого собственного кода. Не все внедрения обязаны содержать единый сервер или веб-портал LBS.

## Решения, принятые по итогам обсуждения

1. Композиция возможностей и провайдеров; всё предметное подключается по необходимости.
2. LLM-Wiki основана на нынешнем `apps.memory`, а не пишется заново.
3. Межагентное взаимодействие предусматривается **сразу на уровне контрактов ядра**, но без обязательного брокера или самописного многоагентного фреймворка.
4. Встроенный LangGraph/LangChain агент — один из опциональных провайдеров; Pi/Claude и другие агенты подключаются через адаптеры.
5. Telegram, on-prem Web Chat/группы, Битрикс24, задачи/канбан, интеграции, идентичность и навыки внедрения — независимые способности, не обязательный стек.
6. Агенты готовят изменения; высокорисковые действия проходят проверяемое исполнение, права и подтверждение.
7. **Kanban/WorkOrders, Waiting List и Warehouse переписываются как подключаемые опциональные предметные компоненты**, с сохранением данных и без обязательного разделения на микросервисы.
8. **Текущую модель управления правами сохраняем и развиваем как LBS Access** — подключаемый прикладной AuthorizationProvider. Общие role/grant/capability механизмы отвязываются от `apps.workorders`; безопасность сетевого многопользовательского профиля никогда не отключается.

## Файлы

- `01_CONCEPT.md` — цели, состав ядра, capabilities/providers, целевая топология.
- `02_AGENT_INTERACTION.md` — агентный реестр, Task API, A2A/MCP/AG-UI, доверие, примеры и приемочные тесты.
- `03_LLM_WIKI.md` — эволюция `apps.memory`, канон знаний, ingest, review, ACL, индексация и упрощение.
- `04_CRITICAL_REVIEW.md` — намеренно критическое ревью, список рисков и способов упрощения.
- `05_ROADMAP_AND_ACCEPTANCE.md` — миграционный план, агентные пакеты задач, тестовые критерии и обязательные ADR.
- `06_PLUGGABLE_BUSINESS_MODULES.md` — детальная спецификация извлечения трёх текущих бизнес-приложений в подключаемые компоненты, риски, этапы, acceptance и задания.
- `07_ACCESS_ARCHITECTURE.md` — развитие текущей системы прав: роли, capabilities, identities, агенты, Wiki, чат, Битрикс24, контракт расширения.
- `08_ACCESS_MIGRATION_AND_TESTS.md` — этапы ACCESS-00..07, задания AX-00..07, тестовая матрица, rollback и ADR.

## Как пользоваться

1. Утвердить решения, помеченные `D` и открытые вопросы в `04_CRITICAL_REVIEW.md`.
2. Агент-архитектор делает актуальную проверку репозитория и dependency map без изменения бизнес-кода.
3. Реализаторы идут по пакетам `P0—P6` из `05_ROADMAP_AND_ACCEPTANCE.md` и сквозному направлению `ACCESS-00..07` из `08_ACCESS_MIGRATION_AND_TESTS.md`, через изолированные PR и проверки.
4. Старую документацию `LBS_Platform_v2` не переписывать молча: оформить **новую редакцию ADR**, явно изменяющую направление LBS Factory.
5. Соблюдать `AGENTS.md`, включая Git safety, секреты, актуализацию `.desc.json` и `make gen-struct`, `make verify-fast/verify-profile/verify-full`.
