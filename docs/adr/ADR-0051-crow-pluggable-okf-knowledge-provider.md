# ADR-0051. CROW и агентское редактирование общей OKF-вики

**Статус** — Accepted. Принято 21 октября 2026 года, пересмотрено владельцем 13 ноября 2026 года. Это целевая архитектура. Состояние продуктивных установок определяется отдельно.

**Область решения** — корпуса LBS с провайдером CROW. Профиль L0 в `apps.memory` остаётся доступен. Эталон совместимости — upstream [CROW v1.0.1](https://github.com/crow-hq/llm-wiki-v2/tree/v1.0.1), коммит `88828ac86a723ae682ef416fc19f5c62afeb5673`, формат корпоративных статей — OKF v0.2.

## Контекст и изменение решения

В октябрьской редакции вся содержательная запись в CROW-корпус шла через `Wiki.ingest`. В параллельном проекте первые статьи выглядели как журнал действий агентов. Один документ может менять несколько тем, а несколько документов — одну тему. Автору расследования нужны доступ к существующим статьям и возможность сразу внести сформулированный вывод. Передача готовой редакции в `remember` запускает повторную маршрутизацию и допускает повторное слияние текста. Причины конкретных неудачных прогонов предстоит проверить на исходном материале. [Октябрьская редакция](https://github.com/AleksinVS/local-business-suite/blob/599933ecd6fee714c950ec5c47e8b5785d4f87fc/docs/adr/ADR-0051-crow-pluggable-okf-knowledge-provider.md)

По уточнению владельца от 13 ноября 2026 года вики запускали в LBS только для тестов. Первую реализацию проверяем на чистом корпусе OKF. Перенос прежних статей в объём работ не входит. Это уточнение касается только вики.

## Решение

| Задача | Ответственный и граница |
|---|---|
| Готовое знание из работы агента | Основной агент ищет, дочитывает любые доступные статьи и источники и сам создаёт или меняет тематические Markdown-файлы. Он может поправить несколько статей, одну или закончить задачу без изменений в вики. Опубликованный текст сохраняет авторскую редакцию. |
| Поиск | CROW обслуживает поиск по разрешённым пространствам. Агент может перейти по ссылкам и запросить другую разрешённую страницу независимо от ранга. Расширенный контекст добавляет доступные строки таблиц, версии источников и признаки расхождений. |
| Классификация предлагаемой правки | В v1.0.1 есть программный клиент `Classifier.choice/nouls/ask` и отдельные шаги `route/match/consolidate`. Штатной команды CLI/MCP «классифицировать произвольную правку без записи» нет. Тонкий Python-адаптер формирует закрытый вопрос по материалу и разрешённым страницам. Он возвращает подсказку, идентификаторы кандидатов и при наличии оценки модели. Классификация сама ничего не записывает. Агент вправе уточнить выбор или продолжить без подсказки. |
| Исходный материал | Штатный CROW принимает допущенный новый источник через ingest/sync, сохраняет происхождение, создаёт или объединяет заметки. Оригинал или его доступная версия остаётся у источника. Готовые авторские статьи исключены из входящих каталогов синхронизации. |
| Поиск и устранение противоречий | За этот процесс отвечает CROW с адаптером LBS. Штатный `ask/conflict` обозначает возможное расхождение в контексте запроса. Штатный revise может обновить заметку по новой редакции того же документа при выполнении его условий. Для разных источников адаптер показывает агенту обе позиции и их основания. Агент устанавливает применимость и исправляет затронутые страницы напрямую. При нехватке оснований обе версии сохраняются с условиями или открытым вопросом. |
| Реструктуризация | CROW предлагает и выполняет операции над деревом и ссылками. Для переноса заметок доступны `audit_routes`, `move_note(s)`; для областей — предложения, переименование и объединение. Разделение содержания одной статьи на две, уточнение смысла и переработка нескольких тем относятся к прямой редактуре агента. |

Такое разделение реализуется адаптерами вокруг неизменённой поставки CROW. В редакторском сценарии используются обычные чтение, создание и редактирование Markdown в разрешённой рабочей области. Сервис публикации, специальный API пакетных правок, обязательная промежуточная БД и обязательный повторный модельный проход не входят в первый этап. Само предложение классификатора или совпадение темы не даёт полномочий на правку. [Клиент классификатора](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.1/src/llmw2/models/classifier.py#L44) · [Шаги](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.1/docs/library/steps.md) · [Ревизии и конфликты](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.1/docs/wiki/crow.md#good-to-know)

## Кто фиксирует изменения и как LBS находит статьи

В управляемом LBS агент завершает содержательную правку, а хост после успешной проверки фиксирует одним Git-коммитом только файлы этой операции. В тот же коммит входят связанные правки ссылок и навигации. При пустом результате коммита нет. При пересечении с чужими правками хост сохраняет предыдущую зафиксированную версию и возвращает конфликт. Во внешней рабочей копии действует обычный Git-процесс проекта. Универсальный навык не требует от агента отдельного вызова Git или регистрации статьи.

Обычные авторские и импортированные CROW-статьи могут не содержать ключа `status`. В OKF v0.2 это означает `stable`. LBS регистрирует такую статью как `active` при соблюдении прав и условий видимости. `active` остаётся значением внутреннего реестра. Явные `draft` и `deprecated` из внешнего источника сохраняются с их смыслом. Права и подтверждение конкретной редакции учитываются отдельно. Штатный CROW не фильтрует статьи по верхнеуровневому `status`. [OKF v0.2, §5.2–5.4](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/0b87c52c6ef999286c745e19998fdfcd03d5dbee/SPEC.md#L388-L422) · [Совместимость CROW 1.0.1 с OKF](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.1/README.md#L432-L444)

CROW обнаруживает новую Note непосредственно в каталоге. Для корпоративного реестра расширяем `memory_reconcile`: после коммита команда сверяет статьи конкретного раздела на зафиксированной ревизии Git с данными LBS по устойчивому ID. Пропущенный запуск можно повторить при старте или по таймеру. Сверка обновляет только производные данные раздела. Целевой порядок требует доработки команды. Сейчас она сверяет лишь ранее зарегистрированные статьи. [Исполнительный план](../architecture/lbs-factory/12_CROW_IMPLEMENTATION_PLAN.md)

## Общий корпус, границы доступа и восстановление

- На каждую физическую область приходится один канонический набор OKF-файлов в Git. Авторские правки и изменяющие операции CROW проходят в том же режиме эксклюзивной записи. Самый простой пилот — один ответственный агент и последовательные операции по разделу. Если действуют фоновые импортёры, CLI, UI или другие процессы, все они должны соблюдать общую блокировку. Читают завершённую редакцию. Проверяются изменённые пути и основания, после Git-коммита обновляются проекции и кэш. Предыдущая версия видна до завершения операции либо чтение временно приостанавливается.
- Доверенный инженерный агент может работать штатными файловыми инструментами внутри разрешённого корпуса. Пользовательский агент в многопользовательской среде получает эквивалентные операции чтения и редактирования под своей идентичностью через ограниченную рабочую область или существующие инструменты хоста. Путь, символьная ссылка, история Git и служебные каталоги не дают дополнительных прав. Перед прямой записью LBS определяет допустимые назначения, перед передачей модели — разрешённую проекцию, перед включением в Git — проверяет фактические изменения.
- LBS Access определяет пространство и ограничения отдельной заметки. Применяются оба условия. Для автоматического импорта, слияния, связей и перемещений выбирается физический раздел с совместимой видимостью. Постраничный запрет на чтение в общем дереве сам по себе не изолирует нативные мутации. Новая страница регистрируется с политикой области до выдачи другим. Поиск, классификатор и ссылки получают только доступные сведения, включая подписи и фрагменты. Чтение raw и каждой архивной версии проверяется отдельно.
- Автор сохраняет стабильные ID, основания, неизвестные поля frontmatter и действующие ссылки. Правка содержания требует пересмотра подтверждения соответствующей редакции. `working` доступно без обязательного согласования. Для авторской статьи новая генерация из сырых источников не является способом восстановления. Git/OKF, разрешения и резервная копия `raw/.archive/.llmw2/sync` восстанавливаются согласованно. Проекции перестраиваются из канона. Открытый [долг по персональным данным](../planning/active/knowledge-personal-data-git-policy-debt.md) сохраняет отдельный статус.
- Публичный Source API остаётся отдельным будущим решением. Используются существующие Source Adapters, идентичность и версия источника, хеш допущенного представления. Подтверждение пользователя, права и хранение исходных байтов не делегируются классификатору CROW.

## Альтернативы и последствия

Штатный ingest для любого текста удобен для импорта, но лишает автора надёжного способа адресно уточнить существующее объяснение. Собственный публикатор дал бы транзакцию пакетной редактуры, однако для согласованного режима такой контракт преждевременен. Изменение upstream ради общего редактора связывало бы обновления библиотеки с устройством LBS. Выбраны прямая авторская редактура и штатная обработка исходников в одном корпусе. Плата за этот выбор — проверка совместимости ручных страниц с поиском, индексами, слиянием, реструктуризацией и восстановлением CROW.

При отключении CROW разрешённые пользователи и агенты сохраняют доступ к Markdown через LBS. Проверяемые возможности классификации, поиска и обогащения контекста определяются включённым провайдером. Перед включением CROW в поставку уточняется применимый режим лицензии AGPL-3.0-or-later. Дополнительные плагины оцениваются по конкретной функции и тестируются независимо.
