# Ускорение тестов без снижения покрытия

Статус: active.

Дата: 2026-08-06.

## Назначение

Документ задает короткий цикл обратной связи для разработчиков и агентов. Политика качества остается в `docs/guides/TESTING_POLICY.md`; здесь описано, как не платить временем и лимитами за повторение заведомо лишних проверок.

## Основной принцип

Проверки выполняются ступенчато: от самого узкого и дешевого набора к полному. Переход на следующую ступень нужен только после успешной предыдущей или когда риск изменения прямо требует более широкого сценария.

1. Синтаксис и системная проверка.
2. Один измененный тест или затронутый модуль.
3. Интеграционные тесты затронутого контура.
4. Нужный e2e-сценарий.
5. Полный набор — один раз перед приемкой крупной работы или в CI.

Документационная и низкорисковая конфигурационная правка не требует полного набора, если она не меняет исполняемое поведение.

## Команды

Установка зафиксированных средств разработки:

```bash
make install-dev
```

Самый частый цикл:

```bash
make verify-fast TEST_SCOPE=apps/ai/tests/test_views.py
make test-failed
```

`make test-fast` использует pytest-django с `--reuse-db`, останавливается после первого падения и хранит базу SQLite в `.local/`. Первый запуск создает схему, последующие переиспользуют ее.

Три пользовательских уровня:

```bash
make verify-fast TEST_SCOPE=<pytest-path>
make verify-profile PROFILE=<ai|memory|ui|contracts|deployment>
make verify-full
```

- `verify-fast` выполняет дешевые проверки и целевой набор без `slow`;
- `verify-profile` запускает заранее заданную связку модулей и контрактов;
- `verify-full` создает чистую базу, проверяет миграции/контракты и является
  контрольным прогоном;
- `test-failed` повторяет только падения предыдущего запуска;
- `test-profile` показывает 25 самых медленных тестов;
- `test-parallel` передает workers только `not serial`, затем отдельно выполняет
  `serial` последовательно.

Для одного теста pytest использует путь и `::`:

```bash
make test-fast TEST_SCOPE=apps/accounts/tests.py::LDAPAuthConfigTests::test_ad_group_sync_removes_only_ad_managed_missing_roles
```

## Маркеры

- `unit` — без базы данных, браузера, файлового или внешнего сервиса;
- `integration` — связка Django view/service/model, контрактов или нескольких компонентов;
- `slow` — заметно дорогой сценарий, который можно исключить из промежуточного прогона;
- `serial` — тест меняет общее файловое, модульное или процессное состояние.

Новый тест следует маркировать сразу. Каждый тест обязан иметь ровно один
основной маркер `unit`/`integration`; pytest отклоняет неклассифицированный или
двойной основной маркер.

## Фикстуры и зависимости

- Неизменяемые записи для всего `TestCase` создавать в `setUpTestData`, а не в `setUp`.
- Для теста без базы использовать `SimpleTestCase`.
- Тестовый профиль использует быстрый MD5 hasher, локальную память для почты и `.local/test-media` для файлов. Проверку настоящего алгоритма хеширования следует выполнять отдельно с явным `override_settings`.
- Сеть, LLM, OCR, SMTP/IMAP и внешние API заменять детерминированными заглушками. Реальные вызовы относятся к отдельным eval или ручным проверкам.
- Ожидание заменять наблюдением состояния; если нужен timeout, использовать минимальный интервал, достаточный для проверяемого поведения.

## Базы и параллельный запуск

После изменения миграций или тестовых настроек выполнить `make verify-full`.
Если быстрый режим обнаружил несовместимую сохраненную схему, выполнить
`make test-db-reset`: команда удаляет только известные
`.local/test-default*.sqlite3*`, не очищая остальную `.local/`.

`make test-parallel` нельзя использовать как единственное доказательство
готовности. Цель сама исключает `serial` из workers и запускает такие тесты
отдельно, но финальный контрольный барьер остается последовательным
`make verify-full`.

## Правила экономии времени и вывода для агентов

- Перед проверкой зафиксировать исходный `git status --short`; не применять `git stash`, `git restore`, `git reset`, `git clean` и аналоги без прямого запроса владельца.
- Обычный промежуточный запуск должен укладываться в 2 минуты. Если он стабильно дольше, сузить scope или сначала профилировать; один полный прогон оставить финальной приемке/CI.
- После правки запускать минимальный тест, который способен обнаружить ошибку в измененном поведении.
- Не повторять одну и ту же упавшую команду больше двух раз без изменения кода, окружения или новой проверяемой гипотезы.
- Не создавать субагента только для запуска одной известной команды: ее дешевле выполнить основным агентом или в CI.
- Использовать субагента для самостоятельного анализа либо комплексной матрицы множества простых проверок, когда дешевая модель действительно сокращает стоимость и объем контекста основного агента.
- Для комплексной матрицы передавать цель, read scope, список действий, критерии приемки, запрет на изменения и структурированный формат отчета.
- Не запускать полный набор одновременно основным и проверочным агентом.
- Для первой диагностики использовать `--maxfail=1`, краткий traceback и `make test-failed`; подробный вывод получать только для конкретного падения.
- Не включать `-vv`, полный traceback и подробный coverage в обычном цикле агента.
- В сообщение другому агенту или владельцу передавать команду, итоговый счетчик, первое содержательное падение и путь к логу, а не полный вывод.
- Длинные логи, отчеты покрытия, Playwright trace/video и временные скрипты хранить только в `.local/`.

Примеры экономически оправданной комплексной проверки дешевой моделью:

- проверить десятки сочетаний ролей, прав и ожидаемых HTTP-кодов;
- пройти набор независимых маршрутов или UI-состояний по готовой таблице;
- сопоставить контракты и их потребителей в нескольких подсистемах;
- проверить журналы, артефакты и результаты нескольких целевых команд;
- выполнить однотипные проверки на нескольких клиентах или конфигурациях.

Если те же действия надежно выполняются одной командой test runner без анализа, субагент не нужен.

## E2E

Тесты Playwright имеют тематические теги: `@smoke`, `@ai`, `@workorders`, `@notifications`.

```bash
bash scripts/e2e/run-smoke.sh
npm run test:e2e -- --grep @ai
npm run test:e2e -- --grep @workorders
```

`@smoke` выполняет настоящий вход и проверяет основной shell портала. HTTP health
имеет отдельный тег `@http` и не требует установки браузера. Скрипт smoke
создает отдельную SQLite-базу и эфемерного пользователя, запускает Django и
складывает журналы только в `.local/`.

Локально trace и video отключены. В CI trace создается на первой повторной попытке, а video сохраняется только при падении.

## Когда нужен полный прогон

Полный `make verify-full` нужен:

- перед приемкой крупного или многошагового изменения;
- после миграций, изменения test runner/settings или общих фикстур;
- после изменений прав, privacy/security, контрактов или нескольких доменов;
- когда выборочные тесты не позволяют надежно определить затронутый scope.

Для обычного pull request полный набор исполняется один раз на Python 3.11. Python 3.12 выполняет быстрый модульный набор; полный совместимый прогон обеих версий выполняется после попадания в `main`.
