## Доступно в репозитории

Шлюз включается для явно зарегистрированного раздела `org/crow/<имя>`. Обычные задачи работают с тем же Git-каноном через пять инструментов. Для полного цикла поиска, чтения и записи достаточно движка `basic`. Закреплённый CROW 1.0.1 подключает BM25 по телу статьи и типизированный классификатор. Устанавливать CROW для работы автора в Markdown необязательно.

| Инструмент | Что получает агент |
| --- | --- |
| `knowledge.search` | Список доступных разделов без аргументов, список статей или результаты по тексту внутри выбранного `bundle_id`. Выдача содержит устойчивые ID и полный SHA |
| `knowledge.get` | Точный опубликованный Markdown разрешённой Note в выбранном разделе по устойчивому `knowledge_id` или относительному `path`, SHA и вычисленное состояние подтверждения |
| `knowledge.source` | Проверенный фрагмент текущего представления источника LBS и ссылку `{source_code, source_object_id, text_hash}`. Эта ссылка используется в `source_refs` статьи |
| `knowledge.compare` | Предложение локального классификатора для двух доступных статей или для статьи и предложенного текста с проверенным основанием. Применение вывода остаётся за автором |
| `knowledge.edit` | Результат одной операции в разделе. Автор передаёт полный прочитанный `expected_revision` и `files` с готовыми Markdown-статьями по относительным путям. Значение `null` удаляет статью. Хост проверяет источники, связи и полномочия и возвращает SHA |

У `memory.search` есть необязательный `bundle_id` для явного поиска в Wiki при `corpus: knowledge`. Общий поиск исторической памяти сохраняет свой прежний охват. Правила подготовки связной статьи описаны в [навыке автора](../../../contracts/ai/skills/wiki-author/SKILL.md); правила выбора источника и доступа задаёт проект.

Каждая Note должна пройти регистрацию на текущем Git SHA, проверку полномочий актёра, источников, чувствительности и места передачи данных. Раздел с пониженными правами отдельных статей допускает чтение разрешённого подмножества. Шлюз записи работает только в однородном разделе, все страницы которого этому автору доступны. Источники с собственным `sources`/raw, архивы, чтение истории, изменение статусов, нативный ingest и физическое перераспределение рубрик остаются за границей этих пяти инструментов. Эта поставка не требует внешней модели. `knowledge.compare` требует локальную совместимую модель. Доступ к данным, разрешённым только локально, пока закрыт в шлюзе чат-агента, поскольку сам чат может работать во внешней среде. [Настройка и проверка на хосте](../../deployment/MEMORY_DEPLOYMENT.md#подключение-раздела-okf).

## 1. Кто ведёт Wiki

Канон LBS — тематические Markdown-страницы с Frontmatter по OKF v0.2 в Git. Уполномоченный агент с контекстом задачи читает нужные страницы, **сам редактирует существующие и создаёт новые файлы** в доступной рабочей копии. За одну задачу он вправе изменить несколько статей или ни одной. Операционные события, включая причины отказа и ход рассуждений, остаются в задаче или техническом аудите. В статье читатель получает результат, условия применения, исключения и проверяемые основания. Одна задача может дать несколько выводов, а одна статья объединяет выводы из нескольких источников.

Тот же Git-канон доступен для импорта внешних документов. Для потока документов CROW умеет извлекать содержание, находить подходящую папку, сливать близкие материалы, связывать и индексировать страницы. Если из документа следуют независимые изменения нескольких тем, агент обрабатывает их отдельно. Инструменты поиска, структурирования, классификации и проверки вызываются по необходимости. Фабрика не требует ни пропускать готовую агентскую статью через `remember/ingest`, ни реализовывать отдельный сервис публикации, менеджер плагинов или новый API пакетных правок.

| Кто | Ответственность |
|---|---|
| Автор задачи или импорта | Определяет, какой будущий вопрос должна раскрыть страница, ищет существующее знание, сверяет первоисточники, редактирует текст и связи |
| LBS Access и владелец источника | Действия инициатора, область файлов, права на каждую версию источника, адресаты и допустимые назначения данных |
| Файловый и Git-контур LBS | Эксклюзивная запись, проверка собственных файлов операции и восстановление партиции. Целевая сверка по коммиту регистрирует статьи и обновляет производные индексы |
| CROW и другие инструменты | Автономные проверки или действия с явным результатом и областью. Данные и полномочия передаёт LBS |

Например, после исправления сверки остатков агент дополняет «Сверка остатков» условием воспроизведения и «Проверка обмена» новым способом обнаружить это состояние. Ссылка ведёт к разрешённому свидетельству. Если обе статьи уже точно описывают результат, работа завершается без редакции. Открытое частное наблюдение можно оставить в исходной задаче или явно обозначить гипотезой с областью применимости.

## 2. Как использовать CROW по частям

| Задача | Возможность версии 1.0.1 | Граница |
|---|---|---|
| Задать ограниченный вопрос модели | Публичный Python-класс `llmw2.Classifier` принимает конфигурацию и `UsageTracker`. `choice` выбирает вариант, `nouls` оценивает утверждения, `ask` принимает типизированные вопросы | Вызывается без `Wiki`, Git или файлов. LBS определяет формулировку, варианты, допустимый контекст и интерпретацию результата. Можно подставить другого поставщика |
| Подобрать тему и связанные страницы | `CROW.route`, `match`, `consolidate`, `relate`, `select` доступны в наборе публичных `Steps`. Именованные функции штатных наборов можно вызывать отдельно | Им требуются `StepContext` и данные CROW (`Folder`, `Note`, `Candidate` в зависимости от шага). Для вызова вне конвейера адаптер подготавливает только разрешённые входы и учитывает возможный LLM fallback. `match` возвращает одну Note либо None |
| Найти страницы | `Wiki.search` выполняет BM25 по заголовку, описанию и телу без `See also`. Через переданный embedder возможен дополнительный семантический поиск. В CROW-режиме `ask/select` может переупорядочить кандидатов классификатором и использовать навигацию при пустом поиске | Штатный `search` работает по своему bundle. Параметр `where` фильтрует metadata и не обеспечивает авторизацию. Для разных ACL см. §4.2 |
| Навести порядок в структуре | `audit_routes(apply=False)` предлагает переносы в другие ветви. `move_note(s)`, `describe_folder`, `create_folder`, `rename_root`, `merge_roots` выполняют конкретные структурные операции. `check()` находит расхождения индекса и повреждённые ссылки | Перенос выполняется в разрешённых границах общего Git-порядка. Перенос папки и смысловое объединение/разделение статей — разные действия. `check()` диагностирует ошибки |
| Импортировать подготовленный документ | `Wiki.ingest`, `ingest_file`, `ingest_many` выполняют полный цикл с provenance и разрешённым `raw`. Гибридный MCP передаёт написание модели клиента | Для обычного текстового источника `summarize → Candidate`, затем создание одной основной заметки или слияние с одной. Ссылки, ревизии и перемещения могут менять дополнительные файлы. `remember(text, title?)` не задаёт целевой путь и не является точным редактированием статьи |
| Проанализировать расхождение | В `ask` проверка `ask/conflict` при нескольких отобранных заметках может попросить модель назвать расходящиеся значения и их источники. Тот же тип вопроса можно задать отдельно на разрешённых фрагментах | Это подсказка к ответу. Разрешение расхождения и собственно правка выполняются по §4.3. При узко определённой новой редакции одного источника CROW отдельно поддерживает `revise` с архивированием |

В CROW закреплены десять сигнатур `extract, summarize, route, name_folder, match, consolidate, merge, relate, select, answer`. Внутри штатной обработки порядок, блокировка и запись принадлежат `Wiki`. Пакетные `plan/plan_more` и последующий `split` при одиночном импорте встроены в `Wiki`, работают и при собственном `route`. До вызова штатного импорта нужно разрешить весь набор его возможных действий в выбранной партиции. Стабильность сигнатур допускает изменения промптов, порогов, лимитов кандидатов, моделей и выбранных страниц при minor-обновлении.

## 3. Пространства, Git и хранение

LBS выдаёт разрешённое логическое пространство (`common`, `accounting`, проект). Для различий в доступе на запись одно пространство может содержать несколько непересекающихся физических OKF-bundles. Например, `org/crow/accounting/` и `org/crow/accounting-restricted/` — два соседних корня; `users/` и прочие корпуса остаются за пределами обоих. Историческое имя пути `crow/` не определяет автора страниц. Не запускать штатный CROW на всём `data/knowledge_repo` или `org/`. `common` также имеет аудиторию, определённую Access.

В Git входят разрешённые страницы, `index.md` и `log.md` соответствующего bundle. Нативные `raw/`, `.archive/`, курсоры `.llmw2/sync/`, временные файлы и модельные журналы не публикуются в Git и общем поиске. Назначение содержимого `.llmw2/` проверяется по закреплённой версии: утрата незакрытых предложений или курсоров имеет другие последствия, чем сброс воспроизводимого поискового кеша. Для каждого служебного вида назначаются доступ, срок хранения и восстановление. `.gitignore` ограничивает добавление в Git, но не чтение файлов другими службами. Исключения нужны также в файловых обходах, общем графе и индексах. Содержимое закрытой партиции не переносится в индекс верхнего уровня или в открытое сообщение коммита.

Для прямой работы агент получает рабочую область, в которой ему разрешено чтение всего видимого содержания и истории Git. При смешанных ACL широкий checkout, свободный shell в общем хранилище или скрытые только интерфейсом файлы обходят предметные права. Использовать уже предоставленное разрешённое представление/изолированную область. В управляемой установке исключительность записи обеспечивает общий механизм LBS; обычный разработчик в разрешённой рабочей копии применяет согласованный порядок Git. Копирование всего дерева, отдельный staging или постоянный отдельный процесс на каждого агента не требуются.

## 4. Работа со страницами

### 4.1 Запись

1. Определить целевую аудиторию, пространство, версию канона и доступ к материалу. Проверить права на тематику и каждую затронутую страницу, включая побочные изменения ссылок и индексов. Текст, заголовок, метаданные, имена путей и ссылки проходят текущую политику назначения до возможной передачи модели.
2. Автор меняет Markdown в разрешённых файлах. Может добавить новую тематическую статью сразу, дополнить раздел в существующей, разделить или свести несколько страниц. Новая страница содержит стабильный глобальный `knowledge_id`, тип, понятный заголовок, описание, происхождение и состояние знания. Обновляя Frontmatter, сохранить неизвестные поля и ссылки; прежнее подтверждение не переносится на новый смысл. Для ссылки на чтение оригинала действует отдельный допуск.
3. Редактирование агентом, человеком и native CROW использует один порядок доступа на запись к общему состоянию. В общем рабочем дереве блокировка LBS (`knowledge_repo_lock` или действующий эквивалент) покрывает затронутые файлы, производные каталоги и Git-коммит. Независимые рабочие копии можно редактировать параллельно; перед объединением сверить базовую ревизию и осмысленно согласовать пересечение изменений. Внутренний lock CROW синхронизирует сотрудничающих пользователей библиотеки, но не сторонние редакторы или Git.
4. Для прямой записи в том же изменении актуализировать индекс затронутой папки, записи о новых или перенесённых подпапках в родительских индексах, изменившиеся входящие ссылки и журнал действий над Wiki. В `log.md` достаточно записи об изменении самих знаний под `## YYYY-MM-DD`, исключая рабочую трассу. Агент может поддерживать их непосредственно по формату или использовать подходящую команду в той же партиции; native CROW сам ведёт их для собственных операций. Независимый параллельный генератор тех же файлов запрещён.
5. Проверить фактический diff, права, базовые версии файлов, ID, происхождение, состояние подтверждения и ссылки. В управляемом LBS хост выполняет обычный коммит только после успешного завершения конкретной Wiki-операции. В него входят лишь её собственные изменения. Если в том же файле есть неразделённые чужие правки, разрешить конфликт в изолированной рабочей копии либо вернуть его автору. Пустой diff завершает операцию без коммита. Во внешней инженерной среде момент фиксации определяют правила проекта; для LBS исходной точкой служит полученная опубликованная ревизия.
6. До коммита читатели видят предыдущую согласованную версию и соответствующие ей источники либо ждут. При сбое восстановить только затронутые файлы и служебные данные. После коммита запустить [сверку корпуса](#46-что-индексируется). Повторная обработка того же коммита не меняет авторский текст.

Если публикация невозможна, содержимое задачи сохраняется в её существующих материалах. Успешный импорт не подтверждает истинность результата. Технический след операции для восстановления использует существующий механизм LBS; не требуется заводить отдельный «пакет изменений», второй writer-сервис или обязательный редакторский workflow. Проверять итог по ревизии Git, а не по факту завершения вызова модели.

### 4.2 Поиск и ручные файлы

Проверено 13 ноября 2026 года на временном bundle CROW 1.0.1 без вызовов моделей. После обычной записи нового `<topic>/policy.md` с Frontmatter `type: Note` публичные `Wiki.tree()` и `Wiki.search()` обнаружили страницу, хотя её ещё не перечислял `<topic>/index.md`. `Wiki.check()` сообщил о пропущенной записи, а корневой лог сам не изменился. Добавление строки в существующий раздел индекса в формате `* [Название](policy.md) - Описание` устранило расхождение. При правке тела BM25 нашёл новый контрольный термин и перестал находить старый. Проверена также команда `move_note`: сохранила ID, обновила обычную входящую относительную ссылку, затронутые индексы и лог.

Причина — загрузчик обходит каталоги и читает подходящие файлы `.md`; родительский индекс даёт описания подпапок, но не задаёт список разрешённых страниц. Корневой `raw/`, скрытые пути, `index.md` и `log.md` исключены из дерева заметок. Не полагаться на обнаружение файла как на доказательство валидности, регистрации в LBS, актуальности индекса, двусторонности смысловой ссылки или допуска читателя. При прямом переименовании обычными средствами агент обновляет входящие/исходящие ссылки сам. При наличии разрешений публичный `move_note(s)` удобен для технического переноса внутри bundle. `Wiki.check()` выявляет ряд расхождений и не ремонтирует их автоматически.

Сохранённый CROW `generated.body_hash` описывает последнее тело, подготовленное генератором. Ручная правка, меняющая основной текст, делает этот хеш несовпадающим. Сохранять исходную метку генератора либо её корректное происхождение, не создавать подложную отметку для агентского текста. При повторном импорте хеш блокирует специальную автоматическую замену старой версии источника; обычное слияние остаётся возможным. До запуска native импорта определить, разрешено ли изменение редакторских и подтверждённых страниц в данной партиции. `rebuild()` удаляет имеющиеся заметки, raw и архивы и компилирует их заново. Новая статья, существующая только в Wiki, может быть утрачена при такой процедуре. Для актуализации поиска после ручных правок достаточно штатного чтения и обновления LBS-проекции; не перестраивать канон через `rebuild`.

В октябрьской основе LBS применялся `Steps.select` с обходом дерева. В 1.0.1 поиск при `ask` в CROW-режиме по умолчанию начинает с локального поиска по содержанию, возможен вызов классификатора для переупорядочения. На пустом результате используется fallback. Нельзя передавать поиску в 1.0.1 проекцию из одних названий и ожидать полнотекстовой релевантности. Поиск и выдача в LBS работают с разрешёнными кандидатами **до** ранжирования, внешних embeddings и fallback. Для целиком разрешённого однородного bundle допустим публичный `Wiki.search`. В смешанном пространстве передать отфильтрованный снимок/разрешённые тексты подходящему инструменту или выполнить уже имеющийся защищённый поиск LBS; проверка результатов после unrestricted `Wiki.search/ask` либо фильтр `where` эту границу не обеспечивают.

### 4.3 Конфликты знаний и подтверждения

Сначала автор формулирует сопоставимые утверждения. Проверяет объекты, даты действия, продукт и версию, подразделение, исключения, полномочия источника. Фразы «платёж согласует руководитель» и «платёж согласует бухгалтер» могут относиться к разным суммам или этапам. JEV/Laya может отметить фрагменты как совместимые, уточняющие или противоречащие и помочь найти материалы. Вероятность, большинство ссылок, дата получения и факт успешного merge сами по себе не устанавливают действующую норму.

Если основания достаточны, автор прямо правит затронутые тематические статьи: разграничивает области действия, отмечает дату вступления в силу, помещает историческое правило в соответствующий контекст, сохраняет ссылки на версии. Если подтверждения нет, фиксирует разногласие, обе доступные версии и открытый вопрос, при необходимости `needs_confirmation`. Если выбор нормы относится к владельцу регламента, подтверждает уполномоченный человек по существующему механизму LBS. Обычная рабочая информация может сразу иметь `working`. `lifecycle: pending` для специальных закрытых случаев остаётся закрытым. Машинная правка подтверждённой страницы не наследует автоматически подтверждение, относящееся к предыдущей содержательной редакции.

У CROW есть отдельная узкая операция ревизии одного документа. При совпадающем сгенерированном теле, совместимом происхождении и подтверждённом сходстве версий она может сохранить прежнюю заметку в `.archive/` и обновить текущую. Она полезна для версий одного источника; противоречия между разными регламентами требуют содержательной работы автора.

### 4.4 Происхождение и импорт

Доменный `SourceAdapter` готовит `SourceObjectEnvelope`; `MemorySourceObject` и `MemorySearchDocument` сохраняют свои роли. При штатном импорте CROW в `raw/` попадает только представление, разрешённое для конкретной цели. Задать устойчивый `Origin(source, account, id, version, link)`. Версия включает редакцию исходника и версию парсера/преобразования. Повтор той же версии и хеша идемпотентен; изменение правил очистки или прав нельзя скрыть старым upstream `unchanged`. В LBS сохраняются связь с первоисточником и версия. Для авторской статьи источник может быть уже известным LBS `source_ref` или проверяемой версией доступного артефакта. Создавать для неё повторную фиктивную копию raw через CROW не требуется.

Git-ссылка на знание и доступ к его источнику регулируются отдельно. При отзыве источника переоценить законность выдачи производных фрагментов, временно закрыть сомнительное и инвалидировать кеш. Нативный `mark_removed` оставляет заметки. `purge` затрагивает целые заметки и может повторно обработать оставшиеся источники. Для корпуса с авторскими страницами оценить состав затронутых материалов и восстановление перед применением.

### 4.5 Физические границы записи

В нативном импорте классификатор видит входы для `route/match/consolidate/relate`, планирование и разделение. Такой обработчик выдаётся только полностью совместимой области чтения, правки и egress. При несовместимых правах LBS выбирает другую разрешённую партицию или ограничивает операцию; модель не должна сначала увидеть закрытые названия или создать перекрёстные ссылки. Экспорт очищенной производной в более широкую область подчиняется разрешению LBS и источника. Ни обычный фильтр поиска, ни разделение по папкам на одном открытом файловом доступе не изолируют данные.

### 4.6 Что индексируется

**Реализация в LBS.** Для обычных исторических страниц `memory_reconcile` по-прежнему сверяет известные активные карточки с файлами рабочего дерева. Для настроенного OKF-раздела эта же команда выполняет полную опись одного Git SHA, включая новые статьи, изменения, переносы и удаления. Рекурсивные обходы исторического корпуса исключают весь `org/crow`. Успешная опись и карточки фиксируются в одной транзакции Django. Отсутствующий корень, конфликт ID и неполная опись не гасят карточки. Готовность раздела проверяется по полному SHA и текущей политике. [Проектор OKF](../../../apps/memory/wiki_reconcile.py) · [Команда сверки](../../../apps/memory/management/commands/memory_reconcile.py).

**Целевой порядок сверки.** После коммита, получения внешних изменений, при старте и по настроенному таймеру LBS вызывает один механизм сверки в границах разрешённого физического корпуса. На старте прохода зафиксировать опубликованный SHA и читать файлы тематических статей именно из его Git-дерева. Исключить `raw/`, `.archive/`, `.llmw2/`, скрытые пути, временные файлы, `index.md` и `log.md`. Список статей для служебной сверки охватывает весь этот корпус; видимость конкретного запроса не используется как опись для определения удалений.

Сопоставить канон с реестром по устойчивому идентификатору статьи (правило в §5). Новый ID регистрируется с политикой области до выдачи. При прежнем ID и новом пути обновить существующую ссылку, при изменившемся содержимом или метаданных обновить проекцию и поисковые данные. Отсутствующий ID выводится из выдачи, включая старые поисковые записи, только после успешной полной описи этого корпуса. Дубли ID, конфликт пути, ошибка чтения или неполный обход не подтверждают удаление. Для небольшого корпуса достаточно полной описи путей и Git-хешей файлов с чтением изменившихся страниц; инкрементальный Git diff — возможная оптимизация.

Для одного корпуса согласовать параллельные запуски блокировкой либо сверкой ожидаемой версии перед обновлением. Отмечать SHA обработанным после успешного обновления производных данных. Пока работа не закончена, изменённые страницы имеют `index_pending`; устаревшая проекция не может раскрыть недоступный материал или выдаваться за текущую. Повтор после сбоя при том же SHA идемпотентен. Проверить перенос вместе с изменением текста, удаление, незарегистрированную статью и повторный запуск. [Запуски существующей команды](../../deployment/MEMORY_DEPLOYMENT.md#запуск-сверки-при-старте-и-по-расписанию).

### 4.7 Кеш и отзыв доступа

Снимок разрешённого bundle может переиспользовать дерево в памяти, тексты и проверенные ссылки конкретной Git-ревизии. Это не физическая копия всего каталога для каждого запроса. Кеш разрешённых представлений учитывает партицию и ревизию контента, актуальные полномочия, аудиторию, назначение данных и версию политики. При изменении файла/прав устаревшая запись закрывается или перестраивается. LBS получает разрешённые ID пакетно и повторяет проверку перед выдачей.

Деталь CROW 1.0.1: обычная загрузка проверяет файловые признаки и переиспользует результат разбора неизменившихся заметок. Внутри штатной пакетной сессии внешняя правка на месте может отразиться только в следующей сессии. Поэтому внешнее редактирование в обход общей блокировки одновременно с пакетным импортом не входит в поддерживаемые режимы.

### 4.8 Полный цикл CROW: подготовка контекста вокруг select

`knowledge.search` возвращает подходящие доступные заметки. Для `knowledge.prepare_context` агенту могут понадобиться ещё строки таблицы, прежняя версия или расхождение между источниками. Подготовка контекста использует разрешённые версии конкретных материалов:

- Для обращения к `raw` и `.archive/` независимо проверить право прочитать конкретный источник/версию и `destination`. При недостатке доступа возвращать доступную часть с признаком неполноты без раскрытия личности/пути закрытого источника. Финальные ссылки разрешает LBS.
- Штатная обработка таблиц CROW сохраняет листы как `sheet_text`, содержащий заголовок листа и CSV. Код `ingest_file(xlsx)` может разделить книгу на листы до переопределяемого `extract`. Если данные нуждаются в подготовке, LBS сначала применяет доступ и политику к колонкам/строкам, названиям и числовым данным, затем формирует совместимое представление и привязывает `Origin.id` каждого листа к файлу и листу. Подбор строк и статистика вычисляются только над разрешённым набором. Отдельно обрабатывать исчезнувший лист и связи при предразбиении.
- Для исторического вопроса извлекать разрешённую прошлую версию и обозначать дату. При межкорпусном поиске LBS ограничивает общий бюджет и передаёт для сопоставления только доступные версии; один `Wiki.ask` не сопоставляет несколько bundles.
- Для однородного разрешённого bundle можно использовать upstream-подготовку. На 1.0.1 у `Researcher.ask` помимо файлового чтения есть поисковый callback, история, проверка риска противоречий и строки таблиц. При смешанных ACL нельзя ограничиться заменой `answer` или фильтрацией уже полученной выдачи. Если нужен адаптер к приватным `Researcher/_with_*`, локализовать зависимость и проверить на закреплённой версии все чтения, поиск и fallback. Контекст также можно собрать из тех же источников через инструменты LBS, без обязательного подключения приватного кода.

[Поиск и дополнительное чтение в CROW 1.0.1](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.1/src/llmw2/agents/researcher.py) · [Особенности таблиц](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.1/src/llmw2/bundle/sheets.py)

### 4.9 Перестройка рубрик и статей

Запуск `audit_routes` возвращает конкретные предлагаемые переходы между ветвями. Автор проверяет, помогает ли новая рубрика читателю, и при согласии применяет перенос. Для разбиения смешанной статьи он создаёт подходящую тему, редактирует обе страницы, переносит относящиеся к ней свидетельства и проверяет входящие ссылки. Для объединения дублей он сводит содержание и исключения в устойчивую целевую статью, исправляет ссылки и сохраняет адресуемость прежних ID согласно действующим правилам LBS. Это редактирование доступно непосредственно из рабочей копии.

Авторы CROW опубликовали две причины различать техническое перемещение и редактуру. Автоматический перенос в кажущуюся широкой подрубрику или частый split ухудшали некоторые результаты на корпоративном справочнике. При нехватке контекста штатный merge длинной страницы сохраняет входной текст целым разделом без вызова модели. Оба случая полезно воспроизводить на материалах LBS при обновлении выбранных инструментов. [Эксперименты со структурой, PR #39](https://github.com/crow-hq/llm-wiki-v2/pull/39) · [Отчёт о потере текста и исправление merge](https://github.com/crow-hq/llm-wiki-v2/issues/25)

### 4.10 Реестр и политика доступа в LBS

В первой поставке соответствие `bundle_id → path`, читатели, авторы и сужения на ID задаются оператором в `LOCAL_BUSINESS_WIKI_BUNDLES`. Из Django берутся действующие пользователи, роли и группы. БД хранит производные карточки и результат сверки. Ниже описана целевая схема для нескольких пространств.

LBS Access остаётся источником действующих пользователей, групп, ролей и grants. Реестр пространств связывает `space_id` с `bundle_id`. Редкие ограничения отдельной Note привязываются к устойчивому `knowledge_id` в предметной политике/БД и могут сужать доступ пространства. Для чтения одновременно нужны активный субъект, право пространства, зарегистрированная разрешённая Note, допустимая чувствительность и аудитория. Отказ/неизвестная ACL приоритетны. Текущие `scope_tokens` могут ускорять выборку, но простое OR-пересечение ролей не реализует это AND-условие. Регистрация новой страницы при коммите должна предшествовать её выдаче. При отзыве роли кеш не сохраняет прежний допуск.

В YAML нет второй матрицы пользователей/групп. Допустимы идентификаторы, происхождение и метки чувствительности, нужные для проверки в LBS. Пользователь может читать производное знание, не имея права выгрузить весь оригинал. В групповом канале проверяется фактическая аудитория. Нативные HTTP, MCP, CLI и широкие рабочие каталоги не выдаются как обход Access.

## 5. OKF v0.2 и перенос страниц

| Данные | Канон и применение |
|---|---|
| `type: Note`, `title`, `description`, `sources` | Читаемая статья с описанием и проверяемыми свидетельствами. В bundle CROW раздел имеет свой `index.md`, общие действия с Wiki записываются в корневой `log.md` по датам |
| `knowledge_id`, native `id` CROW | Сохранить явный глобальный `knowledge_id`. Если штатная Note содержит только `id`, LBS детерминированно получает глобальный ID из пары (устойчивый `bundle_id`, native `id`) в выделенном пространстве идентификаторов. Привязка воспроизводится после восстановления без дописывания YAML. Внутри корпуса переименование сохраняет ID. Между корпусами перенос оформляется явно с сохранением прежней глобальной привязки; обнаружение того же native `id` в другом разделе само по себе не означает перенос. При конфликте ID остановить регистрацию затронутых записей. |
| Необязательное поле `status` и `lifecycle` | Отсутствующий `status` означает `stable`. Обычная текущая страница проецируется как `active` в `MemoryKnowledgeItem`. Полученные извне `draft` и `deprecated` сохраняются, учитываются при отборе и явно обозначаются при показе. CROW 1.0.1 не фильтрует Note по этому полю. LBS применяет собственные правила видимости, в том числе для закрытого `pending`. Внутренние значения Django не записываются в OKF. |
| `working/needs_confirmation/confirmed`, `verified` | Подтверждение привязано к реально проверенной версии. Метка пригодности `stable` сама по себе не подтверждает достоверность человеком |
| `sources[].resource`, ссылка LBS, версия, хеш подготовленного материала | Нативная `/raw/…` действительна внутри данного bundle. Для уже существующего источника LBS сохраняется стабильная разрешаемая ссылка на него. После перемещения проверяются все зависимости |

При разделении статьи новая тема получает отдельный ID и явную связь. При объединении проверить прежние ID и входящие ссылки внешних потребителей. При переносе внутри одной допустимой области проверить ID, ссылки, журналы, проекции и архивы. Между областями LBS проверяет обе политики, отсутствие расширения аудитории и работоспособность разрешаемых источников. Одна команда перемещения файла не переносит право доступа. CROW не определяет логику корпоративных подтверждений.

## 6. Приватность и восстановление

[Политика подготовки контента](10_CONTENT_PRIVACY_PIPELINE.md) различает `wiki_git`, `agent_context`, `external_llm` и другие назначения. Проверяется также выдача заголовков/путей и метаданных. Обязательная обработка всех персональных данных общим детектором не принята. В закрытом разрешённом режиме допустимая подготовленная копия может содержать ПДн; объём, место обработки, срок хранения и возможность попадания в Git задаёт согласованная политика. [Отдельное решение по ПДн и Git](../../planning/active/knowledge-personal-data-git-policy-debt.md)

Полная резервная копия native корпуса содержит согласованную ревизию Git, разрешённые `raw`, историческую `.archive`, невоспроизводимые служебные данные и настройки/права LBS. Восстанавливаемые поисковые кеши можно построить заново. Проверить работоспособность `previous_version`, ссылок на raw, редких ACL, статусов и исходных листов таблиц. У Git-копии без raw и архива остаётся текст страниц, но не все первоисточники или старые версии. Нельзя заменить восстановление редакционных статей переимпортом исходников. При падении native ingest до завершения зафиксировать состояние, ограничить выдачу затронутой партиции и довести восстановление до согласованного набора файлов; оставшийся raw удаляется только после проверки ссылок и retention.

## 7. Обновление и отключение

Внешние зависимости закрепляются по версии и скрыты за реальными точками вызова. Инструменты пишутся как обычные функции/адаптеры, могут использовать одну библиотеку и процесс. Каждый принимает доступный материал и возвращает понятный вызывающей стороне результат. Для смены decision-провайдера, поиска или линтера не нужно менять статью, Git-пути или `knowledge_id`. Без внешней модели агент может читать основную Wiki, редактировать статьи и использовать детерминированный поиск и проверки. Документировать, какие семантические возможности недоступны в конкретном профиле.

Перед сменой версии прогнать контрактные проверки по входам/выходам и контрольные вопросы по содержанию, затем оценить поведенческие отличия. При отключении CROW сохранить доступность страниц, разрешённых источников и проекций. Отдельно проверить восстановление специфичных для CROW функций архивов и табличных строк. Использование лицензионного кода/промптов upstream оценивается по конкретному способу поставки; при заимствовании только интерфейсной идеи копирование исходного кода не требуется.

## 8. Роль Source API

[ADR-0018](../../adr/ADR-0018-universal-source-adapters-memory-analytics.md) фиксирует адаптеры и форму исходных объектов; LBS Source API относится к чтению оригиналов и их версий. Он не является системой ACL заметок или обязательным новым микросервисом. Сохранить устойчивые `source_ref`, версии, политику происхождения, `MemorySourceObject`, бизнес-адаптеры. Режим доступа к оригиналу определяет его владелец, подготовленное представление для назначения — LBS.

Встраивание Source API вместо CROW `raw/` остаётся условной будущей отдельной работой, например если возникнут измеренные сложности с объёмом или отзывом. Такое изменение затрагивает происхождение и дедупликацию, чтение CSV и истории, удаление и восстановление. Если оно понадобится, проверить эквивалентность context/citations, прав и версий на одном корпусе. Замена `MemorySourceObject` на native raw не утверждена.

## 9. Проверка интеграции

- На одной реальной по структуре задаче агент обновляет две существующие темы, по другой создаёт новую страницу, повтор не создаёт дубль, а техническое действие без нового знания оставляет канон неизменным. Читатель может ответить по статье без истории выполнения задачи.
- Создать авторскую Note без `status`, проверить в CROW `tree/search` и в LBS по устойчивому ID. Уточнить её текст, переместить, затем удалить в тестовой ревизии. К каждой завершённой ревизии привести поиск, навигацию, ссылки и проекции. Повтор сверки не создаёт дублей. Для импортированных `draft` и `deprecated` проверить сохранение явного статуса и его учёт LBS.
- Два пользователя с разными допусками, в том числе внутри общего пространства, не получают запрещённые заголовки, описания, фрагменты, ссылки, raw, прошлые версии или строки таблиц. Проверить входы удалённой модели/embedding и fallback. Смена прав инвалидирует кеш.
- Содержательную редакцию `confirmed` и два противоречащих источника проверить с ограничением по дате или области, а также с неустранимой неопределённостью. Запуск `ask/conflict` сам не меняет страницы.
- Проверить конкурирующие действия автора и импорта, расхождение базовой ревизии, частичную запись native CROW и отказ регистрации после Git-коммита. При восстановлении не выдаются запрещённые или устаревшие данные, новая страница регистрируется ровно один раз. Резервная копия восстанавливает независимую авторскую статью, источники, архив и доступ.
- Те же задачи выполнить при отключённом CROW/JEV, проверяя именно доступные локальные функции. Для отдельного инструмента сравнить стоимость/задержку и его фактическое влияние на поиск нужной статьи или выявление расхождений. Отсутствие ключа обозначается как непройденная сетевая проверка, не препятствуя проверке прямой записи, Git, доступа и детерминированного поиска.
