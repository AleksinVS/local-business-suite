# Раздел «Склад»: реализация и миграция

## Цель

Создать общий складской домен для партийного и адресного учёта лекарств,
расходных материалов и медицинских изделий, добавить закрытые по умолчанию права
по подразделениям, три обязательных отчёта и воспроизводимую миграцию из старых
локальных баз.

## Бизнес-ценность

- одна система вместо локальных программ;
- остатки и сроки годности видны по подразделению и месту хранения;
- действия выполняются персонально и аудируются;
- отчёты восстанавливаются на дату из журнала;
- переход со старой базы можно повторить и проверить до запуска.

## Read Scope

- архитектура и модели `apps.core`, `apps.accounts`, `apps.inventory`,
  `apps.workorders`, `apps.settings_center`;
- `contracts/role_rules.json` и схема;
- пользовательские и deployment-инструкции;
- приватные legacy-файлы только для локального dry-run с ограничением выборки и
  без копирования в основной Git.

## Write Scope

- `apps/warehouse/`;
- общий read-only Access transport в `apps/core/integrations` и
  `scripts/windows`;
- role contract, схема, редактор и навигация;
- `templates/warehouse/`, `static/src/warehouse/`;
- целевые тесты и management-command e2e;
- `docs/guides/`, `docs/deployment/`, `README.md`;
- planning/workflow, `.desc.json`, `PROJECT_STRUCTURE.yaml`.

## Non-goals

- Не копировать таблицы Access один к одному.
- Не менять смысл `apps.inventory.MedicalDevice`.
- Не импортировать legacy-пароли и локальные пути.
- Не импортировать реквизиты подписантов из legacy.
- Не фиксировать общий организационный регламент остановки старой программы и
  переключения конкретного учреждения.
- Не реализовывать межподразделенческое перемещение, серверный PDF или
  специальную печатную форму в MVP.
- Не добавлять цены, закупки, отпуск пациенту, маркировку и специальные
  регуляторные режимы в MVP.
- Не вводить отдельный сервис, брокер или базу склада.

## Порядок

`01 → 02 → 03 → (04, 05) → 06`.

Пакеты 04–05 можно выполнять параллельно только после стабильных моделей,
политик и сервиса проведения. Они не должны одновременно менять один файл без
явного разделения write scope.

## Acceptance

- соблюдены инварианты ADR-0047;
- security matrix закрывает чужие подразделения;
- проведённые документы неизменяемы, остаток не уходит ниже нуля;
- текущая проекция пересобирается из проводок без расхождений;
- три отчёта работают на дату, применяют общий scope и формируют безопасные CSV
  и XLSX;
- migration dry-run, идемпотентный повтор и strict reconciliation проходят на
  синтетическом fixture;
- пилотная приватная база VOB3 проходит inspect/prepare/reconcile без утечки
  паролей и путей;
- выполнены целевые проверки и один `make verify-full` перед приёмкой;
- документация и карта структуры обновлены.

## Решения владельца

Зафиксировано 2026-08-31:

- дроби пока запрещены через точность единицы `0`, при этом поле БД имеет запас;
- номер требования необязателен;
- межподразделенческое перемещение отложено, разрешено только перемещение адреса
  внутри подразделения;
- пороги истечения находятся в runtime-настройках;
- серверный PDF и специальная печатная форма не нужны; CSV и XLSX входят в
  первый выпуск;
- `WarehouseReportProfile` остаётся и заполняется вручную;
- создаются отдельные роли `warehouse_operator`, `warehouse_controller` и
  `warehouse_administrator`;
- реквизиты подписантов из legacy не мигрируются;
- организационное переключение со старой системы не фиксируется в общем плане.

ADR-0047 принят. Числовые пороги истечения задаются в настройках до пилотного
запуска.
