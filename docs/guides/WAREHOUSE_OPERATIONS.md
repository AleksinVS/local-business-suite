# Раздел «Склад»: эксплуатация и миграция

## 1. Назначение

Раздел `/warehouse/` ведёт количественные остатки медикаментов, расходных
материалов и изделий по подразделению, складу, адресу, партии, сроку годности и
источнику финансирования. Поштучные основные средства остаются в
`apps.inventory`.

Проведённые документы и проводки не редактируются. Ошибка исправляется сторно
или корректировкой. Текущий `StockBalance` является пересобираемой проекцией
журнала `StockEntry`.

## 2. Подготовка новой установки

```bash
python manage.py bootstrap_runtime
python manage.py migrate
python manage.py seed_roles
python manage.py check
```

`warehouse.settings` читается через единый репозиторий настроек: Git-файл задаёт
дефолт, а изменённая рабочая версия хранится в PostgreSQL. Файловое runtime-зеркало
не создаётся. В deployment allowlist должен присутствовать `warehouse.settings`.
`seed_roles` создаёт группы
`warehouse_operator`, `warehouse_controller` и `warehouse_administrator` из
актуального `role_rules`.

Начальные права:

- `warehouse_operator` — просмотр и штатные операции в ветке подразделения;
- `warehouse_controller` — то же плюс списание, корректировка, сторно, адреса и
  профили отчётов;
- `warehouse_administrator` — просмотр, адреса и профили всей организации,
  общий каталог; без штатных операций и корректировок;
- superuser — резервный полный доступ.

Роли назначаются через раздел «Доступ». Складской администратор не получает
права изменять остатки автоматически.

## 3. Обновление действующей установки

Регистрация `warehouse.settings` не сливает `role_rules.json`. Для действующей
рабочей версии ролей применяется
существующий защищённый процесс:

1. Сформировать проверяемый candidate на основе текущего runtime `role_rules`:
   добавить каталог складских возможностей, а всем существующим ролям — только
   `none`/`false`. Не добавлять новые роли в этот первый candidate.
2. Выполнить preview и применить candidate командой
   `migrate_role_capabilities` с ожидаемыми runtime/Git hash и активным
   superuser-оператором.
3. В разделе «Доступ» создать три складские роли по Git-дефолту или применить
   их через те же аудитируемые сервисы определения ролей.
4. Выполнить `seed_roles`, затем назначить группы сотрудникам.
5. Проверить матрицу: сотрудник без роли получает 403, оператор не видит
   соседнее подразделение, администратор каталога не может провести документ.

Общий документ не фиксирует организационный порядок остановки старой программы
и переключения учреждения.

## 4. Настройки и справочники

В Центре настроек документ `warehouse.settings` содержит:

```json
{
  "default_quantity_precision": 0,
  "expiry_warning_days": [30, 90, 180]
}
```

Точность хранится в диапазоне `0..6`; первый выпуск использует целые количества.
После появления проводок точность единицы можно увеличить, но нельзя уменьшить.
Пороги срока должны быть уникальными неотрицательными целыми числами по
возрастанию.

Глобальный каталог содержит категории, единицы, номенклатуру и источники
финансирования. Склады и адреса всегда принадлежат подразделению. Для адресов
`quarantine` и `unassigned` штатная выдача запрещена.

`WarehouseReportProfile` заполняется вручную. Реквизиты подписантов из legacy не
импортируются.

## 5. Документы и отчёты

Штатные операции: начальный остаток, приход, выдача, внутреннее перемещение
адреса. Номер требования необязателен. Списание, корректировка и сторно требуют
повышенного права и причины. Межподразделенческое перемещение не поддерживается.

Перед первым приходом оператор регистрирует партию через экран «Зарегистрировать
партию». Серия и срок годности вводятся явно; если одно из значений неизвестно,
обязательна причина неполных данных. После появления проводок идентификационные
данные партии не изменяются.

При выдаче система запрещает просроченные и недоступные партии. Если выбрана не
самая ранняя доступная партия по FEFO, нужна причина отклонения.

Доступны три отчёта в HTML, CSV и XLSX:

- расход за период;
- стеллажная карта на дату;
- наличие в подразделении на дату.

CSV имеет UTF-8 BOM. CSV/XLSX записывают пользовательские значения как строки и
нейтрализуют префиксы формул. Область данных экспорта совпадает с экраном.

## 6. Проверка журнала

Только проверка без записи:

```bash
python manage.py warehouse_rebuild_balances --actor <username> --department-id <id> --check
```

Пересборка подтверждённой области:

```bash
python manage.py warehouse_rebuild_balances --actor <username> --department-id <id>
```

Полная проверка/пересборка без `--department-id` разрешена только superuser.

Сквозная проверка создаёт данные в транзакции и откатывает их после проверки:

```bash
python manage.py warehouse_acceptance_e2e
```

## 7. Legacy Access

Инструмент работает на Windows с установленным Microsoft ACE OLE DB. Источник
открывается только для чтения. `inspect` получает схему, индексы, счётчики и не
более `N` строк; поля паролей и похожие на секреты значения удаляются.

```powershell
python manage.py warehouse_legacy_inspect `
  --adapter access-v1 `
  --source C:\private\uls.mdb `
  --run-id <uuid> `
  --sample-size 5 `
  --dry-run
```

Сопоставления задаются отдельным локальным JSON, который не коммитится:

```json
{
  "opening_date": "2026-09-01",
  "departments": {"legacy name": 12},
  "units": {"шт.": "шт."}
}
```

Подготовка и применение:

```powershell
python manage.py warehouse_legacy_import --run-id <uuid> --source C:\private\uls.mdb --mappings C:\private\warehouse-map.json --dry-run
python manage.py warehouse_legacy_import --run-id <uuid> --mappings C:\private\warehouse-map.json --actor <username> --commit
python manage.py warehouse_legacy_reconcile --run-id <uuid> --strict
```

Landing package хранится только в `data/warehouse/imports/<uuid>` или
`.local/warehouse-import/<uuid>`. Повторная запись другого содержимого под тем
же `run-id` запрещена. Критические проблемы блокируют `--commit`; неизвестные
подразделения и единицы не создаются автоматически. `sett`, `tmp`, `treb`,
пароли и локальные пути не импортируются. Начальные остатки проводятся обычным
доменным сервисом, прямой записи `StockEntry`/`StockBalance` нет.

## 8. Диагностика

- 403 — проверить складскую роль и область подразделения;
- выдача отклонена — проверить остаток, срок, назначение адреса и FEFO;
- настройки не читаются — выполнить `bootstrap_runtime` и проверить
  `warehouse.settings` в Центре настроек;
- импорт заблокирован — изучить `WarehouseImportIssue` и dry-run summary;
- сверка расходится — не пересобирать проекцию до анализа исходных проводок и
  отчёта `warehouse_legacy_reconcile`.
