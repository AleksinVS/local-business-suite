# LBS Factory v3.4 — пакет архитектурных решений

Статус: **СОГЛАСОВАНО (Accepted) — целевая архитектура LBS Factory v3.4, 2026-10-21.** Это не утверждение о выполненной реализации и не разрешение немедленно менять production.
Редакция: 2026-10-21. Исторический baseline исходников указан ниже; перед изменением кода проверить актуальный HEAD.
База ревью исходников: `AleksinVS/local-business-suite`, `main`, SHA `4ea22b2dcbd6ce5e101b26064b8bfc02a501dfe3` (проверенный снимок; повторно сверить перед работами).

## Назначение

LBS Factory — agent-first набор инструментов обследования, проектирования, сборки, внедрения и сопровождения корпоративных информационных сред. Конкретное решение составляется из существующих ИС, open-source продуктов, конфигураций, навыков и только необходимого собственного кода. Не все внедрения обязаны содержать единый сервер или веб-портал LBS.

## Решения, принятые по итогам обсуждения

1. Композиция возможностей и провайдеров; всё предметное подключается по необходимости.
2. LLM-Wiki основана на apps.memory: рабочие знания сохраняются **сразу**, реестр требующих подтверждения сведений не блокирует запись и поиск.
3. Межагентное взаимодействие предусматривается на уровне контрактов, но начальный профиль использует одного агента; отдельный ledger, A2A и брокер добавляются при реальной потребности.
4. Встроенный LangGraph/LangChain агент — один из опциональных провайдеров; Pi/Claude и другие агенты подключаются через адаптеры.
5. Telegram, on-prem Web Chat/группы, Битрикс24, задачи/канбан, интеграции, идентичность и навыки внедрения — независимые способности, не обязательный стек.
6. Агенты готовят изменения; высокорисковые действия проходят проверяемое исполнение, права и подтверждение.
7. **Kanban/WorkOrders, Waiting List и Warehouse переписываются как подключаемые опциональные предметные компоненты**, с сохранением данных и без обязательного разделения на микросервисы.
8. **Текущую модель управления правами сохраняем и развиваем как LBS Access** — подключаемый прикладной AuthorizationProvider. Общие role/grant/capability механизмы отвязываются от `apps.workorders`; безопасность сетевого многопользовательского профиля никогда не отключается.

## Файлы

- `01_CONCEPT.md` — цели, состав ядра, capabilities/providers, целевая топология.
- `02_AGENT_INTERACTION.md` — агентный реестр, Task API, A2A/MCP/AG-UI, доверие, примеры и приемочные тесты.
- `03_LLM_WIKI.md` — **единая целевая модель Wiki v3.4 после ADR-0051:** Knowledge API, корпуса LBS/CROW, OKF, два режима поиска/контекста, Access и восстановление.
- `04_CRITICAL_REVIEW.md` — намеренно критическое ревью, список рисков и способов упрощения.
- `05_ROADMAP_AND_ACCEPTANCE.md` — согласованный план LBS/Factory; CROW-пакеты не дублируются, первичный источник технической реализации CROW — документ `12`.
- `06_PLUGGABLE_BUSINESS_MODULES.md` — детальная спецификация извлечения трёх текущих бизнес-приложений в подключаемые компоненты, риски, этапы, acceptance и задания.
- `07_ACCESS_ARCHITECTURE.md` — развитие текущей системы прав: роли, capabilities, identities, агенты, Wiki, чат, Битрикс24, контракт расширения.
- `08_ACCESS_MIGRATION_AND_TESTS.md` — этапы ACCESS-00..07, задания AX-00..07, тестовая матрица, rollback и ADR.
- `09_PROGRESSIVE_COMPLEXITY_AND_OPENFGA.md` — **целевая редакция v3.4**: обязательная модульность, неблокирующий реестр подтверждений, прогрессивное усложнение, optional OpenFGA.
- `10_CONTENT_PRIVACY_PIPELINE.md` — единый контракт безопасного представления текста и метаданных, разрывы в ingestion/adapter_check и поэтапная очистка индексов.
- `11_CROW_OKF_INTEGRATION.md` — подключаемый CROW почти без изменений, OKF v0.2 с первого этапа и подготовленный путь к Source API.
- `12_CROW_IMPLEMENTATION_PLAN.md` — **основной исполнительный план** CROW/OKF: пакеты CROW-00..06/05b, контракты и негативные проверки; Factory roadmap задаёт зависимости и критерии, не заменяет его.

**CROW / OKF:** согласованная архитектура интеграции описана в [`11_CROW_OKF_INTEGRATION.md`](11_CROW_OKF_INTEGRATION.md) и [ADR-0051](../../adr/ADR-0051-crow-pluggable-okf-knowledge-provider.md) (Accepted). CROW остаётся заменяемым модулем, сохраняет собственный `raw` на старте; список заметок — `select`, полный контекст с CSV/историей/подсказками — `Researcher.ask` c заменённым `Steps.answer`, базовое дерево кэшируется и получает только материалы после единого [privacy-контура](10_CONTENT_PRIVACY_PIPELINE.md). Поддержка OKF v0.2 обязательна для новых страниц; продуктивной Wiki пока нет, новый формат LBS приводится к OKF без миграции пользовательских данных. Source Adapters/Source API исторически запланированы независимо от CROW; они не заменяют LBS Access. В первом профиле CROW остаётся единым механизмом поиска знаний сразу в нескольких логических пространствах; LBS Access выбирает разрешённые пространства и заметки **перед `Steps.select`**, а финальная выдача проверяется повторно. Запись источников с несовместимыми правами выполняется в отдельные физические CROW write-partitions. **Внедрений Wiki пока нет: перенос исторических данных не требуется** (перепроверить перед работами). **Архитектура принята, в коде не реализована.** Для корпуса с CROW основной поиск знаний — CROW, а не параллельный общий FTS; native `raw/.archive/.llmw2/sync` резервируются отдельно от Git. При отключении CROW LBS обеспечивает базовое чтение OKF, но не автоматически его полный интеллектуальный контекст.

## Как пользоваться

**Приоритет v3.4:** обычные знания записываются без обязательного review по `09_PROGRESSIVE_COMPLEXITY_AND_OPENFGA.md`; перед Git/индексами/LLM действуют авторизация, защита секретов и согласованная политика назначения по `10_CONTENT_PRIVACY_PIPELINE.md`. **Универсальное PII-обнаружение/маскирование НЕ принято** — см. [долг по ПДн в знаниях и Git](../../planning/active/knowledge-personal-data-git-policy-debt.md). Production-семантика не меняется без отдельного внедрения и проверок.


1. Использовать этот пакет как **согласованную целевую архитектуру**; непроработанные вопросы вести отдельно в backlog/ADR, не трактовать согласование как выполнение работ. Для CROW отдельно открыт долг по персональным данным и Git.
2. Агент-архитектор делает актуальную проверку репозитория и dependency map без изменения бизнес-кода.
3. Реализаторы идут по Factory `P0—P6` из `05_ROADMAP_AND_ACCEPTANCE.md`, **по CROW-00..06 и CROW-05b из `12_CROW_IMPLEMENTATION_PLAN.md`**, а по правам — ACCESS-00..07 из `08_ACCESS_MIGRATION_AND_TESTS.md`. Не создавать конкурирующие задания на одни файлы.
4. Старую документацию `LBS_Platform_v2` не переписывать молча: оформить **новую редакцию ADR**, явно изменяющую направление LBS Factory.
5. Соблюдать `AGENTS.md`, включая Git safety, секреты, актуализацию `.desc.json` и `make gen-struct`, `make verify-fast/verify-profile/verify-full`.

**Открытый архитектурный долг:** [долг по ПДн в знаниях и Git](../../planning/active/knowledge-personal-data-git-policy-debt.md) — окончательная политика персональных данных для CROW `raw`, OKF Wiki, Git-истории, индексов и резервных копий. Не вводить обязательное массовое обезличивание до отдельного решения. Это не препятствует разработке и синтетическому пилоту.

## Зафиксировано в v3.4

Модульность остаётся обязательной без физического разделения на микросервисы. OpenFGA предусмотрен как будущая необязательная реализация ресурсных отношений, без замены существующей LBS Access и без включения в базовый runtime.

## Иерархия решений и проверка консистентности

**Сначала:** принятый [ADR-0051](../../adr/ADR-0051-crow-pluggable-okf-knowledge-provider.md) → [11_CROW_OKF_INTEGRATION.md](11_CROW_OKF_INTEGRATION.md) (полный контракт) → [03_LLM_WIKI.md](03_LLM_WIKI.md) (единая пользовательская модель) → [12_CROW_IMPLEMENTATION_PLAN.md](12_CROW_IMPLEMENTATION_PLAN.md) (технические этапы) → [05_ROADMAP_AND_ACCEPTANCE.md](05_ROADMAP_AND_ACCEPTANCE.md) (общие зависимости Factory).

Особенно важно: CROW **не** становится обязательным движком всей Factory, но для `provider=crow` именно native CROW создаёт и ищет Note; LBS управляет правами, privacy, Git-коммитом и восстановлением. `knowledge.search` (быстрый select) **не равно** `knowledge.prepare_context` (Researcher.ask с защищённым store). FTS сохраняется для source_data/других корпусов. Raw/archive не являются частью Git backup. До реального пилота с ПДн — отдельное решение о допустимых местах и назначениях; не трактовать `SafeProjection` как тотально обезличенный текст.
