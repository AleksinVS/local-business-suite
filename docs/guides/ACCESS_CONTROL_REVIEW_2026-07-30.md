# Ревью системы прав и доступа — 2026-07-30

Область: все приложения `apps/`, контракты ролей, шаблоны, админка, тесты.
Реализованные по итогам ревью решения зафиксированы в ADR-0034; остальные
находки перенесены в backlog (Next).

## Архитектура «как есть»

Три механизма авторизации:

1. **Capability-роли из контракта** `role_rules.json` + группы Django по имени
   роли — основной механизм (`apps/workorders/policies.py`, доменные `policies.py`).
2. **`is_staff` / `is_superuser`** — жёсткие гейты админки и settings_center.
3. **Django `Permission`** — точечно в `apps.memory` (+ scope-токены записей).

Сильные стороны (соответствуют лучшим практикам Django):

- Правильное разделение слоёв: `policies.py` (кто может) / `services.py`
  (изменения + аудит) / `views.py` (оркестрация) — вместо разбросанных по view
  проверок.
- Row-level доступ там, где спроектирован, применяется на уровне queryset
  (`visible_workorders_queryset`), а не пост-фактум: чужая запись даёт 404, не
  утечку факта существования. Это канонический паттерн (queryset-scoping)
  вместо тяжёлых per-object ACL.
- Контракт ролей редактируется через единый write-path с валидацией, атомарной
  записью и оптимистической блокировкой (ADR-0031).
- Шаблоны не содержат логики прав: флаги (`can_edit`, `show_*_nav`) приходят из
  policies через context — UI-скрытие вторично к серверным проверкам (ADR-0023).
- Двойная защита критичных операций (view + service layer, например
  `_require_superuser` в `apps/accounts/services.py`).
- Нет захардкоженных проверок по username; media — через защищённый диспетчер.

## Находки

Исправлено в рамках ADR-0034:

| Находка | Решение |
|---|---|
| Лист ожидания (ПДн пациентов) был доступен любому авторизованному | Права `view_waiting_list`/`create_waiting_list`, по умолчанию только роль `doctor`; пункт меню скрыт без права |
| `superuser_rules()` отстал от контракта (нет `memory_organization_*`) | Строится динамически из справочника `$capabilities` |
| Редактор ролей: захардкоженный неполный список флагов в двух местах | Флаги, подписи и комментарии — из `$capabilities` контракта |
| Права и группы непонятны нетехническому администратору | `$capabilities` (label+description), `description` ролей, `GroupProfile` для групп, легенда в редакторе ролей |
| Группы создавались только для 3 ролей канбана | `seed_roles` создаёт 9 предопределённых групп с профилями |
| Пункты меню «Аналитика»/«Лист ожидания» видны всем | Флаги `show_analytics_nav`/`show_waiting_list_nav` |

Открытые (перенесены в backlog, Next):

1. **`inventory` не ограничен веткой подразделения** — заказчик не видит чужое
   устройство через доску, но видит весь каталог через `inventory:list` напрямую
   (`apps/inventory/views.py` vs `apps/workorders/selectors.py:75-85`).
2. **`analytics` и дашборд `core` считают агрегаты по всем заявкам** без
   `visible_workorders_queryset` — скрытая зависимость от того, что
   `view_analytics` выдан только роли с `view_scope: all`.
3. **Управление колонками канбана не привязано к `Board.allowed_groups`**
   (`apps/workorders/views.py:804-853`) — обладатель `manage_board_columns`
   может менять колонки любой доски.
4. **Утечка справочника пользователей**: список всех пользователей в фильтре
   доски отдаётся любому зрителю доски (`apps/workorders/views.py:376`).
5. **Мёртвая проверка `ai.manage_skills`** — permission объявлен строкой, но не
   создан в моделях (`apps/ai/skill_authoring.py:19,28`); реально работает
   только capability `manage_ai_skills`. Убрать ветку `has_perm` или объявить
   permission.
6. **`can_manage_privileged_flags` нигде не вызывается**
   (`apps/settings_center/policies.py:12-13`) — задумывалась как ограничение на
   редактирование `is_staff`/`is_superuser`/групп; сейчас любой superuser-гейт
   покрывает, но функцию надо либо использовать, либо удалить.
7. **`AIManagementMixin` использует `can_manage_inventory` как гейт ИИ-центра**
   (`apps/ai/views.py:390-392`) — смысловая нестыковка; должен быть
   `manage_ai_skills` или отдельная capability.
8. **Django-админка без row-level scoping** — staff с model-permissions видит
   все записи, включая ПДн листа ожидания. Минимум: не выдавать staff праву на
   `WaitingListEntry`; лучше — `get_queryset` в ModelAdmin по scope.
9. **Тестов на изоляцию просмотра `inventory`/`analytics` нет** — при добавлении
   scoping нужны регресс-тесты (для waiting_list добавлены в этом блоке).

## Row-level доступ: нужен ли и как делать

**Вывод: нужен точечно, через расширение существующего selector-паттерна;
per-object ACL (django-guardian) не нужен.**

Обоснование:

- Модель доступа проекта — ролевая и иерархическая (роль × ветка подразделения
  × авторство/назначение). Все реальные требования выражаются фильтром queryset
  от атрибутов пользователя; индивидуальных прав «этому пользователю — эту
  запись» в требованиях нет.
- django-guardian хранит ACL-строку на каждую пару (пользователь/группа,
  объект): вторая база истины, которую надо синхронизировать при смене
  подразделения/ролей, плюс JOIN на каждый список. Для иерархии подразделений
  guardian всё равно не решает задачу «ветка подразделения» — её пришлось бы
  дописывать поверх.
- Проект уже владеет нужным паттерном: `visible_workorders_queryset` (ADR-0023)
  и scope-токены памяти. Осталось распространить его на отстающие модули.

Рекомендуемая реализация (поэтапно):

1. `apps/inventory`: селектор `visible_devices_queryset(user)` (переиспользовать
   `apps/workorders/selectors.py:75-85`), применить в list/detail; тесты
   изоляции по ветке подразделения.
2. `apps/analytics` + дашборд `core`: считать агрегаты от
   `visible_workorders_queryset(user)` — аналитика автоматически сузится до
   scope роли, скрытая инвариантная зависимость исчезнет.
3. `waiting_list` (после закрытия модульного гейта «только врачи»): решить с
   владельцем, нужно ли построчное разделение между врачами (например, по
   отделению или авторству). Пока данных и требований нет — не реализовывать.
4. Колонки канбана: проверять принадлежность `KanbanColumnConfig.board` к
   `visible_boards_queryset(user)`.
5. Админка: `get_queryset`-scoping или отзыв model-permissions на чувствительные
   модели у staff.

Когда guardian всё же станет уместен: если появятся требования «поделиться
конкретной записью с конкретным пользователем» (ad-hoc sharing) — тогда
отдельный ADR.

## Лучшие практики: сверка

- Deny-by-default: выполняется в workorders/memory; после ADR-0034 — и в
  waiting_list. Для новых модулей — правило по умолчанию (селектор обязателен).
- Единый источник истины прав: контракт (`$capabilities`) — теперь и для UI, и
  для superuser; не дублировать списки прав в коде.
- Проверки на сервере, скрытие в UI — вторично: выполняется (ADR-0023),
  закреплено в POLICY_MODEL.md.
- 404 вместо 403 для скрытия существования записи: выполняется в workorders;
  сохранять при расширении селекторов.
- Человекочитаемые названия прав: `$capabilities` + русские имена
  `Meta.permissions` в memory + `GroupProfile`.
