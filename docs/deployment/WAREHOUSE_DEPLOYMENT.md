# Развёртывание раздела «Склад»

## Назначение

Этот документ описывает только техническое включение общего складского контура.
Организационный порядок остановки старой программы и переключения конкретного
учреждения определяется вне репозитория.

## Установка и обновление

После обновления кода и зависимостей выполнить:

```bash
python manage.py bootstrap_runtime
python manage.py migrate
python manage.py validate_architecture_contracts
python manage.py seed_roles
python manage.py check
python manage.py warehouse_acceptance_e2e
```

Для существующей непустой складской базы миграции inline-серий применяются в
два технических шага. Сначала довести схему до обратимой точки и записать
контрольную сверку:

```bash
python manage.py migrate warehouse 0004
python manage.py warehouse_reconcile_inline_series --actor <superuser> --record-checkpoint
```

Только после успешного отчёта применить контрактный шаг и остальные миграции:

```bash
python manage.py migrate
```

`warehouse.0005` повторно сравнивает журнал, строки документов и остатки с
контрольными точками, затем удаляет старую таблицу `StockLot`. Для новой пустой
базы ручная отметка не требуется. После `0005` миграция необратима на уровне
схемы; откат выполняется восстановлением предварительной резервной копии.

`warehouse.settings` зарегистрирован как типизированный документ Центра
настроек. Git-файл задаёт проверенный дефолт, а изменённая рабочая версия
хранится в PostgreSQL; `bootstrap_runtime` не создаёт файловое зеркало. В
приватный `LOCAL_BUSINESS_SETTINGS_DOCUMENT_DB_ALLOWLIST` нужно включить
`warehouse.settings` и пересоздать все Django-процессы. На действующей установке
изменения `role_rules.json` применяются
защищённым preview/apply-процессом Центра настроек; прямое копирование Git-файла
поверх рабочей версии запрещено.

## Зависимости и хранилище

- Основная БД — общая PostgreSQL проекта; отдельный сервис и отдельная БД складу
  не требуются.
- XLSX формируется библиотекой `XlsxWriter`, закреплённой в
  `requirements.txt` и `requirements.lock`.
- Для чтения Access на Windows нужен установленный Microsoft ACE OLE DB.
  Основное приложение от ACE не зависит; он требуется только узлу миграции.
- Landing packages и сопоставления находятся в `data/warehouse/imports/`,
  `.local/` или приватном deployment-репозитории и не коммитятся.

## Проверка после развёртывания

Проверить вход под четырьмя профилями: без складской роли, оператор, контролёр и
администратор склада. Затем создать тестовую серию прямо в черновике прихода в
разрешённом подразделении, провести его и сформировать три отчёта в HTML, CSV и
XLSX.

Согласованность текущей проекции с журналом проверяется без записи:

```bash
python manage.py warehouse_rebuild_balances --actor <superuser> --check
```

Пересборка выполняется только после анализа расхождения и требует того же
явного пользователя-инициатора. Подробные операции и команды legacy-миграции
описаны в `docs/guides/WAREHOUSE_OPERATIONS.md`.

## Откат кода

Перед обновлением применяется стандартная резервная копия общей БД. Миграции
склада меняют только складские таблицы и не изменяют данные других доменов.
Проведённые документы нельзя удалять или редактировать для «отката» операции:
бизнес-ошибка исправляется сторно или корректировкой.
