# ADR-0040: Единый контур администрирования доступа

- Статус: Accepted
- Дата: 2026-08-12
- Связанные решения: ADR-0007, ADR-0023, ADR-0031, ADR-0034, ADR-0035,
  ADR-0038, ADR-0039
- Частично заменяет ADR-0038 в части единственного UI: единственным остаётся
  service layer, а Django Admin получает резервный адаптер к нему.

## Контекст

В проекте уже есть безопасный основной сценарий назначения ролей: серверный
предпросмотр, привязанный к пользователю и текущему состоянию, явное подтверждение
риска, транзакционное применение и `AccessAssignmentAudit`. Редактор контракта ролей
также валидирует изменения, записывает рабочую копию атомарно и защищается от
устаревшей формы.

Однако административный контур не является единым:

- назначение ролей, профиль пользователя, AD-связь, редактор ролей, технические
  группы и журналы разнесены по нескольким экранам;
- Django Admin оставляет стандартные поля групп, прямых Django permissions и
  технических флагов отдельным путём изменения;
- ИИ-инструмент `access.users.update` напрямую изменяет группы пользователя;
- LDAP-синхронизация ролей напрямую изменяет группы и не учитывает объявленный
  выключатель `ACCOUNTS_AD_GROUP_ROLE_SYNC`;
- разные пути показывают технические коды вместо единого предметного языка и не
  дают общего объяснения результата;
- аудит назначения пользователя, изменения контракта и ИИ-действий хранится в
  разных моделях без общей пользовательской проекции.

Из-за этого хороший UX на одном экране не гарантирует, что изменение доступа
действительно прошло через тот же защищённый серверный сценарий.

## Предлагаемое решение

1. Сохранить текущую гибридную модель авторизации:
   - контрактные роли дают понятный базовый набор возможностей;
   - атрибуты и отношения (`department_branch`, авторство, назначение, разрешённые
     доски, scope-токены памяти) ограничивают область;
   - доменные policies/selectors остаются источником решения;
   - отдельный внешний движок политик не вводится.
2. Ввести единое продуктовое окно «Доступ» с постоянным переключателем разрезов:
   - пользователи;
   - роли;
   - доски;
   - разделы сайта;
   - технические группы;
   - группы памяти;
   - журнал после реализации общей read-only проекции.
   Таблица остаётся главным рабочим объектом. Название сущности открывает полный
   инспектор в правой выезжающей панели поверх рабочей области, как на канбан-доске.
   Значение ячейки открывает контекстный редактор в штатной левой панели вместо
   дерева подразделений и ИИ-чата. На узком экране редактор занимает верхний
   полноэкранный слой, а правая панель сохраняет модальную механику.
   Технические источники раскрываются в контексте выбранной сущности, а проверка
   конкретного доступа вызывается только для поддерживаемых доменных сценариев.
3. Сделать доменные сервисы единственными путями изменения доступа:
   - интерактивное назначение ролей и технических флагов использует подписанный
     preview/apply-протокол;
   - изменение роли использует Settings Center contract service;
   - стандартная Django Admin форма не пишет группы, прямые permissions,
     технические флаги и активность напрямую; отдельный резервный маршрут для
     активного superuser вызывает тот же preview/apply-сервис назначения ролей и
     флагов, требует причину и пишет предметный аудит;
   - ИИ-инструменты вызывают те же сервисы либо создают предложение, но не пишут
     группы напрямую;
   - AD-синхронизация работает только при явном включении, изменяет только заранее
     сопоставленные роли через отдельный аудируемый сервис и показывает источник
     назначения.
4. Разделить административные полномочия, которые сейчас объединены в
   `manage_roles`:
   - просмотр итогового доступа;
   - назначение разрешённых актору ролей;
   - изменение определений ролей;
   - управление привилегированным доступом.
   До появления согласованной модели делегированного администрирования изменение
   определения роли и выдача роли выше privilege ceiling актора доступны только
   superuser. Самоназначение контрактной роли запрещено всем, кроме действующего
   superuser: его технический уровень уже выше любой контрактной роли, но операция
   всё равно считается рискованной, требует отдельного подтверждения и аудита.
   Для первого среза privilege ceiling задаётся не сравнением произвольных наборов
   capabilities, а явной политикой назначения в role contract:
   - `$administration.role_assignment_allowlist` отображает роль актора в список
     назначаемых ролей;
   - роли с хотя бы одной effective capability уровня `critical` отсутствуют в
     allowlist и назначаются только superuser;
   - любое интерактивное назначение роли самому себе запрещено для non-superuser;
   - активный superuser может назначить себе любую существующую контрактную роль
     через подписанный preview/apply; технические группы, прямые permissions,
     `is_active` и собственный `is_superuser` этим исключением не изменяются;
   - superuser может назначать любую существующую роль другому пользователю;
   - определения ролей меняет активный superuser либо участник ролей,
     перечисленных в $administration.role_definition_editor_roles;
     is_staff сохраняет только вход в Django Admin и не даёт продуктовой
     власти;
   - delegated editor не меняет определение роли, которой сам обладает;
     normal/elevated-поля чужой роли доступны через preview/apply, а critical
     capabilities можно только монотонно сужать с подтверждением риска;
     critical expansion/mixed change, создание роли и полный raw apply остаются
     резервным путём активного superuser.
   Конкретный allowlist утверждается владельцем вместе с переводом ADR в Accepted.
5. Не создавать вторую базу истины для аудита. Построить общую read-only проекцию
   над `AccessAssignmentAudit`, `SettingsChange`, `AgentActionLog` и будущими
   записями внешней синхронизации. Новая каноническая audit-модель допустима только
   после отдельного обоснования.
6. Усилить путь записи контракта роли:
   - валидатор проверяет тип каждого значения и запрещает неизвестные/неописанные
     capabilities;
   - проверка полномочий выполняется самим service layer;
   - конкурентная запись защищается межпроцессным compare-and-swap/lock;
   - запись файла и аудита оформляется как восстанавливаемый staged protocol
     (`pending → atomic write → applied`, с reconciliation/compensation), поскольку
     файловую замену и транзакцию БД нельзя объединить обычным `transaction.atomic`.
   Реализация использует единый постоянный lock-файл под `data/contracts`,
   обязательный CAS по версии формы, долговечную запись `PENDING` до `os.replace`,
   сверку фактического хеша и состояния `APPLIED/FAILED/INCONSISTENT`. Команда
   reconciliation не переписывает файл: она только завершает однозначно
   распознаваемый переход. Восстановление версии является новым авторизованным
   и аудируемым изменением, а не скрытой компенсацией.
7. Зафиксировать владельцев модели и путей записи:
   - `apps.accounts` владеет схемой и композицией междоменного role/capability
     каталога, политикой назначения ролей, назначениями субъектам и effective access
     read model;
   - доменные приложения владеют смыслом и серверной проверкой своих capabilities,
     resource scopes и explain-адаптерами;
   - `apps.core` предоставляет только общий contract store/atomic transport и не
     знает бизнес-моделей;
   - `apps.settings_center` предоставляет UI и общий протокол
     preview/write/audit, но не определяет бизнес-разрешения;
   - `apps.workorders` владеет изменением `Board.allowed_groups` через доменный
     сервис и отдельный `BoardAccessAudit`. Эта модель является предметным
     событием ресурсного ACL доски, а не вторым общим журналом: `SettingsChange`
     не описывает M2M-доступ к конкретному объекту, а `AccessAssignmentAudit`
     владеет назначениями субъектам. Общая будущая страница журнала остаётся
   read-only проекцией над этими источниками;
   - создание, изменение, отключение пользователя и привязка AD principal
     используют тот же общий lock доступа, затем одну транзакцию БД. UI передаёт
     callback аудита, поэтому предметное изменение не может сохраниться без
     соответствующего `SettingsChange`; исходные PII не сохраняются, только
     версионированные HMAC-отпечатки;
   - стандартная форма User в Django Admin является read-only для профиля,
     пароля и доступа; резервная запись остаётся отдельным маршрутом ролей и
     технических флагов через общий preview/apply-сервис;
   - LDAP profile sync использует тот же lock/audit. В `manual` режиме он не
     перезаписывает ручную AD identity; `automatic` является явным режимом
     владельца principal-связи и также использует транзакцию и аудит;
   - технические группы памяти изменяются superuser из контекстного редактора
     карточки сотрудника через preview/apply-сервис `apps.memory` с обязательной
     причиной и доменным аудитом; системные команды используются только для
     seed/bootstrap, а общий разрез групп памяти остаётся read-only без выбранного
     пользователя;
   - прямые Django permissions считаются системным исключением и не имеют ручного
     UI до появления отдельного доменного требования.
8. Показывать сложность постепенно:
   - основной режим использует бизнес-названия, область и результат;
   - технические коды, Django permissions, source tokens и сырые контракты находятся
     в раскрываемом экспертном представлении;
   - матрица не является единственным способом редактирования.
9. Сначала реализовать объяснение существующей модели. Временный/JIT-доступ,
   согласования, разделение обязанностей и регулярная сертификация не входят в
   первый срез и требуют подтверждённой бизнес-потребности, модели данных и
   отдельного обновления ADR.

## Уточнение информационной архитектуры от 2026-08-13

Первоначальная реализация безопасно объединила пути записи, но сохранила отдельные
страницы пользователей, ролей, досок и групп памяти. Это не выполнило цель единой
ментальной модели: администратор терял выбранный объект и контекст при переходах.

Принята следующая master-detail модель:

- канонический URL — `/settings/access/`; состояние разреза, выбранного объекта и
  поля допускается восстанавливать из проверенных параметров URL;
- старые URL остаются совместимыми standalone-входами и ссылками «открыть в
  отдельном окне», но основная навигация не уводит из workspace;
- «раздел сайта» является read-only проекцией `$capabilities.section` и не создаёт
  новую модель или второй источник истины;
- общие технические группы показываются и объясняются, но не получают
  универсального редактора без доменного владельца; группы памяти редактируются
  только через сервис `apps.memory`;
- локальная AD identity и локальный профиль могут редактироваться существующими
  сервисами, но интерфейс не утверждает, что изменяет объект в Active Directory:
  AD write API в текущей архитектуре отсутствует;
- редактор состава роли использует предметное пакетное preview/apply поверх тех же
  инвариантов назначения пользователю и создаёт отдельный `AccessAssignmentAudit`
  для каждого реально изменённого пользователя; прямой `Group.user_set.set()`
  запрещён;

## Уточнение карточки и двух разрезов доступа от 2026-08-13

1. Карточка пользователя в правой панели является одной черновой формой. Переход
   между значениями меняет только видимую группу полей и не отправляет запрос;
   введённые значения сохраняются до закрытия панели. Изменения проходят один
   общий preview и одно подтверждённое сохранение.
2. Междоменное сохранение не заменяет предметные сервисы. Прикладной координатор
   держит общий lock доступа и одну транзакцию БД, а доменные profile, AD, role и
   memory preview/apply повторно проверяют подписанное исходное состояние и пишут
   свои журналы. Частичное применение запрещено.
3. Небольшие однострочные поля профиля и статус допускается редактировать на месте
   в левой колонке карточки. Множественный выбор и AD-связь открываются в правой
   колонке. Разделы сайта остаются вычисляемым read-only результатом ролей.
4. Должностная функция и раздел сайта являются разными представлениями одной
   политики, но не двумя базами настроек:
   - роль описывает устойчивую функцию пользователя;
   - capability описывает действие над ресурсом и область действия;
   - раздел сайта является группировкой capabilities и виден, если эффективная
     роль даёт `section.view` либо право чтения основного ресурса раздела;
   - подразделение, авторство и назначение ограничивают scope и не порождают роли
     вида `manager_department_42`;
   - отдельная матрица `роль → раздел` не создаётся.
   Конкретное введение явного `section.view`, временных назначений и разделения
   обязанностей требует отдельного согласования; текущий пакет меняет только
   вычисляемую UI-проекцию и не меняет действующие разрешения.
- Серверный URL полностью восстанавливает выбранный разрез, объект, поле и панель;
  обычная навигация работает без JavaScript. Небольшой JavaScript управляет только
  доступностью модального слоя, фокусом и предупреждением о несохранённых данных.
  Права, stale-check, подтверждение риска, блокировка и аудит остаются серверными.

На широком экране центральная таблица сохраняет размер: редактор значения занимает
штатную левую панель, а правый инспектор накладывается поверх рабочей области и не
перестраивает таблицу. На планшете и телефоне редактор становится полноэкранным;
`Escape`/«Назад» закрывает верхний слой с возвратом фокуса. Полное
значение обрезанной ячейки доступно и при наведении, и с клавиатуры; статус всегда
обозначается не только цветом.

Открытие, закрытие, preview и применение в боковых панелях используют частичный
серверный HTML через HTMX без перезагрузки документа. Обычные ссылки и формы
остаются резервным потоком без JavaScript. URL по-прежнему хранит состояние панели;
история браузера сохраняет живой DOM встроенного ИИ-чата, а успешное применение
одним ответом обновляет редактор и табличную проекцию.

## Инварианты

- UI-скрытие не заменяет серверную проверку.
- Новое право не возникает без записи в каноническом источнике и аудита.
- Техническая группа не называется ролью доступа, если ей не соответствует роль
  контракта.
- Изменение одной роли показывает затронутых сотрудников и серверный diff до
  применения.
- Неполное вычисление итогового доступа обозначается как неполное, а не как
  окончательное разрешение или запрет.
- Автоматический источник не может молча перезаписать локальное назначение: область
  его владения и правило конфликта должны быть явными.
- Non-superuser не может выдать себе роль либо выдать другому субъекту роль выше
  разрешённого ему privilege ceiling и не может единолично изменить правило,
  которое определяет его собственный ceiling.
- Self-assignment superuser всегда имеет отдельный risk marker и аудит с совпадающими
  actor/target; снятие собственного `is_superuser` и самоотключение запрещены.
- Django Admin является резервом при недоступности продуктового экрана, но не
  обходит `apps.accounts`, contract store, БД или аудит и завершается fail-closed
  при их отказе.

## Рассмотренные альтернативы

### Оставить отдельные экраны и улучшить только оформление

Отклонено: это не устраняет параллельные пути записи, различную терминологию и
разорванную историю.

### Использовать Django Admin как основной интерфейс

Отклонено: стандартные формы не реализуют предметный preview, объяснение области,
риск-метаданные контракта и единый аудит.

### Полностью запретить запись доступа через Django Admin

Отклонено владельцем: нужен резерв при отказе продуктовой страницы. Резервный
маршрут не возвращает стандартную ORM-запись, а использует тот же доменный сервис,
preview, подтверждение и аудит. Прямые permissions и технические группы в этот
маршрут не входят.

### Ввести OPA, Cedar, OpenFGA или per-object ACL

Отклонено для текущего этапа: существующие требования выражаются контрактными
ролями, атрибутами пользователя и доменными selector-политиками. Новый движок не
решает сам по себе проблему административного UX и добавляет второй язык политик.

### Сразу реализовать JIT, согласования и access review

Отложено: это зрелые практики для привилегированного доступа, но сейчас нет
согласованных владельцев, сроков, маршрутов одобрения и эксплуатационной модели.

## Последствия

- Первым этапом закрываются прямые write-paths и создаётся резервный Admin-адаптер;
  только затем
  единый раздел может считаться доверенным административным интерфейсом.
- Старые URL можно сохранить как redirects для закладок, но навигация ведёт в один
  раздел.
- Понадобятся изменения `apps.accounts`, `apps.settings_center`, `apps.ai`, LDAP,
  Django Admin, шаблонов и тестов; изменение provenance внешних назначений может
  потребовать миграции.
- Документация эксплуатации AD и ИИ-инструментов обновляется вместе с кодом.

## Принятые границы реализации

Владелец подтвердил начало реализации со следующими границами:

1. Django Admin остаётся резервным write-интерфейсом для контрактных ролей и
   технических флагов, но использует отдельный superuser-only адаптер к общему
   preview/apply-сервису. Стандартные access-поля не пишут ORM напрямую.
2. AD является авторитетным только для явно сопоставленных ролей; локальное
   редактирование этих ролей либо запрещается, либо явно предупреждает о следующей
   синхронизации.
3. В первый продуктовый срез не входят JIT, согласования и регулярная сертификация.
4. `manage_roles` разделяется на назначение, изменение определений и управление
   привилегированными назначениями; до этого критичные операции ограничиваются
   superuser.
5. Утверждается конкретный `$administration.role_assignment_allowlist`; рекомендуемый
   старт — менеджер назначает только `customer` и `technician`, а роли с critical
   capabilities назначает superuser.
6. Технические группы памяти получают отдельный superuser-only сервис `apps.memory`
   и экспертный экран; прямые Django permissions не получают ручного редактора;
   `Board.allowed_groups` переводится на сервис `apps.workorders`.
7. Активный superuser может назначать себе существующие контрактные роли через
   рискованный preview/apply-сценарий. Для всех остальных self-assignment запрещён.

## Статус реализации на 2026-08-12

Первый безопасный срез реализован:

- стандартные access-поля User, permissions Group и `Board.allowed_groups` закрыты
  от прямой записи в Django Admin; резервный superuser-маршрут назначения использует
  общий preview/apply и обязательную причину;
- assignment service проверяет актуального активного actor, allowlist, self-assignment,
  хеш контракта, источник, одноразовость preview, последнего superuser и пишет
  расширенный `AccessAssignmentAudit`;
- общий AI user-update не меняет группы, подписывает исходное состояние actor и
  target и одной транзакцией применяет активность, подразделение и аудит;
  произвольный `confirmed_token` не подтверждает новый payload;
- долговечный `AgentActionLog` рекурсивно очищает identity-поля результатов
  (`username`, email, автор, исполнитель, AD principal), сохраняя технические id,
  статусы и структуру ответа;
- LDAP role sync учитывает выключатель и до появления системного actor работает
  fail-closed; отключённая локальная учётная запись не проходит LDAP login/session
  restore;
- редактор определений ролей использует единый predicate допуска: активный
  superuser или участник ролей из
  $administration.role_definition_editor_roles; отсутствующее поле временно
  означает admin, malformed/unknown value закрывает доступ;
  is_staff сохраняет только вход в Django Admin, а обычный manage_roles без
  editor-role получает только read-only карточку;
  role contract строго проверяет типы, известные capabilities и allowlist;
- продуктовая навигация сведена к пункту «Доступ», список получил серверный поиск,
  компактные фильтры и пять столбцов, технические источники скрыты в экспертном
  раскрытии, после создания сразу открывается назначение роли.

Следующий срез также реализован:

- рабочие контракты записываются через восстанавливаемый staged-протокол с
  межпроцессной блокировкой Linux/Windows, обязательным CAS, командой сверки и
  авторизованным rollback; снимки скрыты от Django Admin, сам журнал неизменяем;
- изменения контракта роли и членства в контрактных ролях используют одну
  межпроцессную блокировку; состав участников и влияние повторно проверяются
  непосредственно перед записью;
- подтверждение ИИ сначала атомарно занимает `PendingAction`, затем выполняет
  инструмент вне транзакции и отдельно фиксирует итог; неопределённый итог
  переводится в `reconciliation_required`; ручная команда сохраняет наблюдение,
  оператора и причину, но не закрывает неопределённый статус без fencing-протокола;
- `Board.allowed_groups` изменяется только доменным подписанным preview/apply,
  имеет `BoardAccessAudit`, а резервный Django Admin вызывает тот же сервис и
  требует причину; неизвестные и технические группы отклоняются;
- добавлены компактный каталог ролей и точечный редактор одной роли с серверным
  diff и оценкой числа затронутых сотрудников;
- технические группы памяти изменяются отдельным superuser-only
  preview/apply-сервисом `apps.memory` с обязательной причиной и предметным
  `MemoryGroupMembershipAudit`;
- демонстрационные назначения ролей используют отдельный аудируемый
  `system_bootstrap`, не удаляют технические группы скрытым `groups.set()`;
  Board bootstrap допускается для доски, созданной текущим запуском, либо для
  заранее созданных миграциями канонических досок `main`/`backlog`, но только
  при пустом ACL и отсутствии истории доступа; он требует причину, использует
  общий lock доступа и создаёт не более одной bootstrap-записи аудита;
- AD identity в Django Admin доступна только для чтения, а удаление пользователя
  заменено управляемым отключением.

Поправка 2026-08-17: редактор определений ролей делегирован без расширения
manage_roles. Один predicate допускает только активную аутентифицированную
учётную запись с is_superuser или членством в роли из
$administration.role_definition_editor_roles. Он используется в standalone и
workspace-маршрутах, правом инспекторе, core contract service и навигации.
Delegated editor не меняет собственную роль; critical право чужой роли можно

Полный apply для role_rules и critical expansion/mixed change остаются

Остаются: общая read-only проекция журнала, расширенные explain-адаптеры и

## Уточнение полноты ролевой модели и сервисных границ от 2026-08-17

Повторный сквозной аудит выявил класс ошибок, который не закрывается единым
административным интерфейсом: право может отображаться в роли, но фактическая
операция продолжает зависеть от имени роли, `is_staff`, авторства, несвязанной
capability или предварительной проверки только во view. Поэтому принимаются
следующие дополнительные правила.

1. Любая пользовательская операция записи имеет actor-aware доменную команду.
   Команда после блокировки объекта повторно читает активного актора, проверяет
   capability, область ресурса и состояние объекта. View, HTMX и AI являются
   адаптерами и не считаются границей безопасности.
2. Политики разделяются на четыре непересекающихся класса: должностные роли,
   ACL конкретного ресурса, технические группы/операторские команды и резервный
   superuser/Django Admin. Техническая или резервная принадлежность не выдаёт
   бизнес-capability неявно.
3. `is_staff` означает только доступ к Django Admin и не даёт управление
   продуктовыми контрактами. Определения ролей меняют active superuser и явно
   уполномоченная контрактная роль. Для non-superuser запрещено менять собственную
   эффективную роль, поднимать собственный privilege ceiling и изменять critical
   определения вне разрешённых целей. Предыдущее допущение любого `is_staff` к
   продуктовому редактору ролей этим уточнением заменяется.
4. Лист ожидания получает отдельные области видимости, редактирования и переходов,
   а также наборы исходных и целевых статусов. Авторство действует только внутри
   явно настроенного scope. Граф допустимых переходов проверяется независимо от
   ролевого подмножества.
5. Чтение данных также проходит scoped selectors. Главная страница, инвентарь,
   аналитика, AI-операции, память и файловая организация не могут расширять
   видимость по сравнению с канонической доменной политикой.
6. Формат capability metadata расширяется ссылкой на источник допустимых значений.
   Один renderer поддерживает scope и targets разных доменов без предположения,
   что любой список targets является статусами заявок. Неизвестный источник или
   отсутствующее новое право обрабатываются fail-closed.
7. Секретные настройки никогда не передаются в HTTP template context. Для
   `sensitivity=secret` UI получает только состояние «настроено/не настроено» и
   маску, независимо от имени env-переменной или ключа словаря.
8. Физическое удаление предметных записей через AI запрещено, если домен не имеет
   отдельной capability, статусов удаления и сохраняемого аудита. Для заявки
   пользовательским действием является отмена, а не hard delete.

Совместимость обеспечивается явной миграцией Git-default и рабочей копии
`role_rules`: старые широкие флаги раскладываются на новые scopes только для тех
ролей, которым они уже давали эквивалентный доступ. Новое чувствительное право не
выдаётся по умолчанию. Рабочая копия изменяется штатным атомарным Settings Center
protocol с preview, CAS и аудитом; прямое копирование default поверх runtime
запрещено.

## Продуктовый Центр настроек (уточнение 17b-A)

Центр настроек использует отдельную критическую capability `manage_settings`.
В дефолтном контракте она включена только для роли `admin`; superuser имеет
автоматический резервный доступ. `is_staff` сохраняет исключительно вход в
Django Admin и не выдаёт продуктовую власть. Дескрипторы используют закрытый
набор `manage_settings`/`manage_users`; неизвестное `required_permission`
отклоняется. Preview, apply и прямой сервисный вызов проверяют одну и ту же
свежую матрицу активного актора.

Настройки окружения создают только заявку: сервис повторно проверяет
`manage_settings` непосредственно перед записью заявки. Редактирование
рабочих навыков ИИ использует общий lock, повторную проверку
`manage_ai_skills` и уникальный временный файл в том же каталоге перед
`os.replace`.

ИИ-центр использует собственную capability `manage_ai_skills`; право
`manage_inventory` больше не является косвенным пропуском в этот раздел.

## Ревью памяти и файловая организация (уточнение 17b-B/17b-C)

Техническая группа памяти определяет допустимый тип операторского действия,
продуктовая capability — право менять память организации, а ACL/адаптер
источника — доступ к конкретному ресурсу. Действие разрешено только при
одновременном выполнении всех трёх условий. `is_staff` не участвует в этой
матрице. Пространства токенов разделены: `role:<code>` относится только к
контрактным ролям, `group:<name>` — к техническим и ACL-группам.

Физическое упорядочивание файла использует единый порядок блокировок
`actor → source → proposal → files → jobs → placements`. Решение сохраняет
неизменяемый снимок состава файлов, версий и хешей; worker сверяет его перед
созданием заданий и файловым вводом-выводом. После любого неоднозначного сбоя
задача переходит в `NEEDS_REVIEW`, а не повторяет физическую операцию
автоматически. Операционные модели FileHub доступны в Django Admin только для
чтения; резервное изменение справочных моделей оставлено активному
superuser.

Статус `MemorySource` является общей границей остановки для ingestion,
индексации и FileHub. Все штатные переходы статуса, включая резервный Django
Admin, сериализуются тем же межпроцессным lock, что и файловые операции;
автоматический envelope не включает источник повторно. Длительный файловый
ввод-вывод не удерживает транзакцию БД. Для необратимого purge сначала
фиксируется committed-намерение `PURGE_IO`; поэтому сбой после unlink, но до
обновления БД завершается детерминированным recovery, а не повторным удалением
или молчаливой потерей состояния.
