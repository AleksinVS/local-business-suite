# LBS Factory v3.4 — Content Privacy Pipeline

**Статус:** проект исправления подтверждённых архитектурных разрывов, **не реализованный код**.  
**Дата:** 2026-10-21.  
**Основа проверки:** репозиторий `AleksinVS/local-business-suite`, `main` перед началом изменений документации: `41c5450a53fdd0b8598a0c2ab8cdceaa3ed6535e`.  
**Цель:** единое предсказуемое представление контента для индексации, LLM-Wiki, агентного контекста и внешних моделей без собственного DLP-сервиса, нового workflow и обязательного review каждого знания.

## 1. Проблема: один источник, разные результаты обработки

Существующая реализация содержит частично работающие распознавание PII и защиту от секретов. Но **проверка доступа к исходному объекту и безопасная форма возвращаемого текста не эквивалентны**.

| Код | Проверенный путь | Наблюдаемое расхождение |
|---|---|---|
| `apps/memory/document_ingestion.py:inspect_source_object_for_ingestion()` | extract → `scan_for_secrets()` → `detect_pii()` → `"text": extracted.text` | После детекции тело **не маскируется**, при `pii_guarded` формируется предупреждение; `pii_strict` не блокирует найденные PII |
| `apps/memory/document_ingestion.py:_ingest_source_object_text_locked()` | `index_body = safe_text or ""` → повторная детекция → `MemoryIndexRecord` | Имя `safe_text` вводит в заблуждение: реально может быть raw; `block` не применяется. В индекс добавляются необработанные `file_name`, `relative_path`, `object_id` |
| `apps/memory/services.py:_prepare_source_text_for_index()` | SourceAdapter → secret scan → PII → `redact_text()` | Body обрабатывается правильнее, но `_upsert_projection_indexes()` дополнительно индексирует `envelope.title` и `object_id` без общего преобразования |
| `apps/memory/services.py:render_source_object_text()` | `adapter_check` → `adapter.can_access()` → `get_object()` → `render_envelope(...).text` | Свежее содержимое возвращается **мимо ранее подготовленной safe-проекции**. `retrieval.read_search_document_text()` использует этот маршрут для контекста/выдачи |
| `apps/memory/retrieval.py` | Search candidates и `source_data` fallback | Названия, URI, заголовки, цитаты и индексы требуют отдельной проверки даже при безопасном body; доступ пользователя к источнику не означает разрешение публикации raw в AI |
| `apps/memory/chat_memory.py:sanitize_memory_text()` | chat → найденные секреты/secret handles → Wiki Git | Проверяется известное секретное содержимое, но **не существует универсального PII-преобразования** перед первым Git-коммитом |
| `contracts/ai/memory_sources.json` | `workorders` и `waiting_list` явно указывают `pii_off` | В Waiting List псевдоним пациента не устраняет PII в свободном `comment`; в WorkOrders необработанными могут быть description/comment. Механизм не должен считать это «доказанно чистым» текстом |

**Текущие тесты:** `test_ingest_source_objects_blocks_secret_and_audits_pii` проверяет предупреждение PII и присутствие документа в поиске, но не отсутствие исходного email в содержимом индекса. Тесты `deidentification.py` проверяют маскирование отдельно, но этого недостаточно для проверки всех реальных путей.

Это **кодовое подтверждение риска**, не утверждение об имевшей место утечке: фактические настройки, эксплуатационные индексы и история ещё требуют проверки.

### 1.1. Особая оговорка про PII

Существующий `deidentification.py` использует регулярные выражения и эвристики. `redact_text()` **не гарантирует полной анонимности**, особенно для свободных описаний медицинских случаев, редких комбинаций признаков и косвенных идентификаторов. HMAC-псевдонимизация сохраняет связь между записями и не является полноценной анонимизацией.

Обязательная первая цель: **одинаково и проверяемо применять выбранные политики** ко всем безопасным выходам. Более точные NER/DLP и юридические профили — отдельный поэтапный выбор по риску и качеству.

## 2. Решение L0: небольшая общая библиотека, не новая платформа

Используем существующие `apps.memory.security`, `apps.memory.deidentification`, `apps.core.source_adapters` и конфигурацию источников. Добавляем один общий метод формирования **SafeProjection** для конкретного назначения (**destination**), вызываемый всеми sinks.

```text
  Файлы / Source Adapters / Telegram / чаты / Bitrix24
                          |
                 исходный объект (raw)
                          |
         source ACL + актуальная privacy-политика
                          |
           prepare_content(raw, destination)
             ├── CredentialGuard / secret gate
             ├── PII detect → mask или strict-block
             ├── безопасные body/title/display_ref
             ├── allowlist indexable metadata
             └── source_hash + policy_id/version
                          |
                    SafeProjection
                 /        |         \
         local_index    wiki_git    agent_context / external_llm
                          |
        оригинал остаётся у владельца данных; `original_read`
        в предметном UI — отдельная авторизованная операция
```

Логический контракт (можно адаптировать существующий DTO, **новой DB-модели не требуется**):

```python
@dataclass(frozen=True)
class SafeProjection:
    body: str
    title: str
    display_ref: str
    index_fields: tuple[str, ...]
    metadata: Mapping[str, Any]       # allowlist, без raw payload
    source_hash: str
    policy_id: str
    policy_version: str
    destination: str
    blocked: bool
    reason_code: str = ""

def prepare_content(source_record, *, privacy_profile, destination) -> SafeProjection: ...
```

Фиксируем узкие назначения: `local_index`, `wiki_git`, `agent_context`, `external_llm`, `external_export`. Не строим универсальный policy DSL на десятках осей. Для **одного source_hash + policy_version + destination** ожидается одинаковый безопасный результат независимо от входного транспорта.

**Обязательные правила:**
1. Финальная запись в FTS/vector/индексируемую metadata и передача AI принимают `SafeProjection`, а не сырой `str` с обманчивым именем `safe_text`.
2. `title`, `file_name`, `relative_path`, `object_id`, `source_uri`, свободные поля payload, preview, citation и логические имена документов рассматриваются как потенциальный PII. Нельзя автоматически включать их в поисковое тело. Технический ID при необходимости хранится отдельно как **неполнотекстовый** ключ и не раскрывается в ответе.
3. Применять политику **до** индексирования, эмбеддинга, кеширования для выдачи и **до первого Git-коммита**. В логах — только безопасные ID, решение, версию и агрегированные счётчики, не исходные значения.
4. Авторизация доступа к объекту (в том числе `adapter_check`) и privacy transform **не заменяют** друг друга.
5. При ошибке преобразования, отсутствии обязательной версии политики, изменении raw-объекта или отказе обязательного детектора **не подставлять исходные заголовки или raw-текст**. Закрыть соответствующую выдачу либо подготовить заново по актуальной политике.
6. Источник/индекс несёт `source_hash` и `policy_version`. Устаревшая безопасная проекция не должна молча считаться актуальной после смены политики; нужен reprepare/reindex или контролируемый отказ для соответствующего назначения.
7. Ошибка одного sensitive объекта **не должна блокировать сбор остальных безопасных знаний** и весь ingestion job.

## 3. Профили: сохранить существующую простоту

| Профиль | Значение в безопасном интерфейсе |
|---|---|
| `pii_off` | Отключает PII-маскирование для **явно разрешённого источника и назначения**; не свидетельствует об отсутствии PII и **не разрешает автоматически external_llm** |
| `pii_guarded` | Известные детектору прямые идентификаторы маскируются в body, title и индексируемых/видимых метаданных до использования |
| `pii_strict` | Обнаружены запрещённые PII → конкретный объект блокируется **и при файле, и при адаптере, и при повторном чтении**, без старого опасного результата |

`CredentialGuard` остаётся отдельно включённым критическим гейтом для секретов, перед записью безопасной проекции. Не превращать секреты в обычные Wiki-факты.

Сейчас `resolve_privacy_profile()` использует guarded по умолчанию для ряда внешних источников, но для многих внутренних выбирает `pii_off`. **Не переключать действующие внутренние источники массово**: сначала инвентаризация и явный договор с владельцем домена. Для нового неизвестного источника документов рекомендован `pii_guarded` или блокировка, если риск выше возможностей regex. Для медицинских свободных текстов, где недостаточно простого маскирования, может быть проще **отдельный защищённый корпус + локальный доступ + запрет cloud egress**, чем неограниченный NER.

## 4. `adapter_check`: правильная граница

Действующий `render_source_object_text()` проверяет активного пользователя, scope и `adapter.can_access()`. **Не отменять эти проверки.** Но после `adapter.render_envelope(source_record)` возможны только:

- вызов `prepare_content(envelope, destination="agent_context")` и возврат safe-проекции;
- использование ранее сохранённой safe-проекции **после** проверки соответствия текущему `source_hash` и `policy_version`;
- контролируемый отказ/задание на пересчёт, если безопасное представление недоступно.

**Запрещено:** fallback к `envelope.text`, `file_name`, `relative_path` или `object_uri` при отказе политики.

`original_read` — иной API/действие системы-владельца, требующее актуальных полномочий пользователя и исходной бизнес-цели. Например, врач вправе работать с ФИО пациента в своём медицинском интерфейсе. Это не основание отдавать те же идентификаторы в общий RAG/облачную модель.

## 5. LLM-Wiki без review: безопасный Git writer

Выполняем принципы v3.4:
1. Интервьюер или агент формирует короткую тематическую рабочую запись.
2. **Перед первым сохранением в Markdown/Git** writer применяет `prepare_content(..., destination="wiki_git")`, включая title/metadata/источник.
3. Безопасная `working` страница сохраняется **сразу**. `needs_confirmation` лишь необязательная отметка о достоверности, **не privacy-очередь**.
4. Если конкретный фрагмент опасен, он не попадает в Git; сохранение безопасных других фрагментов продолжается. Объяснение проблемы не включает PII в логах. Raw интервью/документ остаётся в контролируемой системе-источнике или закрытом staging.
5. Поисковый индекс строится по уже подготовленной канонической странице. Сбой индексатора не отменяет успешного Git save; повторная индексная работа не меняет текст канона.

Отдельно проверять каналы Web/Telegram/Bitrix24 и выбор cloud/on-prem модели: локальное разрешение читать оригинал **не означает** разрешения внешнего egress. Для внешнего LLM может потребоваться более строгая политика или полный запрет передачи.

## 6. Первый запуск без миграции продуктивных знаний

**У системы знаний LBS пока нет внедрений.** Поэтому обязательного переноса существующей корпоративной Wiki, очистки продуктивной Git-истории и миграции прежних полнотекстовых/векторных индексов **не требуется**. Правильные политики, OKF v0.2 и безопасные индексы следует реализовать **до первого запуска**, обновив тесты и фикстуры. Исправление текущего кода не требует сохранения несуществующей продуктивной истории.

Перед тестовым запуском нужно:
1. Проверить отсутствие фактически используемого внешними пользователями корпуса Wiki/source_data и не делать предположений только по настройкам по умолчанию.
2. Включить единый `prepare_content` для файлов, адаптеров, чатов, записи Wiki и AI egress; запретить небезопасный fallback.
3. Проверить все пути на **синтетических** PII и секретах, затем создать заново тестовые поисковые проекции. Содержимое текущего dev/test хранилища можно сбросить с учётом обычных правил работы с репозиторием и тестовыми данными.
4. Перед первым корпоративным пилотом подтвердить отсутствие небезопасных активных индексов и доступность backup/restore.

**Если позднее обнаружится действующая инсталляция с реальными индексами**, тогда нужен отдельный условный путь: инвентаризация → ограничение выдачи → резервная копия → безопасная переиндексация по источникам → проверка выдачи → очистка по retention. Он не является обязательной работой для нынешнего первого внедрения. Схемные миграции Django при изменении моделей не равны миграции содержимого Wiki.

**Важное исключение:** ошибка отдельного документа не должна блокировать индексацию остальных разрешённых документов или обычное Discovery.

## 9. Совместимость с остальной архитектурой

- **Модульность сохраняется**: единая *библиотечная* политика используется всеми подключаемыми источниками, но не становится централизованным runtime-монолитом или обязательным отдельным сервисом.
- **LLM-Wiki:** `working` записывается сразу после safety-gate; `Knowledge Confirmation Register` касается достоверности знаний, не privacy-block.
- **LBS Access/OpenFGA:** права на исходник и его безопасная форма различаются; OpenFGA **не выполняет** обезличивание.
- **1С/Битрикс24/Telegram:** внешний источник сохраняет оригиналы и свои права; LBS готовит собственное разрешённое представление по destination.
- **AgentTask/A2A/MCP:** передавать safe content/artifact refs по конкретному получателю; не доверять raw payload или текстовому заявлению агента о правах.
- **Progressive Complexity:** сложные NER, OCR, DLP, централизованные политики и privacy-worker — только при подтверждённом риске/улучшении качества; базовая защита остаётся обязательной.
- **Устойчивость:** отказ отдельного safety-gate не останавливает весь ingestion или опрос, но и не разрешает сырой fallback.

Черновик `docs/adr/ADR-0012-data-anonymization-and-privacy-pipeline.md` описывает значительно более широкий контур; для этого исправления предлагается **узкий ADR-F08** без автоматического внедрения большой системы из черновика.

## 10. Подключаемый CROW — потребитель SafeProjection, не параллельный pipeline

Первоначальный CROW работает практически без изменений, но **не получает raw напрямую из файлов/адаптеров**. `LbsCrowAdapter` перед вызовом upstream проверяет ACL источника и `prepare_content(source, destination)` из этого документа. Нельзя ограничиться `wiki_git`, если модель написания/классификатор расположены во внешнем облаке: допустимость `external_llm` проверяется отдельно, а передаваемый CROW текст должен удовлетворять обоим назначениям. При конфликте — локальная модель, более строгий общий результат или отказ с понятной ошибкой; никакого fallback к оригиналу. Поля `title`, `origin.link`, `source_ref` и выдержки индекса также могут раскрывать сведения, поэтому нормализуются/проверяются отдельно.

CROW `raw` хранит только подготовленное представление, физически исключено из Git и имеет отдельную политику доступа и резервирования. Смена `policy_version` требует новой обработанной версии и контролируемой переиндексации; `Origin.version` формируется с учётом ревизии преобразования, чтобы native CROW не вернул ложное `unchanged`. Корпус CROW на первом этапе — однородный по ACL, иначе его classifier может увидеть чужие заголовки.

Это **не новая библиотека очистки**: решение CROW использует тот же `SafeProjection`. См. [план CROW/OKF](11_CROW_OKF_INTEGRATION.md), [инженерные пакеты](12_CROW_IMPLEMENTATION_PLAN.md) и [ADR-0051](../../adr/ADR-0051-crow-pluggable-okf-knowledge-provider.md).
