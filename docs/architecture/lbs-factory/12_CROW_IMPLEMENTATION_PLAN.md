# LBS Factory v3.4 — рабочий план интеграции CROW/OKF

**Статус:** **Accepted — согласованный план реализации на основе ADR-0051; исполняемый код по плану ещё не изменён.**
**Основа:** [11_CROW_OKF_INTEGRATION.md](11_CROW_OKF_INTEGRATION.md), [ADR-0051](../../adr/ADR-0051-crow-pluggable-okf-knowledge-provider.md), [Content Privacy Pipeline](10_CONTENT_PRIVACY_PIPELINE.md). Upstream `crow-hq/llm-wiki-v2`, зафиксированный commit `d1e03f4b71cd54b4bd6fad062ca5e488401b95a6`.
**Цель:** рабочий CROW в отдельном OKF v0.2 пространстве **без переписывания алгоритмов** и без замены `MemorySourceObject`. Приоритет L0: **CROW — единый механизм отбора знаний**, LBS Access — независимое двухуровневое ограничение (пространства, затем заметки) с **предфильтрацией до CROW `select`**. Минимум два логических пространства доступны сразу, дополнительные физические CROW bundles используются для разных write-ACL. Подключение Source API *внутри* CROW — отдельная возможная задача после пилота. **Продуктивной Wiki пока нет, миграция пользовательских знаний не нужна.**

**Открытый долг вне объёма текущих пакетов:** [долг по ПДн в знаниях и Git](../../planning/active/knowledge-personal-data-git-policy-debt.md). Обязательная тотальная очистка ПДн не входит автоматически в CROW-01; до пилота с реальными ПДн требуется отдельно определить допустимое размещение/передачу.

## 1. Конечный результат первой очереди

Один текущий Django runtime LBS. `apps.memory` остаётся владельцем общего фасада Wiki и защищённого поиска исходников. В конфигурации нескольких логических пространств включается provider `crow`; каждому физическому CROW bundle выделяется свой подкаталог **в том же Git-каноне**, внутри которого работает почти штатный `llmw2.Wiki`. Native `raw/`, `.archive/` и `.llmw2/sync/` считаются вспомогательным состоянием CROW, а не бизнес-каноном, и отдельно резервируются. LBS остаётся владельцем доступа, privacy, индексов/confirmation-state и Git-фиксации.

Если модуль выключен, LBS сохраняет доступ к содержимому OKF-страниц без CROW. Все документы нового внедрения сразу соответствуют OKF v0.2. Для существующих dev/test данных достаточно обновления кода, тестовых фикстур или повторного создания стенда — **нет нужды разрабатывать мигратор продуктивных Wiki-данных**.

### Минимальные конфигурационные атрибуты (логический контракт)

```yaml
corpus_id: org-crow-common
provider_code: crow
bundle_path: org/crow/common
scope: org:default       # только пример: фактический допуск настраивает Access
writer: lbs-controlled
external_llm_allowed: false  # определяется privacy policy; запрещённый внешний вызов fail-closed
index_corpus: knowledge
enabled: false            # до прохождения acceptance
```

Не вводить новую сущность БД/общий реестр модулей ради единственного пилота. Использовать действующие typed runtime-настройки и capability gate LBS. Отключение provider не удаляет bundle. Указанный `scope` — не самостоятельная авторизация, а ограничение сверху от LBS Access.

## 2. Контракты и владельцы операций

### Выбор стратегии доступа до запуска первого корпуса

**Профиль L0 = A + выборочная C (только чтение):** два и более логических пространства (например, общие знания и бухгалтерия). Каждый объединяет один или несколько самостоятельных физических CROW OKF bundles. LBS Access выбирает разрешённые bundles **и заметки внутри них** до `Steps.select`; финальная проверка повторяется перед выдачей. Для пользователя **нет конкурирующего общего защищённого поисковика**; существующие Source Adapters, MemorySourceObject и технические FTS-проекции сохраняются для регистрации/обработки источников и вспомогательных нужд.

**Фильтрация перед `select` — небольшая операция адаптера**, без изменения native алгоритма: создаём request-local **копии Folder и Note** с безопасными title/description и непрозрачными относительными ссылками. `check_select` сравнивает идентичность выбранных Note **с теми Note-копиями, которые входят в переданный фильтрованный root**, а не с оригинальным деревом; поэтому копирование допустимо и снижает риск случайного использования `body/sources`. Сопоставление Note-копии с каноническим `knowledge_id` остаётся исключительно в LBS. Native `select` не читает `raw`. Нельзя использовать native `Wiki.ask` как общий пользовательский API: он может дополнительно читать `raw` и `.archive`. **Фильтрация во время `ingest` — другая, более сложная задача**: автоматические merge/relate/plan/split не должны смешивать несовместимые ACL. L0 маршрутизирует запись в отдельные физические write-partitions с однородным разрешённым доступом, скрывая их от пользователя за логическим пространством. Вариант временных read-only bundles допускается только как эксперимент. Source API не является системой прав, OpenFGA может быть backend решения Access.

**Инвариант производного знания:** слияние допустимо только когда целевая аудитория имеет право на все используемые источники и содержание. Не переносить закрытую информацию в общий CROW-корпус через обезличивание без подтверждённой достаточности обработки/деклассификации.

| Вопрос | Единственный владелец |
|---|---|
| Оригинальные файлы и бизнес-объекты | Домен/внешняя система |
| `MemorySourceObject`, ID источника и статус индекса | Нынешний LBS source ingestion |
| Подготовка безопасного текста/названия/URI | LBS `prepare_content` из PRIV-плана |
| Организация/синтез заметок в выделенном bundle | Native CROW, только через LBS adapter |
| Право на чтение, помещение в prompt, публикацию в комнате | LBS Access и destination privacy |
| Коммит файлов заметок и их доступность | LBS corpus writer gate |
| `working / needs_confirmation / confirmed` | Frontmatter канонической заметки + LBS confirmation projection |
| Индексы FTS, карточки `MemoryKnowledgeItem`, аудит | Существующий `apps.memory`; можно пересоздать |
| `raw`, `.archive` и sync cursors CROW | Вспомогательное состояние CROW с отдельным lifecycle |

### Где живут права (минимальная LBS-owned реализация)

**Из CROW не вызывается LBS Access API.** Роли, группы и пользователи уже хранятся в `accounts`/PostgreSQL; LBS Access вычисляет права в текущем доверенном процессе LBS. Дополнительно нужен лишь реестр `space_id → bundle_id[]` + правило чтения/записи пространства (может быть typed runtime-настройкой или небольшой моделью `KnowledgeSpace`) и **необязательные** Note-level исключения, привязанные к стабильному `knowledge_id` (например, `KnowledgeNoteRestriction` / существующий ресурсный ACL backend). Записи grants — только в LBS Access; никаких групп/пользователей в CROW.

Проверка `can_read_note = can_read_space AND note_is_registered AND note_policy_allows AND sensitivity/audience_allows`. Отсутствие отдельной Note-рестрикции = наследование пространства *для зарегистрированной действующей страницы*, явный deny имеет приоритет; Note не может расширить права пространства. Текущий LBS `scope_tokens_match` проверяет OR-пересечение и **не заменяет** нужную семантику AND-наследования.

Минимальный OKF Frontmatter для CROW: штатные `type/id/title/description/sources`, плюс управляемые LBS `knowledge_id` (стабильный внешний идентификатор), `sensitivity` и `confirmation_state`. `space_id` определяется через привязку физического bundle в LBS; **не нужны** списки ролей, имена пользователей и ACL-правила в YAML. Нынешний `scope_tokens`, присутствующий в нескольких LBS проекциях, в новом пути нельзя оставлять вторым независимо изменяемым источником прав. Дублирование допустимо только как восстанавливаемый индекс, не как отдельная матрица разрешений. Подробности: [4.10–4.11 архитектурной спецификации](11_CROW_OKF_INTEGRATION.md).

### Минимальный adapter (псевдокод, не реализован)

```python
class LbsCrowAdapter:
    def ingest_safe_source(self, source_ref, actor_ctx) -> str: ...
    def select_notes(self, query, actor_ctx) -> list: ...
    def prepare_context(self, query, actor_ctx): ...  # native Researcher.ask + capture-answer
    def answer(self, question, actor_ctx): ...  # optional: gated final LLM
    def get_note(self, note_ref, actor_ctx): ...
    def reconcile(self, corpus_id): ...
```

**Два режима CROW вместо одного:** `knowledge.search` может вызывать только `Steps.select(ctx, filtered_root, question)` для списка подходящих Note; **это быстрый поиск без строк таблиц, истории и конфликтных подсказок**. Для итогового агентского ответа использовать `knowledge.prepare_context`: нативный `Researcher.ask()` с `ScopedReadStore` (`load/read` с ACL + destination privacy) и подменённым **только** `Steps.answer=collect_context` (не вызывает финальную CROW LLM). Обёртка `select_and_hydrate` — **только условная оптимизация**, не обязательная часть пилота. Тогда CROW по-прежнему выполняет `_with_history`, `_conflicting`, `_with_rows`, а LBS-агент формирует финальный ответ. Изменение upstream не требуется для прототипа; тип `WikiStore` в конструкторе `Researcher` — не официальный протокол, поэтому обязательны contract tests на pinned CROW. Ни `Wiki.ask` со штатным store, ни `Answer.citations` от capture-режима не считать безопасным LBS API. Подробно: [разделы 4.7–4.8 архитектуры](11_CROW_OKF_INTEGRATION.md).

### CROW-01 — SafeProjection и единый допуск до модели

**Скоуп PII остаётся открытым:** этот пакет обеспечивает единый маршрут доступа/назначения и использует только **выбранный** профиль `pii_off / pii_guarded / pii_strict`; он **не предписывает обязательную детекцию, извлечение или обезличивание всех персональных данных**. Для доверенного закрытого локального режима PII может быть допустим по правам/цели; для внешней модели требуется отдельное egress-разрешение. Не строить новый NER/DLP сервис до отдельного архитектурного решения. Синтетические PII-тесты проверяют работу выбранной политики, а не автоматическое включение `guarded` у всех источников.


**Зависимость:** PRIV-00..PRIV-04. **Не начинать на реальных данных без этой границы.**

**Сделать:** LBS формирует целевое представление текста, заголовка, полей, безопасного `Origin.link` и хеша из `MemorySourceObject`/`SourceObjectEnvelope`. Проверяет и источник, и **все назначения** (`wiki_git`, `agent_context`, `external_llm`, если применимо). При отсутствии разрешения облаку — работать только с разрешённой локальной моделью либо отказать. `Origin.version` включает fingerprint исходной версии, парсера и privacy-политики. Исходные paths/ФИО в `origin.id` не выпускать, если destination это не допускает: использовать стабильный непрозрачный ID и разрешаемый LBS `source_ref`.

**Проверить:** запрещённый маркер отсутствует не только в `raw`/заметке, но и во входном prompt, title, ссылке, `index.md`, `log.md`, карточке индекса, trace и исключении. Смена `policy_version` не приводит к ложному `unchanged`.

### CROW-03 — единый writer, читательский барьер и восстановление

**Сделать:** один глобальный `knowledge_repo_lock` вокруг полного *пишущего* вызова CROW, после native save — проверка изменённых файлов/путей/Frontmatter/ACL/секретов и единственный LBS Git commit. Нельзя использовать per-file `write_knowledge_item_file` для существующих CROW заметок. Добавить **барьер чтения этого корпуса** на время native mutation и согласования commit/index: `knowledge.search/get` и `CROW.select/ask` должны ждать, либо возвращать управляемое «обновляется»; никакой частично обновлённой страницы через LBS API. Продумать порядок блокировок LBS → CROW, без вложенного получения того же LBS lock.

**Сделать:** зафиксировать маленький журнал операции (`corpus, operation_id, start_git_head, changed_paths, phase, committed_git_head`), размещённый **вне Git**. На старте, обнаружив незавершённую операцию, блокировать выдачу изменённого корпуса до reconcile/restore. До Git commit восстановить только выделенные tracked paths из исходного `HEAD` и удалить только новые разрешённые пути операции; после успешного commit — восстановить проекции. **Никогда не выполнять `git reset --hard` всего репозитория.** Отдельно определить судьбу новых и изменённых `raw/.archive/.llmw2/sync`: нужен manifest и backup/restore; их нельзя без проверки чистить глобальным `rmtree`.

**Проверить:** падение после `save_raw`, `archive_note`, `write_note`, `relate`, `append_log`, после Git commit и во время индексации. После restart нет частично читаемой заметки, потерянной одобренной ревизии, потерянного исходника либо «тихой» успешной повторной загрузки.

### CROW-04 — OKF v0.2, метаданные, индекс и перемещения

На новых заметках проставлять LBS `knowledge_id`, `lifecycle: current`, `confirmation_state: working`; `status` имеет только значения из OKF `draft|stable|deprecated` или отсутствует; LBS `active/deleted` остаётся только внутренним статусом проекции. `verified` дописывать только при реальном подтверждении человека. Native CROW `update_note` сохраняет неизвестные поля, но адаптер должен проверять это на каждом merge.

**Сделать:** регистрировать *новые* файлы CROW как `MemoryKnowledgeItem`, обновлять карточки по устойчивому идентификатору (CROW `id` можно использовать как ключ в пределах `corpus_id`, а `knowledge_id` как публичный ID). Перемещение заметки (`move_note` / `_split_folder`) меняет path, но не `knowledge_id`, связи, разрешения и историю. **Весь namespace, управляемый CROW, исключить из legacy LBS walkers/index/log/materializer и обычного `memory_reconcile`; CROW projector отдельно читает только `type: Note`, никогда `raw/`, `.archive/`, `.llmw2/`, `type: Source`.** Особенно важно не включить закрытые CROW заметки в общий `org/index.md`, который сейчас строится через рекурсивный обход `org/**/*.md`. Никогда не присваивать модели LBS строку `stable` как её собственный статус. В синхронизации новых и ранее созданных CROW страниц не перезаписывать CROW `index.md`/`log.md`; их ведёт CROW. Коммиты LBS использовать без свободных заголовков/путей, которые могут попасть в общий журнал.

**Проверить:** roundtrip неизвестного Frontmatter, type/OKF status, правильный scope и `verified`, перенос заметки в новый раздел, повторный импорт/переиндексация без дубликатов; `MemorySearchDocument` после восстановимого сбоя. Тестовый `lifecycle: pending` не должен раскрываться — это **проверка контракта**, а не миграция исторических данных.

### CROW-05 — поиск, ответ и отключение провайдера

**Сделать:** построить **кэш базового дерева Python-объектов в RAM для каждого физического CROW bundle** (один полный `WikiStore.load()` после старта или удачного commit, immutable snapshot, атомарная замена и проверка версии в каждом LBS worker). **Это не физическая копия Markdown-файлов и не только список путей:** содержатся Frontmatter и body Note, raw/архивы отдельно на диске. На запрос пакетно вычислить разрешённые IDs из LBS Access и собрать только **лёгкое scoped `Folder/Note` дерево** без повторного чтения Markdown-файлов. Пространства без Note restrictions могут использовать готовое безопасное представление; дорогую per-profile/per-user cache вводить лишь после измерений. LBS `knowledge.search` маршрутизирует запрос по разрешённым `space_id → bundle_id`, вызывает native `Steps.select` с этим filtered tree и возвращает `KnowledgeSearchHit`, а не upstream `Answer`. Клонировать **и Folder, и Note** в request-local дереве: `check_select` использует Python `id(Note)` только относительно **переданного scoped root**, поэтому возвращённые выборкой копии допустимы. Note-копии содержат только разрешённые безопасные `id/title/description` и при необходимости обезличенный `rel`, без `body/sources/See also`; скрытые ветви/описания исключаются. Проверять fallback `classic.select` на том же scoped-root. После выборки проверять ACL страницы, источников/citations, `See also`, получателя и `confirmation_state`; только затем LBS/агент формирует ответ. Native `Wiki.ask` не используется в защищённом потоке, так как `_with_rows` и `_with_history` читают raw/archives без per-source LBS Access. Никакой второй основной retrieval по закрытым документам не нужен.

**Сделать:** выключение provider запрещает новые вызовы в CROW, не удаляет данные; LBS в состоянии прочесть CROW OKF Markdown самостоятельно, не включая `llmw2`. Альтернативный provider может принять тот же `corpus_id` лишь при остановке прежнего writer, сохранении стабильных `knowledge_id`/`sources`/статусов и инвариантов безопасности.

**Проверить:** Access работает независимо от Source API и CROW: пользователь общего пространства получает только разрешённые CROW-заметки; пользователь бухгалтерии получает разрешённые common + accounting; ограничения отдельных Note внутри accounting работают **до `select`**, недоступные заголовки/описания отсутствуют в prompt/trace и не расходуют top-k. При попытке открыть raw дополнительно вызывается проверка ACL оригинала; корпоративный групповой чат не раскрывает чужие источники. Read-only чтение/поиск после отключения CROW остаются возможны через LBS по каноническому OKF; для полнофункционального classifier-поиска нужен другой выбранный provider.

### CROW-05b — сохранение штатной подготовки контекста

**Цель:** не потерять функциональность CROW `Researcher.ask`, но использовать окончательный ответ агента LBS.

**Сделать:** создать request-local `ScopedReadStore` c `load()` (scoped tree из кэша с **разрешёнными full body Note**; строковые тела из безопасного кэша можно переиспользовать по ссылке, не копируя текст) и `read(rel)` (авторизованный доступ к raw/archive версии плюс destination privacy). Штатный `Steps.select` получает только разрешённые заметки; его текущие classifier-промпты используют лишь безопасные title/description и пути, не body. До передачи корпуса CROW подтвердить, что выбранная политика разрешает тексты для внешнего/локального классификатора и агента. Запрещённые источники и история должны давать контролируемый отказ/пропуск с явной отметкой о неполном контексте. **Опционально после измерений:** metadata-only view + `select_and_hydrate`, который дозагружает тела только выбранных заметок.

На основе `dataclasses.replace(wiki.steps, answer=collect_context)` создать собственный `Researcher` (официальные Steps, конструктор с доверенным read-proxy) **на каждый запрос**. `collect_context` сохраняет итоговые Note и augmented question (с исторической/конфликтной подсказкой) в локальный объект и возвращает обычный `str` для CROW `check_answer`; реальный final LLM answer выдаёт LBS. Не использовать `Answer.citations`, формируемые regex по сгенерированному тексту, как LBS provenance в capture-режиме: собрать их из разрешённых ID и подтверждённых Source refs.

**Таблицы — отдельный приёмочный gate:** `Researcher._with_rows` работает с нативным форматом `sheets.sheet_text` (§sheet name + CSV block§), а не любым произвольным обработанным текстом. При предварительной LBS-очистке XLSX **разбирать её на листы в LBS**, применять privacy/row-level restrictions **до** raw и передавать CROW отдельные `Wiki.ingest(text=safe_sheet_text, origin=Origin(id=file_id#sheet,...))`; обычный `Wiki.ingest_file` формирует листы до extract hook и не подходит для запрета исходных PII внутри CROW. При необходимости адаптер отдельно воспроизводит `Wiki._after_sheets` (связи/удалённые листы) на разрешённых материалах. У `rows_for` статистика может учитывать все строки переданного листа; смешанные per-row ACL без безопасного предварительного отбора/агрегирования запрещены.

**Проверить реальные условия upstream:** `_with_history` только если `revisions=replace`, есть предыдущая версия и classifier выбрал историю; `_conflicting` включается при 2+ Note и `answer_conflicts`, не доказывает конфликт; `_with_rows` читает sheets из `/raw/` с бюджетом `effective_read_chars`. Состояние classifier/privacy destination и логи должны быть защищены. Тестировать note-level deny, raw без прав, отказ старой версии, отсутствие пропуска запрещённого body в prompt и глобальное ограничение итогового контекста. Когда CROW изменит внутренний пайплайн — контрактные тесты не должны молча пропустить регрессию.

**Несколько bundles:** встроенная `_conflicting` работает только внутри каждого вызова `Researcher.ask`. При объединении результатов корпусов LBS может повторить проверку межкорпусного конфликта через чистую функцию CROW `conflicts.conflict_state` и один classifier-вызов, если такой сценарий нужен; общий token/char budget применяется перед ответом агента LBS. Не утверждать, что native CROW сам обеспечивает cross-bundle проверки.

### CROW-06 — эксплуатация и объективное решение о Source API

**Сделать:** backup/restore Git + `raw` + `.archive` + sync-state + БД-проекций/manifest; периодические проверки ссылок и чтения; p95 времени ingest/search, прирост объёма `raw`, число raw-копий на источник, долю merge/fallback, число ручных исправлений и ошибок, стоимость LLM/классификатора. Проводить оценку на корпусах 100, 1 000 и ≥10 000 документов либо на меньших, если пилот это ограничивает; отмечать потолок проверенного масштаба.

**Только после метрик:** отдельно обсудить прямой Source API в CROW (переписать чтение `raw` в `OriginIndex`, ревизиях и табличном retrieval; совместимые `/raw/` aliases), либо отказ от CROW как provider. `MemorySourceObject` в любом случае не меняется без отдельного ADR.

## 4. Основная матрица e2e-проверок

| Проверка | Успех |
|---|---|
| Набор рабочих интервью | Запись `working` сразу, `needs_confirmation` не блокирует |
| Подтверждённая заметка изменена агентом | Новая редакция не остаётся `confirmed` автоматически |
| Несовместимая ACL для ingestion | Не допускается автоматическое cross-ACL merge; материал направлен в подходящий write-partition или запись отклонена |
| Отзыв группы во время поиска | Финальная проверка LBS прекращает выдачу после отзыва, устаревший кэш не разрешает доступ |
| Незарегистрированная новая Note | Не выдаётся до проекции Access/Knowledge, даже при валидном OKF |
| Подмена `scope_tokens` или `sensitivity` агентом | Не расширяет права; writer отклоняет/удерживает правку |
| Individual Note ACL внутри отдела | Запрещённые title/description/body/папки не попадают в `select` и его fallback |
| Доступ к Note, но не к её raw | Разрешённая заметка видна; исходный raw не открывается без отдельного ACL источника |
| Таблица в разрешённой Note | `prepare_context` использует релевантные строки raw только при праве на источник; plain `select` их не добавляет |
| XLSX с разными ACL на строки | LBS подготавливает per-sheet безопасный `sheet_text` до ingest; статистика raw не содержит запрещённых строк, данные оригинала не отправляются CROW |
| Вопрос об историческом правиле | `prepare_context` включает разрешённую предыдущую `.archive` редакцию (при условиях CROW), недоступную не читает |
| Противоречие между двумя Note | `prepare_context` передаёт подсказку о возможном конфликте; `select` один этого не делает |
| Несколько физических bundles | Итоговый LBS контекст ограничен общим бюджетом; cross-bundle конфликт проверяется отдельно, если включён |
| Два писателя / Windows | Одновременное изменение одного namespace исключено |
| Чтение во время merge | Нельзя получить промежуточную редакцию |
| Кэш дерева | 100 повторных поисков без изменений не вызывают 100 `WikiStore.load()`, обновление после commit видно всем workers по версии |
| Прерванная запись/перезапуск | Журнал восстанавливает либо блокирует, никакой тихой потери |
| `raw` и архивы не в Git | Нет следов в `git ls-files`; есть separate backup и restore |
| Попытка читать `raw` как Wiki Note | Отказ/исключение из любого обхода |
| Legacy `status: active` / `lifecycle: pending` | Нет ошибочной публикации после OKF-конверсии |
| OKF unknown keys + citations | Сохраняются при merge, split и rename |
| Смена privacy-политики | Проекция пересчитана или блокирована, нет false `unchanged` |
| Отказ CROW/выключение модуля | Страницы и статусы доступны через LBS без зависимости от CROW |
| Обновление pinned upstream CROW | Набор контрактных тестов повторно проходит |
| Отказ индекса | Канон сохранён, поиск корректно деградирует или блокируется до восстановления |

## 5. Подготовка возможной будущей смены хранения источников (не миграция первого запуска)

Для каждого `sources[]` сохраняются не только нативный `resource: /raw/...`, но и: стабильный `source_ref`, источник/аккаунт/id, версия входа, версия обработки, хеш подготовленного тела. Не делать путь `/raw` корпоративным `source_ref` или единственным ID; так CROW можно заменить.

Если после опытной эксплуатации возникнет потребность читать `raw` через LBS Source API, подготовить *новую реализацию внутреннего SourceBackend CROW*, не меняя договорённости о `knowledge_id`, OKF Markdown и адресах LBS API. **Это будет отдельная будущая миграция способа хранения**, если уже накопятся реальные данные CROW. Для первого запуска её нет. Потребуются сравнение read/write результатов old-native и new-Source API и сохранение совместимых aliases, а не слепая подмена путей.

При смене модуля raw/архивы не должны исчезнуть раньше, чем все ссылающиеся заметки стали независимы от них или их версии надёжно доступны по новому адресу.

## 6. Согласование перед кодом

Открытые решения для владельца архитектуры: (1) какие два или более первоначальных логических пространства создать и как задать аудиторию каждого; (2) какие отдельные запреты на Note внутри них ожидаются и где нужны физические write-partitions; (3) какая схема retention/backup для native raw и `.archive`; (4) какие модели могут получать `SafeProjection` с учётом egress; (5) что считать метриками для будущего Source API или mixed-ACL ingest. **LBS Access всегда определяет права вне CROW; Source API не является предпосылкой для ACL.**

Остальные принципы (OKF, один writer, сохранение `MemorySourceObject`, сменяемость CROW, privacy до Git и модели) зафиксированы в архитектурном предложении и не должны внедряться на основании только этого плана без ADR/проверок.
