# Отчёт исполнения: 02 — формы в правой панели

## Результат

Общий правый сайдбар подготовлен к безопасным пользовательским формам создания
и редактирования без универсального CRUD-контроллера:

- серверный `RightPanelFormDescriptor` оборачивает только дескриптор,
  сформированный зарегистрированным доменным поставщиком;
- допустимые режимы ограничены `view`, `create`, `edit`, добавлен размер
  `workspace`;
- пользовательская команда формы отделена от существующей команды
  `open_right_panel`; серверная граница `ui.open_right_panel -> view` не
  изменялась;
- формы с `data-right-panel-form` получают защиту от повторной отправки,
  сохранение введённых значений при ответе 422, признак несохранённого
  черновика и сообщение при транспортной ошибке;
- каноническое событие `rightPanelFormSucceeded` закрывает панель без
  подтверждения и один раз публикует `rightPanelFormSaved`; доменные события
  обновления списка остаются ответственностью доменного ответа `HX-Trigger`;
- улучшены ловушка фокуса и возврат фокуса к элементу, открывшему панель;
- предупреждение показывается только при закрытии или замене формы с
  несохранёнными изменениями;
- режим `workspace` адаптирован к узкому экрану как полноэкранный слой, панель
  действий переносит кнопки без горизонтальной обрезки.

После независимого ревью дополнительно усилены границы оболочки:

- сервер рекурсивно декодирует адрес и отклоняет абсолютные URL, authority
  (`//host`), обратные слеши, управляющие символы и фрагменты;
- клиент разбирает адрес через `URL`, сверяет `origin` с текущим окном и до
  разбора отклоняет те же приёмы, включая кодированные обратные слеши;
- поддерживаемый swap сужен до фактически реализованного `innerHTML`, поэтому
  стабильный узел `#global-right-panel-content` не может быть удалён;
- одновременно существует только одно поколение загрузки и один
  `AbortController`: закрытие и новое открытие отменяют старый запрос, а
  запоздавший ответ не меняет DOM и состояние занятости;
- ловушка фокуса возвращает Tab/Shift+Tab внутрь панели, даже если фокус
  программно оказался снаружи.

## Проверки

- `node --check static/src/js/right_panel.js` — успешно;
- `python -m py_compile apps/core/right_panels.py apps/core/test_right_panel_forms.py` — успешно;
- `manage.py test apps.core.test_right_panel_forms --verbosity 1` — успешно,
  восемь тестов (`Ran 8 tests`, `OK`); системная проверка вывела только уже
  известное предупреждение `settings_center.W002` о недоступном состоянии
  миграции документов настроек;
- `manage.py test apps.core.tests.RightPanelContractTests --verbosity 1` —
  успешно, три существующих контрактных теста (`Ran 3 tests`, `OK`);
- `playwright test -c scripts/e2e/playwright.config.ts scripts/e2e/tests/right_panel_form_shell.spec.ts --project=chromium`
  — успешно, семь браузерных тестов (`7 passed`), включая настоящий
  HTMX-цикл `GET -> POST 422 -> POST 204 + HX-Trigger`; после повторного
  ревью набор снова выполнен успешно (`7 passed`, 9,4 с);
- `git diff --check` — успешно на момент проверки.

Первый обычный запуск целевого набора временно остановился из-за промежуточного
состояния параллельной миграции склада (`StockLot` уже отсутствовал в модели,
но ещё импортировался админкой). После синхронизации с исполнителем миграции
запуск повторён штатно и завершён успешно.

Playwright-сценарий проверяет черновик, закрытие, 422, повторную отправку,
успешное событие, возврат фокуса, ширину 390 px, вредоносные URL, запрет
`outerHTML`, закрытие во время загрузки и обратный порядок ответов. Повторное
ревью дополнительно закрыто наблюдаемыми проверками границ:

- два последовательных `requestSubmit()` выполняются при искусственно
  задержанном настоящем HTMX POST; пока первый запрос выполняется, route
  фиксирует ровно одну попытку, кнопка сохранения заблокирована, а после 422
  она снова доступна и значение формы сохранено;
- ограничивающие прямоугольники обязательных действий «Сохранить» и «Отмена»
  полностью находятся внутри окна `390 x 844 px` по обеим осям.

HTMX в сценарии настоящий (`static/django_htmx/htmx.min.js`), однако ответы
выдаёт управляемый Playwright route, а не Django-домен. Полный сквозной
Django/HTMX сценарий создания и редактирования складского документа намеренно
остаётся в задаче 04: именно она владеет доменной формой, сохранением и panel
endpoint. Этот остаток не относится к общему механизму задачи 02.

## Проверка AI-границы вне write scope

Независимое ревью обнаружило, что исходный тест
`apps.ai.tests.test_views.AIViewsTests.test_generic_right_panel_rejects_edit_mode_at_gateway_boundary`
получал `outside delivered task policy`, то есть завершался до проверки `mode`
в `_dispatch_tool`. Ранее успешный запуск этого теста нельзя было считать
доказательством границы `view-only`.

Файл `apps/ai/tests/test_views.py` не входит в write scope задачи 02. Основной
агент параллельно исправил тест следующим образом:

1. Получил `snapshot = ai_policy_snapshot()` из
   `apps.ai.tests.test_contract_gateway`.
2. Добавил в
   `snapshot["ai.contract.task_types"]["payload"]["task_types"]` тестовую
   политику:

   ```python
   {
       "id": "ui.open_right_panel",
       "title": "Open right panel",
       "mode": "read",
       "description": "Test delivered policy for the right-panel tool.",
       "allowed_tools": ["ui.open_right_panel"],
       "requires_confirmation": False,
       "output_mode": "ui_command",
       "example_requests": ["Open a visible record."],
   }
   ```

3. Выполнил POST внутри
   `patch("apps.ai.views.get_ai_document_snapshots", return_value=snapshot)`
   отдельно для `mode="create"` и `mode="edit"`.
4. Для каждого ответа проверил `status_code == 400` и наличие текста
   `ui.open_right_panel поддерживает только режим просмотра` в массиве
   `response.json()["errors"]`, запись `AgentActionLog(status=FAILED)` на
   попытку и отсутствие `PendingAction`.

Основной агент сообщил об успешном повторном запуске параметризованного теста;
ложноположительная проверка закрыта без выхода исполнителя задачи 02 за
назначенный write scope.

## Остаток для доменных задач

Складские partial-шаблоны должны помечать форму атрибутом
`data-right-panel-form`, возвращать 422 с заполненной формой при ошибках и
отправлять `rightPanelFormSucceeded` вместе со своим событием обновления списка
после атомарно успешного сохранения. Серверная идемпотентность записи остаётся
обязанностью складского сервиса; общий клиентский слой только отбрасывает
повторную отправку, пока первый запрос выполняется.
