# Встроенное редактирование записей листа ожидания

Статус: реализовано и технически принято 2026-08-11.

## Цель

Убрать отдельный переход по кнопке «Редактировать»: доступные для изменения поля должны быть
формой непосредственно в окне просмотра записи. После сохранения окно остаётся открытым и
показывает обновлённые данные и историю.

## Границы

- `apps/waiting_list`: контекст формы, серверное сохранение, точный аудит изменённых полей;
- `templates/waiting_list`: единая разметка полей для создания и встроенного редактирования;
- `static/src/css/app.css`: компактное представление формы в окне просмотра;
- unit/integration и Playwright-сценарий.

Вне границ: изменение набора полей, модели прав, статусов и схемы базы данных.

## Решение

1. `WaitingListEntryDetailView` передаёт заполненную `WaitingListEntryForm`.
2. Пользователь с правом редактирования видит поля сразу; пользователь только с правом просмотра — прежнее представление без полей ввода.
3. Форма отправляется HTMX-запросом на существующий маршрут обновления и заменяет содержимое того же окна.
4. Сервис обновления в транзакции блокирует запись, сравнивает нормализованные значения, сохраняет только фактические изменения и создаёт одну запись аудита с названиями изменённых полей.
5. Исходные и новые персональные значения в строку аудита не копируются.

## Приёмка

- в окне просмотра нет кнопки «Редактировать»;
- автор записи может изменить данные и сохранить их, не покидая окно просмотра;
- при ошибке проверки форма остаётся в окне и показывает ошибки;
- очищение необязательных полей сохраняется;
- аудит создаётся атомарно, содержит автора и только реально изменённые поля;
- сохранение без изменений не создаёт ложную запись аудита;
- пользователь без права редактирования не видит форму и получает `403` при прямом POST;
- целевые тесты, профиль `ui`, один полный прогон и сквозной браузерный сценарий проходят.

ADR не требуется: границы приложения, схема данных, модель прав и существующий паттерн предметного аудита не меняются.
