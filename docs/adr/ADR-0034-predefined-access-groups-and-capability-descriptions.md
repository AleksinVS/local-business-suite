# ADR-0034: Предопределённые группы доступа, комментарии к правам и направление row-level доступа

- Статус: Accepted
- Дата: 2026-07-30
- Дополнения:
  - 2026-08-05 — административный UX ролей и риск-метаданные прав;
  - 2026-08-06 — серверное двухшаговое подтверждение и защита устаревшей формы.
- Связанные документы: `docs/architecture/POLICY_MODEL.md`, ADR-0023 (branch-доступ заказчика), ADR-0031 (contract store)

## Контекст

Ревью системы прав (2026-07-30) показало:

1. В проекте три параллельных механизма авторизации: capability-роли из контракта
   `role_rules.json` (сопоставление с `django.contrib.auth.Group` по имени),
   флаги `is_staff`/`is_superuser` и точечно Django `Permission` (только `apps.memory`).
   Ни права, ни группы не имели человекочитаемых комментариев — нетехнический
   администратор не мог понять, что даёт та или иная галочка.
2. Группы создавались командой `seed_roles` только для ролей контракта
   (`customer`/`technician`/`manager`); группы памяти (`memory_admin` и др.)
   нигде не создавались автоматически.
3. Лист ожидания (персональные данные пациентов: ФИО, дата рождения, телефон)
   был доступен любому авторизованному пользователю: `can_view_waiting_list` =
   `is_authenticated`. По правилам организации доступ должны иметь только врачи
   (уточнение владельца, 2026-07-30).
4. `superuser_rules()` дублировал список прав вручную и уже отстал от контракта
   (не содержал `memory_organization_write/review`).
5. Редактор ролей (`core:role_rules`) хранил список флагов захардкоженным в двух
   местах и не показывал `manage_ai_skills`, `memory_organization_*`.

## Решение

1. **Справочник прав в контракте.** В `contracts/role_rules.json` добавлен служебный
   блок `$capabilities`: для каждого права — `type` (`flag`/`scope`/`targets`),
   `label` и `description` на русском языке для нетехнических пользователей.
   Ключи с префиксом `$` не являются ролями: валидатор, редактор ролей и
   `seed_roles` пропускают их (валидатор дополнительно проверяет структуру блока).
   Контракт остаётся единственным источником истины: подписи редактора ролей и
   набор булевых прав `superuser_rules()` выводятся из `$capabilities`
   (`apps/workorders/policies.py: capability_flags()`), статический список остаётся
   только как fallback на случай деградации store на старый снимок.

2. **Комментарии ролей.** У каждой роли контракта появилось поле `description` —
   понятное описание «кому выдавать и что даёт» (рядом с существующим
   `display_name`).

3. **Предопределённые группы.** Команда `seed_roles` создаёт и поддерживает:
   - роли канбан-доски: `customer` (Заказчик), `technician` (Техник),
     `manager` (Менеджер);
   - `admin` (Администратор портала) — все права контракта; доступ в Django-админку
     по-прежнему требует флага `is_staff` (группа не может выдать его);
   - `doctor` (Врач) — доступ к листу ожидания;
   - группы памяти: `memory_admin`, `memory_auditor`, `memory_index_operator`,
     `memory_observer` (описания — `apps/memory/policies.py:
     MEMORY_REVIEW_GROUP_PROFILES`).

4. **Комментарии групп в БД.** Новая модель `apps.accounts.models.GroupProfile`
   (OneToOne к `Group`): `title`, `description`, `is_predefined`. Для
   предопределённых групп профиль синхронизируется `seed_roles` из контракта;
   для произвольных групп заполняется вручную (админка, settings_center).
   Кастомные Django `Permission` приложения `memory` уже имеют русские
   человекочитаемые имена в `Meta.permissions` — отдельная модель комментариев
   для них не требуется.

5. **Лист ожидания — только врачи.** Новые права `view_waiting_list` и
   `create_waiting_list`; `apps/waiting_list/policies.py` проверяет их через
   `has_role_capability` вместо `is_authenticated`. В дефолтном контракте они
   включены только роли `doctor` (в том числе выключены у `manager`/`admin` —
   решение владельца «к листу ожидания имеют доступ только врачи»).
   Суперпользователь как технический аккаунт сохраняет полный обход
   (`superuser_rules()` включает все булевы права) — это стандартная семантика
   Django; при необходимости строгого запрета и для суперпользователя нужен
   отдельный ADR. Пункты меню «Лист ожидания» и «Аналитика» скрываются по
   правам (`show_waiting_list_nav`, `show_analytics_nav`) — это только UI,
   серверная проверка выполняется во views.

6. **Административный UX и риск-метаданные.** Для каждого элемента
   `$capabilities` обязательны `section` (`workorders`, `organization`,
   `ai_memory`, `personal_data`) и `risk` (`normal`, `elevated`, `critical`).
   Сервер использует эти поля для карточной группировки, предпросмотра и
   обязательного подтверждения чувствительных изменений. Клиентский JavaScript
   может улучшать предпросмотр, но не определяет риск и не разрешает запись.
   В пользовательском интерфейсе «роль доступа» означает шаблон бизнес-прав из
   контракта, а «техническая группа» — Django/AD-группу без соответствующей роли.
   Назначение ролей меняет только группы, совпадающие с ключами ролей, и не
   удаляет технические группы.

7. **Подтверждение не зависит от браузерного скрипта.** При первой отправке
   чувствительных изменений без подтверждения сервер не перенаправляет на
   пустую форму, а повторно показывает введённые значения, точный список риска
   и отдельную кнопку подтверждения. JavaScript отвечает только за ранний
   предпросмотр. До разбора checkbox-полей сервер проверяет версию HTML-формы и
   хеш прочитанного контракта; устаревшая вкладка отклоняется целиком и не может
   трактовать отсутствующие новые поля как отзыв действующих прав. Перед
   атомарной записью хеш проверяется повторно в сервисном слое.

## Row-level доступ: анализ и направление (не реализовано в этом ADR)

Нужен ли доступ на уровне записей — да, но точечно. В проекте он уже есть там,
где спроектирован: `workorders` (селектор `visible_workorders_queryset`, scope
`department_branch` и др., ADR-0023) и `memory` (scope-токены). Пробелы:

- `waiting_list`: просмотр не ограничен построчно (этот ADR закрывает доступ на
  уровне модуля — только врачи; построчное разделение, например по отделению
  врача, — отдельное решение);
- `inventory`: список/карточки устройств не ограничены веткой подразделения,
  хотя те же устройства в контексте заявок ограничены;
- `analytics` и дашборд `core`: агрегаты считаются по всем заявкам без учёта
  scope роли — скрытая зависимость от того, что `view_analytics` выдан только
  роли с `view_scope: all`;
- управление колонками канбана не привязано к `Board.allowed_groups`;
- Django-админка показывает staff-пользователю все записи без scoping.

Рекомендация: расширять существующий паттерн «policies + selectors»
(фильтрация queryset по пользователю, deny-by-default), а не вводить
per-object-ACL (django-guardian): модель доступа проекта ролевая и
иерархическая (ветка подразделения), отдельные ACL-строки на запись не нужны,
они добавили бы вторую базу истины и накладные расходы на синхронизацию.
Работы вынесены в backlog (раздел Next).

## Альтернативы

- **django-guardian (per-object permissions)** — отклонено: нет требований к
  индивидуальным ACL на запись; selector-паттерн уже решает задачу дешевле.
- **Отдельная модель Role в БД вместо контракта** — отклонено: дублировала бы
  `role_rules.json` (ADR-0031), потеряли бы git-историю и валидацию контрактов.
- **Комментарии прав в БД (PermissionProfile)** — отклонено для capability-прав:
  права живут в контракте, там же должны жить их описания; для Django
  `Permission` достаточно человекочитаемого `name`.
- **Хранить описания групп только в контракте (без GroupProfile)** — отклонено:
  группы создаются и вне контракта (админка, AD-синхронизация), им тоже нужны
  комментарии.

## Последствия

- Поведенческое изменение: пользователи без роли `doctor` теряют доступ к листу
  ожидания (dev-этап, боевых данных нет; существующим пользователям листа
  ожидания нужно выдать группу `doctor`).
- Новое право в контракте достаточно описать в `$capabilities` — оно
  автоматически появляется в редакторе ролей и у суперпользователя.
- После изменения структуры выполнены: миграция `accounts.0006_groupprofile`,
  `seed_roles`, обновление рабочей копии `data/contracts/role_rules.json`
  (dev-этап: копия совпадала с дефолтом).
