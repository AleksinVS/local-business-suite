# ADR-0044: Единый путь выполнения самописного ИИ-чата

- Статус: Accepted
- Дата: 2026-08-26
- Принято владельцем: 2026-08-26
- Уточняет: ADR-0027, ADR-0028, ADR-0032
- Связанный план: `docs/architecture/NATIVE_AG_UI_CHAT_DEVELOPMENT_PLAN.md`
- Workflow: `workflow/active/native-ag-ui-chat-development/`

## Контекст

Самописный ИИ-чат имеет два пользовательских представления:

- компактный чат в левой боковой панели;
- полноэкранная страница со списком сессий, командами и вложениями.

Боковая панель уже использует AG-UI через Django same-origin proxy и
`services.agent_runtime /ag-ui`. Полноэкранная страница сохранила отдельный
двухшаговый путь `send` + `stream` и нестандартный поток `/chat/stream`. Из-за
этого различаются обработка событий, ошибок, истории и вложений, а исправления
нужно повторять в двух клиентах.

Простая замена адреса недостаточна. Текущий endpoint боковой панели всегда
выбирает sidebar-сессию, доверяет части состояния клиента и повторно сохраняет
пользовательское сообщение. При повторе HTTP-запроса это может создать дубли и,
что важнее, повторить серверное действие инструмента.

## Решение

### 1. Один сценарий выполнения для двух native-представлений

Оба самописных представления используют один серверный сценарий:

```text
native sidebar | native full page
  -> Django: подготовить пользовательский ход
  -> Django: запустить ход в принадлежащей пользователю сессии
  -> services.agent_runtime /ag-ui
  -> общий AG-UI decoder/reducer
  -> отдельное отображение sidebar | full page
```

Едиными являются подготовка хода, проверка сессии, история, AG-UI transport,
редуктор событий, аудит и обработка ошибок. Разметка, навигация, список сессий и
компоновка поля ввода остаются разными представлениями.

### 2. Разделить три независимых понятия

- `session_channel` — назначение и жизненный цикл данных сессии (`internal` или
  `sidebar`);
- `presentation_surface` — место отображения (`sidebar` или `full_page`);
- `ui_driver` — реализация клиента (`native` или `copilotkit`).

Полноэкранное представление может открыть принадлежащую пользователю сессию
любого поддерживаемого канала. Новая полноэкранная сессия создается с каналом
`internal`; компактная панель продолжает создавать `sidebar`-сессии.

### 3. Сервер является источником истины

Django по URL определяет сессию и проверяет ее владельца и активное состояние.
Переданный `threadId` обязан совпадать с `ChatSession.external_id`. История для
runtime строится из базы данных; произвольные `messages`, `state`, `context` и
`resume` от браузера не считаются доверенными данными.

Actor payload использует реальный `session_channel`. Контекст страницы проходит
существующую серверную очистку и привязывается к конкретному пользовательскому
сообщению.

### 4. Подготовленный ход и защита от повтора

Перед AG-UI run браузер выполняет multipart-запрос подготовки хода. Django:

- проверяет сессию и длину запроса;
- на сервере разрешает slash-команду и повторно проверяет длину результата;
- проверяет вложения;
- один раз сохраняет пользовательское сообщение и привязывает к нему контекст;
- возвращает стабильные идентификаторы хода и сообщения.

Пара `(session, run_id)` уникальна. Повтор завершенного запуска воспроизводит
сохраненный результат и не вызывает агента или доменные инструменты повторно.
Параллельный повтор выполняющегося запуска отклоняется. Неопределенный результат
после разрыва соединения не перезапускается автоматически с тем же `run_id`.

### 5. Канонический поток AG-UI

`services.agent_runtime /ag-ui` становится единственным runtime endpoint для
пользовательских чатов. Он формирует события в причинном порядке:

1. `RUN_STARTED`;
2. текстовые, инструментальные и проектные события по мере работы;
3. ровно одно терминальное событие `RUN_FINISHED` или `RUN_ERROR`.

Аргументы инструментов не передаются в браузер необработанными. UI-команды имеют
стабильный идентификатор и применяются идемпотентно.

После приемки удаляются старые Django endpoints `send`/`stream`, клиент
`AgentRuntimeClient.chat_stream` и runtime endpoints `/chat` и `/chat/stream`.
Продуктовый URL `/ai/chat/` сохраняется.

### 6. Команды, вложения и ошибки

- Список команд в браузере служит только для выбора; доступ и раскрытие команды
  проверяются на сервере.
- Вложения принадлежат подготовленному сообщению, проходят ограничения размера и
  допустимого типа и выдаются через существующую проверку владельца.
- Ошибки получают единый безопасный пользовательский текст, технический журнал и
  аудит. Частичный ответ не считается успешно завершенным ходом.
- Завершение SSE без терминального события считается ошибкой.

### 7. CopilotKit остается эталонным клиентом

CopilotKit не переводится на Django same-origin endpoint в рамках этого решения.
Его Node runtime продолжает обращаться к тому же `services.agent_runtime /ag-ui`
и проверяет совместимость нижележащего AG-UI-контракта. Это сохраняет границы
ADR-0027 и не делает CopilotKit владельцем бизнес-логики.

Закрепленные версии `@ag-ui/client=0.0.55`, CopilotKit `1.59.5` и профиль
`ag-ui@0.0.55` не обновляются без отдельного согласования.

## Рассмотренные альтернативы

### Оставить два пути выполнения

Отклонено: исправления ошибок, история, аудит и потоковые события неизбежно
расходятся.

### Перевести только полноэкранный интерфейс на существующий sidebar endpoint

Отклонено: endpoint имеет sidebar-семантику сессии и не защищает запуск от
повтора.

### Перевести CopilotKit через Django endpoint одновременно

Отклонено как отдельная миграция без текущей пользовательской ценности.
Совместимость обеспечивается общим `/ag-ui` контрактом.

### Сохранить старый путь как постоянный аварийный режим

Отклонено: ADR-0032 уже вывел legacy-драйвер. Возврат одной только предыдущей
Git-версии небезопасен, потому что её код не знает о `ChatRun`. Для отката нужен
заранее проверенный совместимый код с сохранением расширенной схемы либо
восстановление всей базы из согласованной резервной копии. Постоянно
поддерживаемая параллельная реализация для этого не требуется.

## Последствия

Положительные:

- один исправляемый и проверяемый сценарий выполнения;
- одинаковое поведение ошибок, истории, команд и UI-команд;
- повтор HTTP-запроса не повторяет доменную операцию;
- полноэкранный интерфейс получает AG-UI без Copilot Runtime.

Стоимость и риски:

- требуется миграция для устойчивой записи запуска;
- до завершения переноса старый и новый endpoint временно существуют рядом;
- потоковая запись результата должна учитывать разрыв соединения;
- необходимы unit, integration и e2e проверки обоих native-представлений и
  контрактная проверка CopilotKit.

## Критерии приемки

- чужая, архивная и подмененная сессия недоступна без раскрытия ее данных;
- повтор одинакового `(session_id, run_id)` создает один пользовательский ход и
  один терминальный результат и не повторяет инструмент;
- `threadId` совпадает с подписанным `session_id`;
- события имеют правильный порядок и ровно одно терминальное событие;
- позднее событие старого запуска не меняет выбранную пользователем сессию;
- команды разрешаются сервером, вложения проверяются и принадлежат сообщению;
- оба native-представления используют один reducer и endpoint выполнения;
- CopilotKit проходит тот же контракт `/ag-ui` без смены своей архитектуры;
- после инвентаризации вызовов старые endpoints и код удалены;
- документация, мониторинг и карта проекта обновлены.
