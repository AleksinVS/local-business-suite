# CROW как подключаемый OKF-модуль LBS Factory

**Статус:** предложенная архитектура для согласования. Не описание уже работающего модуля.
**Редакция:** 2026-10-21. **Основа LBS:** Factory v3.4, коммит `41c5450a53fdd0b8598a0c2ab8cdceaa3ed6535e`. **Основа CROW:** `crow-hq/llm-wiki-v2`, коммит `d1e03f4b71cd54b4bd6fad062ca5e488401b95a6`.
**Формат:** [OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md).
**Решение:** модульность с первого дня; прямое подключение LBS Source API к внутреннему хранилищу CROW — только при доказанной необходимости. Замена `MemorySourceObject` на CROW `raw` не утверждена.

## 1. Цель и смысл слова «модуль»

CROW отвечает за **интеллектуальное упорядочивание и поиск**: `summarize`, `route`, `match`, `consolidate`, `merge`, `relate`, `select`, а также собственное планирование/разделение каталогов, обработку таблиц и ревизии. В первом этапе используется штатный Python `Wiki` / `Steps=CROW`, максимально близкий к upstream.

LBS остаётся владельцем: идентичности и прав, определения разрешённой аудитории, политики обезличивания/допустимой передачи, общего Knowledge API, Git-канона и процедуры восстановления, подтверждений `working / needs_confirmation / confirmed` и бизнес-источников. Алгоритм CROW не является вторым владельцем *тех же* заметок; для выделенной области он действует как единственный активный исполнитель операций записи **под управлением LBS**.

Под «почти неизменённым CROW» понимается отсутствие переписывания его `Librarian`, `Researcher`, decision-моделей и логики `raw`/`revisions`. Основные изменения приходятся на LBS-адаптер и инфраструктуру безопасной записи. Локальный интеграционный патч upstream возможен только при найденном непреодолимом препятствии, оформляется отдельно и проверяется при обновлении upstream.

## 2. Инварианты

1. **OKF v0.2 обязателен с этапа 1** для новых и изменяемых модулем CROW концептов; старый корпус не объявляется соответствующим формату без проверки и миграции.
2. Один канон содержания знания — Markdown + Frontmatter под контролем LBS, в Git. На один путь/пространство **ровно один активный writer**. Индекс, реестр подтверждений и БД-карточки — восстановимые проекции.
3. CROW `raw` на старте сохраняется физически и функционально, но содержит **только уже проверенный и разрешённый для данной области обработки текст**. Файлы raw не добавляются в историю Git; они доступны лишь привилегированному сервису и входят в отдельную политику backup/retention.
4. Не требуется отдельная БД CROW, сетевой CROW API, универсальная шина, Object Storage, OpenFGA или переписывание `apps.memory`. Модульность логическая.
5. `MemorySourceObject`, `MemorySearchDocument`, `SourceObjectEnvelope` и существующие адаптеры сохраняются. Их замена raw отложена.
6. Запрещено подавать в CROW документы с несовместимыми ACL: CROW видит названия папок и содержание заметок без пользовательской предметной фильтрации.
7. Необязательное подтверждение знаний v3.4 не превращается в блокирующую очередь. Legacy `lifecycle: pending` нельзя раскрывать.
8. При выключении/замене CROW канонические страницы, источники и их ссылки доступны через LBS; отключение модуля не стирает данные.

## 3. Первый этап: один выделенный OKF-корпус, один writer

Рекомендуемая структура *одной тестовой области с одинаковым допуском*:

```text
data/knowledge_repo/                  # существующий Git-канон LBS
  org/
    sources/ ...                      # существующие заметки apps.memory, не переносим все сразу
    index.md                          # генерирует LBS; не авторитетен для CROW
    log.md                            # генерирует LBS из Git; не авторитетен для CROW
    crow/
      common/                         # граница единого допуска и корень отдельного OKF-bundle
        index.md                      # CROW, okf_version: "0.2"
        log.md                        # CROW, журнал изменений этого bundle
        raw/                          # CROW raw; игнорировать Git, защищённо резервировать
        <topic>/
          index.md
          <note>.md                   # ЕДИНСТВЕННЫЕ канонические страницы этой области
  users/ ...                          # личные знания LBS, не видны CROW
  schemas/ ...
```

В `data/knowledge_repo/.gitignore` исключить именно `org/crow/common/raw/` (и разрешённые дальнейшие raw-пути), **не исключать** заметки, `index.md` или `log.md`. Если raw находится внутри рабочего дерева Git, он всё равно не попадает в коммиты; отдельное физическое размещение raw через Source API — последующий вариант. Проверить `git ls-files` и политику резервного копирования. Обычная копия Git **не является полной копией источников CROW**.

CROW получает `bundle=.../org/crow/common`. CROW сохраняет не только `raw/`, но и `.archive/` (старые редакции заметок), `.llmw2/sync/` (курсоры синхронизации), а также журналы использования моделей при их включении. Все вспомогательные каталоги/файлы с содержимым или секретами исключаются из Git **по точечному allow/deny-списку** и индексирования; для них назначается отдельная политика хранения и backup. `previous_version` в заметках ссылается на `.archive/`, поэтому одного Git backup недостаточно для воспроизведения штатной истории CROW. Проверять и восстанавливать нужно связанный комплект Git + raw + archive + sync state. Доступ к native веб-серверу, CLI-записи и прямому файловому редактированию CROW для пользователей не предоставлять; вызывать штатную библиотеку только из доверенного локального `LbsCrowAdapter`. Встроенный `WikiStore.lock` CROW на Windows недостаточен для межпроцессного writer: **внешний адаптер** обязан держать общий кроссплатформенный `knowledge_repo_lock` LBS на весь цикл изменений, включая журнал и Git-коммит. Прочие писатели этого Git-канона используют ту же блокировку.

`common` не означает автоматически «публичный». У него есть явная однородная политика допуска. На первом этапе туда не попадают пользовательские, личные, чужого подразделения, закрытые/удалённые, `pending` и смешанные по ACL страницы. Если источник или результат требуют более закрытого уровня — не консолидация в `common`, а отказ/маршрутизация в другой разрешённый контур LBS. Несколько корпусов — только после тестов изоляции. **Не запускать CROW на всём `data/knowledge_repo` или на `org/`.**

Существующие заметки LBS вне этого поддерева остаются в существующем провайдере. LBS Knowledge API может объединять *разрешённые* результаты двух пространств. Перенос старых заметок в CROW — отдельная проверяемая миграция с сохранением `knowledge_id` и источников, а не скрытая повторная загрузка.

## 4. Контракты первой интеграции (логические, без новых микросервисов)

```text
LBS Knowledge API (единая точка для пользователей и агентов)
  ├─ LBS MemoryProvider (существующие пространства)
  └─ LbsCrowAdapter (только corpora с назначенным provider=crow)
       ├─ LBS Access + Privacy + Egress / аудит
       ├─ LBS Source Adapters → проверенный текст + Origin
       ├─ upstream llmw2.Wiki(cfg, steps=CROW)
       │    ├─ native raw / index / log / revisions
       │    └─ native summarize / route / match / merge / relate / select
       ├─ LBS Writer Guard → валидация OKF/ACL/изменений/commit
       └─ LBS projection sync → MemoryKnowledgeItem, MemorySearchDocument, FTS
```

Реализовать только необходимый вызов провайдера: `ingest_safe_source(source_ref, actor_ctx)`, `select_notes(question, actor_ctx)`, `get_note(note_ref, actor_ctx)` и техническое `reconcile()`. **Native `Wiki.ask` выдаёт итоговый ответ, а не список поисковых результатов**; поэтому для существующего `knowledge.search` использовать стабильный CROW `Steps.select(ctx, root, question)` с преобразованием `Note → LBS search hit`. При необходимости `Wiki.ask` можно отдельно предоставить как защищённый `knowledge.answer`. Это имена **проектируемого адаптера**, не upstream API. Пользовательские `knowledge.search/get/save_working/flag_confirmation/confirm` остаются фасадом LBS v3.4 и не зависят от CROW.

Контракт backend/модуля закрепить как `KnowledgeOrganizationProvider` (или как расширение действующего `KnowledgeProvider` без второго конкурирующего фасада). Регистрация provider по **корпусу**: `corpus_id → provider_code=crow|lbs`. Конкретная настройка deployment имеет одного активного writer на corpus_id. Не создавать универсальный SDK десяти методов до второго работающего провайдера.

### 4.1 Запись

1. LBS идентифицирует инициатора, корпус и источники; проверяет доступ и допустимость выдачи именно этому модулю/LLM.
2. Source Adapter получает исходник, извлекает/нормализует текст; единый privacy/secret gate по [10_CONTENT_PRIVACY_PIPELINE.md](10_CONTENT_PRIVACY_PIPELINE.md) готовит `SafeProjection` (body **и** title/display_ref/разрешённые метаданные). Проверка включает назначения `wiki_git`, `agent_context` и, если используется внешняя модель или классификатор, `external_llm`. Отказ безопасности → **нет вызова CROW**.
3. Для CROW обязательно задаётся стабильный `Origin(source, account, id, version, link)`. `version` должен учитывать версию исходника **и редакцию очистки/парсера**, иначе изменение privacy-профиля при прежнем внешнем `etag` может неверно распознаться как `unchanged`.
4. Адаптер под общим writer lock и **барьером чтения изменяемого корпуса** вызывает штатный `Wiki.ingest(...)` / `ingest_many(...)` для выделенного bundle. Все чтения этого корпуса через LBS и CROW во время записи ждут окончания либо временно отклоняются. Включение только общего writer lock не предотвращает чтение наполовину обновлённых заметок. CROW сам записывает raw, заметки, links, index и log.
5. **До публикации/коммита** LBS проверяет изменённые пути, отсутствие секрета/PII-политики в результате модели, правильный ACL и максимально закрытую классификацию, соответствие OKF, совместимые метаданные и idempotency. На новых заметках задаёт `knowledge_id`, `confirmation_state: working` (либо `needs_confirmation` при необходимости), `lifecycle: current`; сохраняет ключи CROW. При смысловом изменении `confirmed`-страницы прежнее подтверждение нельзя молча переносить на новое тело — указать необходимость повторного подтверждения. Регламентные правки, требующие предварительного разрешения, проходят отдельный защищённый путь.
6. Единственная LBS запись/commit в **тот же Git-канон** (добавление в Git только разрешённых путей; `raw`, `.archive` и `.llmw2/sync` не попадут в коммит), регистрация новых заметок в `MemoryKnowledgeItem` и индексе. Сбой индекса после успешного commit → `index_pending` и существующий retry/reconcile; источник истины остаётся Git. Повторный запуск по тому же `origin/version` не должен создавать вторую заметку.
7. При неудаче до Git-коммита исправить/откатить изменения **только выделенного CROW-поддерева**, не трогая чужие файлы и незакоммиченные изменения. При обнаруженной незавершённой операции корпус не выдаётся до восстановления. При успешном commit и неудаче индексации запрещено выдавать прежнюю индексную карточку как актуальную: до reconcile она помечается устаревшей либо корпус ограничивается в выдаче. Для падения процесса хранить маленький журнал операции; при перезапуске сравнить дерево с последним завершённым коммитом. Сиротские raw очищать лишь после проверки ссылок и политики хранения.

CROW пишет несколько файлов на операцию, его native запись **не является транзакцией**. Две дисциплины надёжности для MVP: глобальная блокировка на этапе записи и явное восстановление после частичной операции; нельзя обещать атомарность всего набора без теста аварийного восстановления.

### 4.2 Чтение/поиск

LBS Access определяет разрешённый корпус **до** передачи вопроса в CROW. Один CROW bundle изначально содержит только данные одной аудитории. Ответ, цитаты и ссылки публикуются через LBS Knowledge API; перед публикацией в групповой чат повторить проверку всей аудитории. Прямые `GET /note`, `GET /tree`, `/ask` upstream для корпоративных пользователей **не открывать**.

`CROW.select` не умеет самостоятельно применять ACL отдельных заметок. Если в одном bundle появятся разные ACL, **не включать** его до реализации безопасного scoped дерева/разделённых bundles и отрицательных тестов. LBS проверяет права на цитату при раскрытии, но поздняя проверка не заменяет запрет передачи чужих заголовков модели при поиске.

Текущий источник заметок в CROW (`sources: resource: /raw/...`) может быть восстановлен/прочитан штатным `WikiStore.read`. Ссылки на оригинал через `origin.link` / LBS `source_ref` открываются только через права источника.

### 4.3 Действующее хранилище LBS: минимальные изменения

- `MemorySourceObject` и существующий `SourceObjectEnvelope` не переносить; формировать из них CROW `Source` / `Origin`.
- Ввести регистрацию и индексацию новых файлов CROW через LBS-проектор: нынешний `memory_reconcile` **обходит только существующие карточки `MemoryKnowledgeItem`**, поэтому одного Git-коммита CROW недостаточно, чтобы новая заметка появилась в поиске.
- Изолировать `raw/`, `.archive/` и другие служебные каталоги от `_walk_knowledge_files()` и графового materializer: сейчас обход `org/**/*.md` **захватывает Markdown в `raw/` и `.archive/`**, даже если каталоги добавлены в `.gitignore`. Raw нельзя представлять как организационное знание и включать в `index.md`.
- Не использовать `write_knowledge_item_file()` как слепую перезапись CROW-страницы: его рендеринг сегодня заново собирает Frontmatter из модели и может потерять CROW `sources`, `id`, `tags`, `description`, `generated`. Сделать нормализатор/писатель, **сохраняющий неизвестные ключи**.
- Индексы `org/index.md` и `org/log.md` остаются LBS-проекциями, индексы/журнал **внутри** `org/crow/common` принадлежат CROW. Не запускать два генератора на одном `index.md` / `log.md`.
- В существующем чате `memory.remember/search`, LBS Access и обработчиках заданий провести через единый фасад только соответствующие корпуса; старый корпус и его поведение не ломать.

## 5. OKF v0.2: поддержка с первого этапа

Цель — **форматно-независимый от провайдера канон**. Каждый новый `<note>.md` — UTF-8, YAML Frontmatter с непустым `type`, Markdown body. Корневой `index.md` каждого OKF-bundle допускает `okf_version: "0.2"`; `index.md` — список ссылок, `log.md` — записи под заголовками ISO дат `## YYYY-MM-DD`. Дополнительные поля LBS и CROW не запрещены, неизвестные поля обязательно сохранять при редактировании. Проверять стандартным валидатором и CROW `llmwiki2 check`, плюс внутренние LBS-инварианты. Сама конформность OKF не обеспечивает ACL и подтверждение.

**Семантика `status` несовместима без адаптации:**

| Назначение | Файл OKF v0.2 | Действующая LBS / цель |
|---|---|---|
| Готовность для использования | `status: draft / stable / deprecated` | В действующей LBS `status: active/deleted/superseded`; при переходе это **внутренний** статус, не писать его в OKF `status` |
| Достоверность | `verified: [{by: human:<id>, at: ...}]` | `confirmation_state: working / needs_confirmation / confirmed`. Историческое `confirmed` — лишь при настоящем подтверждении |
| Закрытый системный поток | — | `lifecycle: current / pending`; старое `pending` никогда не становится доступным из-за преобразования |
| Тип сущности | `type: Note` | LBS `kind`, `knowledge_id` — дополнительные поля |
| Происхождение | `sources[].resource`, опционально `id`, `title` | Не смешивать с устаревшим `source_refs`; на переходе сохранять обе формы только как **один канон + вычисляемая проекция** |

В новом CROW bundle `status` может отсутствовать (OKF читает как stable) или иметь валидное значение. `stable` в OKF = пригодно для потребления, **не = подтверждено человеком**. Для неустановленной достоверности использовать `confirmation_state` и отсутствие `verified`. При смысловой правке прежняя отметка `verified` должна считаться относящейся к старой ревизии, а не к новому тексту. Связи `sources` по возможности снабжать стабильными `id` и точными версиями.

**Legacy LBS:** текущие страницы часто не имеют `type`, используют `status: active`, а сгенерированный `log.md` не имеет группировки по заголовкам `## YYYY-MM-DD`. Это не нужно «лечить» перезаписью всего репозитория в первом PR, но перед импортом старых страниц в CROW должны быть выполнены совместимая конверсия, сохранение стабильных идентификаторов, проверка ACL, ссылки и golden tests. Нельзя объявлять весь исторический bundle уже конформным OKF. Введение OKF на первом этапе — **обязательный gate для новых CROW-страниц и их export**, а не обещание, что все существующие исторические файлы приведены без миграции.

## 6. Классификация, подтверждения и raw

Проверку текста выполняет единая LBS-политика безопасности из [10_CONTENT_PRIVACY_PIPELINE.md](10_CONTENT_PRIVACY_PIPELINE.md). CROW получает **результат её применения**, не запускает параллельный механизм обезличивания. `MemorySourceObject` при этом сохраняется. Изменения обработки по версии политики учитываются в `Origin.version`/`source_ref`, до помещения raw и до обращения к облачным моделям.


- CROW сырой исходник после очистки сохраняет как `raw`. Это его служебное свидетельство, **не принятая Wiki-страница**. `raw` даже без PII может содержать коммерческую тайну; его ACL не ниже источника/разрешённого корпуса.
- Один `origin.id` = одна логическая сущность источника, `origin.version` = конкретная подготовленная версия; содержимое CROW raw в точности соответствует *допущенному* `safe_text`. Зафиксировать версию правила обработки и хеш этого текста.
- Для персональных данных, для которых обезличенное представление нельзя безопасно получить, не делать запись ни в `raw`, ни в Git.
- Обычный новый материал сразу становится `working`, может быть помечен `needs_confirmation`, но не ждёт человека. Если CROW вносит содержательную правку в ранее подтверждённую страницу, нужен новый статус достоверности/подтверждения либо ограничение такой операции; официальные регламенты защищаются отдельной политикой.
- Подтверждения, снижение классификации и расширение аудитории не осуществляются автоматически CROW.
- Git-история и журнал CROW не заменяют аудит LBS и не должны хранить raw персональные данные.
- При удалении/отзыве доступа к источнику прекратить выдачу производных материалов, проверить ссылки и знание; обычное `CROW.mark_removed` оставляет заметки и **само по себе недостаточно** для корпоративного отзыва доступа.

## 7. Безопасное обновление и замена CROW

CROW — *provider*, а не новый стандарт хранения. Пользовательские страницы доступны по `knowledge_id` и OKF-пути даже при `provider=crow disabled`. В данных не использовать ID, требующие CROW runtime для разрешения: сохранять `knowledge_id`, `origin`, версии и ссылки на исходник. Дополнительное `id` CROW допустимо как алиас; не делать его единственной корпоративной идентичностью.

При отключении: остановить новые работы/исходящие вызовы CROW, сохранить Git, raw и архивы, продолжать чтение через LBS; интерфейс не должен для базового чтения Markdown вызывать upstream CROW. для записи назначить альтернативного провайдера **только после** проверки, что он понимает OKF, источники и иерархию. На namespace ровно один writer; no split-brain и «горячего» одновременного редактирования.

**Смена провайдера:** инвентаризация → архив/backup → dry-run импорт/проверка OKF → read-only сравнение выдачи, origin/citations/ACL → переключение единственного writer → rollback по известной ревизии. Сырые `raw` не удалять при переключении до миграции зависимых алгоритмов и проверки версий.

## 8. Будущая интеграция Source API (НЕ этап 1)

В этапе 1 **только договорённость о стабильном адресе источника**, без реального SourceBackend внутри CROW:

```yaml
sources:
  - id: src-1
    resource: /raw/20261021-policy.md   # нативный CROW путь, действителен в его bundle
    title: Внутренний регламент
    hash: "sha256:<prepared-content-hash>"
    origin:
      source: lbs
      account: "<installation>:<access_scope>"
      id: "<stable-source-id>"
      version: "<source-version+transform-version>"
      link: "<source-reference>"
    lbs_source_ref: "source:files:1254"
    lbs_transform_revision: "redaction-v2"
```

Пример — **проект соглашения** поверх допустимых дополнительных полей. Нативный CROW генерирует `source` из своего `raw` и `Origin`; LBS-адаптер может добавить `lbs_source_ref` при нормализации, **не меняя** алгоритм CROW. `resource` сейчас остаётся `/raw/...`, поэтому полная поддержка Source API в CROW в будущем **не сводится** к изменению одной настройки.

При измеренной проблеме объёма/версий/удаления/ACL внедрить за пределами этапа 1 порт чтения подготовленного содержимого и метаданных. Придётся адаптировать: `WikiStore.save_raw/read/find_origin/mark_origin_removed`, `OriginIndex`, `revisions.same_document`, `Researcher._with_rows`, удаление/GC ссылок и финальную запись заметок. Можно оставлять совместимые `/raw/...` aliases до завершения миграции. Тесты обязаны подтвердить одинаковый результат native-raw и Source-API режимов на одних источниках.

**Возможность заменить `MemorySourceObject` на raw остаётся альтернативой для дальнейшего ADR** и не входит ни в MVP, ни в обязательный путь к Source API.

## 9. Поэтапная реализация и оценки

| Этап | Минимальная работа | Точка контроля |
|---|---|---|
| **S0 / read-only** | inventory нынешней Wiki/БД, тесты формата OKF, анализ `raw`/`status`, ACL и лицензии | Нет тихого изменения существующих данных |
| **S1 / интеграция** | LBS gateway и единый writer lock; отдельный CROW bundle; safe_text intake; нативные origin/raw; OKF нормализация и проверка; importer/index; recovery | CROW работает практически штатно, не создаёт второй канон; два пользователя с разным допуском не видят чужих файлов |
| **S2 / эксплуатация** | сравнение качества маршрутизации и поиска, объём/backup raw, тесты аварий, измерение p95 | Решение сохранять CROW/менять provider/менять backend основано на наблюдениях |
| **S3 / условно** | Source API непосредственно внутри CROW и миграция raw, при необходимости несколько ACL-корпусов | Реализация только после отдельного ADR/метрик |

Не вводить до измерений: OpenFGA, векторную базу ради CROW, фоновый брокер, десятки новых моделей и собственный CROW fork. Источники CROW и LBS не индексировать автоматически дважды в одном поисковом канале.

## 10. Проверки приёмки (не декларативные)

1. `OKF v0.2`: `type` есть у каждой новой CROW-страницы, `sources` корректны, `index.md`/`log.md` валидны; неизвестные ключи сохраняются при merge и редакторе LBS.
2. Старый `status: active` никогда не ошибочно интерпретируется как OKF `stable` без совместимого преобразования; legacy `pending` закрыт.
3. Два автора не могут одновременно записывать один corpus; внешний CROW CLI и HTTP write-path недоступны.
4. В `raw` попадает только подготовленный текст; Git никогда не содержит raw, а отдельно заданный backup обеспечивает восстановление raw и ссылок.
5. `apps.memory` не индексирует `crow/.../raw/*.md` как знания и не перезаписывает CROW `index.md`/`log.md`.
6. Новая заметка видима через LBS Knowledge API и `MemorySearchDocument` после успешного Git-коммита; при аварии индекса данные восстанавливаются.
7. Падение между CROW `save_raw` и `write_note`/`relate`, а также между Git commit и индексацией не создаёт тихой потери/повторного применения.
8. Повторный ingest того же `origin/version/transform` идемпотентен; изменение политики очистки вызывает обработку заново.
9. Чужой заголовок/`index.md`/`raw` не попадает в classifier или LLM prompt; CROW не обслуживает смешанный ACL corpus.
10. Ответ в групповой чат проходит проверку адресатов; утечка через citations/source link запрещена.
11. Работа `working/needs_confirmation/confirmed` не блокируется обычным review; машинная правка confirmed не остаётся подтверждённой без новой проверки.
12. Отключение CROW сохраняет поиск/чтение его OKF-страниц через LBS; повторное включение и смена провайдера не переписывают канон.
13. Git restore/backup восстанавливает канон, отдельный raw backup восстанавливает исходные подготовленные свидетельства, `reconcile` возвращает индекс.
14. Изменения CROW-upstream проходят контрактные/regression-тесты перед обновлением pinned version.
15. Лицензия AGPL-3.0-or-later оценена до коммерческого включения исходного кода; при необходимости выбран разрешённый способ распространения/коммерческая лицензия.

## 11. Риски, которые нельзя скрывать

- Native CROW **сам пишет несколько файлов и не предоставляет общей транзакции**. Внешние блокировка, **барьер чтения** и восстановление обязательны, хотя сам алгоритм не меняется.
- CROW на полном корпоративном дереве без ACL-фильтра перед классификатором небезопасен. Однородный отдельный bundle — ограничение MVP, не признак, что решены будущие произвольные page-level ACL.
- Проекция LBS из нового CROW-формата **не реализована** в текущем `memory_reconcile`. Потребуется явная импортная логика.
- Native `raw` и `.archive` остаются физическими копиями и резервируются отдельно; сокращение дублирования откладывается. При публикации Git-копии без `raw/.archive` результат остаётся **OKF-совместимым по структуре, но не самодостаточным по источникам/истории**. Для переносимого экспорта нужны включённые разрешённые исходные версии либо проверяемая схема их разрешения через LBS Source API.
- Непроверенные результаты CROW могут менять смысл заметок, а программа автоматического подтверждения не существует. `confirmation_state`/provenance и политики официальных знаний нельзя обходить.
- Старые LBS файлы ещё не полностью соответствуют OKF. Поддержка стандарта с первого этапа = валидные новые документы + план и тесты совместимой миграции, а не заявление о готовой конформности всего архива.
