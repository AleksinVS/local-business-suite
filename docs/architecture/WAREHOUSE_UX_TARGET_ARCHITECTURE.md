# Целевая UX-архитектура склада и автодополнения портала

- Статус: Approved for implementation
- Дата: 2026-09-02
- ADR: ADR-0049, ADR-0050; сохраняются инварианты ADR-0047
- План: `docs/planning/active/warehouse-ux-simplification.md`
- Workflow: `workflow/active/warehouse-ux-simplification/`

## 1. Цель

Свести обычную складскую работу к двум основным экранам:

1. список остатков с фильтрами, быстрым расходом и режимом перемещения;
2. список документов, из которого создание, просмотр и редактирование открываются
   в правой панели.

Пользователь не должен заранее создавать серию, искать служебный номер строки,
заполнять поля другой операции или загружать многотысячный справочник в
`select`. Значение, которое система уже знает из контекста, заполняется
автоматически и остаётся видимым пользователю.

## 2. Принципы интерфейса

1. Одна задача — одна рабочая поверхность. Форма не показывает поля, которые не
   участвуют в выбранной операции.
2. Растущие справочники и связи выбираются автодополнением.
3. Серия допускает свободный ввод; существующие значения являются подсказками,
   а не обязательным справочником.
4. Строки документа редактируются в таблице.
5. Подразделение, дата, единица, срок существующей серии, доступный остаток и
   адреса заполняются из контекста, когда выбор однозначен.
6. Сохранение и проведение выполняются по явной кнопке без дополнительного
   диалога подтверждения.
7. Любое автозаполнение можно понять: рядом отображается источник значения или
   доступное пользователю поле изменения.
8. Клиент ускоряет ввод, но не является границей доверия. Все права,
   совместимость полей и остатки повторно проверяются сервером.

## 3. Информационная архитектура

### 3.1 Главный экран «Склад»

Верхняя строка содержит:

- автодополнение подразделения, если пользователю доступно больше одного;
- основные вкладки `Остатки`, `Документы`, `Отчёты`, `Настройка склада`;
- действия `Приход`, `Выдача`, `Новый документ` согласно правам.

Под основной навигацией показываются компактные показатели:

- общий доступный остаток;
- позиции с истекающим сроком по каждому настроенному порогу;
- просроченные позиции;
- карантин и неразобранные адреса.

Показатели являются фильтрами списка, а не отдельными тупиковыми карточками.

### 3.2 Остатки

Фильтры:

- подразделение;
- склад и адрес;
- позиция;
- категория;
- источник финансирования;
- серия;
- диапазон или группа срока годности;
- состояние адреса.

Все растущие значения используют общее автодополнение. Фильтр хранится в URL,
поэтому представление можно обновить и передать без потери состояния.

Таблица по умолчанию группирует повторяющееся подразделение и показывает:

- выбор строки;
- позицию;
- серию;
- срок;
- источник;
- склад / адрес;
- доступное количество с форматированием единицы;
- предупреждение о сроке.

Данные выводятся постранично на сервере. Ограничение `[:200]` без сообщения
пользователю запрещено.

### 3.3 Документы

Список поддерживает фильтры по подразделению, периоду, типу, статусу, номеру,
позиции и серии. Клик по строке открывает карточку справа. Кнопка создания
открывает там же новый документ.

Черновик можно редактировать. Проведённый документ открывается только для
просмотра и разрешённых действий сторно. В списке используются различимые
статусы, автор, дата изменения и число строк.

### 3.4 Отчёты

Каждый отчёт имеет видимые фильтры и русские пользовательские столбцы. Внутренние
`*_id` не показываются. CSV и XLSX используют тот же набор фильтров и данных,
что экран.

`WarehouseReportProfile` сохраняется. Профиль выбирается сервером по одному
подразделению и дате отчёта; реквизиты не импортируются из legacy.

## 4. Общий компонент автодополнения

### 4.1 Граница ответственности

```text
Общий компонент UI
  -> общий безопасный HTTP-контракт
    -> зарегистрированный доменный provider
      -> domain selector / policy
        -> ограниченные варианты
```

`apps.core` не импортирует бизнес-модели. Каждый домен регистрирует поставщиков
и использует свои selectors/policies.

### 4.2 Режимы

`entity`:

- видимое поисковое поле + скрытый идентификатор;
- введённая подпись без выбора не считается значением;
- серверная форма повторно использует разрешённый queryset.

`suggestion`:

- видимое поле является отправляемым значением;
- пользователь может выбрать подсказку или оставить новый текст;
- метаданные выбранной подсказки могут заполнить зависимые поля;
- сервер нормализует и валидирует итоговый текст.

### 4.3 Контракт поставщика

Поставщик объявляет:

- стабильный `provider_code`;
- разрешённые контекстные параметры;
- режим и минимальную длину строки;
- `search(actor, query, context, limit)`;
- безопасное представление `label/secondary/metadata`.

Контекст передаёт только необходимые идентификаторы, например выбранное
подразделение или позицию. Поставщик заново проверяет их видимость.

### 4.4 Производительность и доступность

- задержка 180–250 мс;
- отмена устаревшего запроса;
- не более 20 вариантов;
- индексы по фактическим поисковым полям;
- целевой p95 ответа на пилотной PostgreSQL-базе — до 300 мс;
- `Cache-Control: private, no-store` для вариантов, зависящих от пользователя;
- полная работа клавишами и с экранным диктором по WAI-ARIA combobox;
- повторная инициализация после HTMX swap без двойных обработчиков.

## 5. Табличный редактор документа

### 5.1 Правая панель

Панель получает размер `workspace`: на широком экране занимает достаточно места
для таблицы, на ширине до 960 px становится полноэкранной.

Структура:

- закреплённая шапка: тип, подразделение, дата, номер;
- прокручиваемая таблица строк;
- компактный комментарий и причина только там, где они нужны;
- закреплённый подвал с `Отмена`, `Сохранить черновик`, `Провести`.

Во время запроса кнопка блокируется и показывает состояние. Ошибка строки
отображается в её ячейке и не сбрасывает остальные строки.

### 5.2 Строки

Общие правила:

- `sequence` скрыт и вычисляется сервером;
- первая пустая строка доступна сразу;
- новая строка добавляется кнопкой или клавишей в конце последней строки;
- удаление помечает строку без немедленной серверной записи;
- выбор позиции заполняет единицу и точность;
- количество проверяется по точности единицы;
- копирование и вставка нескольких строк допускается отдельным последующим
  улучшением, но не блокирует первый срез.

Приход:

- позиция — `entity` autocomplete;
- серия — `suggestion` autocomplete по выбранной позиции;
- срок — заполняется при выборе серии или вводится для новой;
- источник и целевой адрес — `entity` autocomplete;
- если адрес в подразделении один, он заполняется автоматически.

Выдача:

- после позиции предлагаются только доступные остатки;
- подпись варианта показывает серию, срок, источник, адрес и количество;
- варианты сортируются FEFO;
- выбор заполняет серию, срок, источник и исходный адрес;
- количество не может превышать доступное на момент проведения.

## 6. Серия без отдельного справочника

Целевые поля:

| Сущность | Поля | Назначение |
| --- | --- | --- |
| `StockDocumentLine` | `item`, `series`, `series_key`, `expires_on`, `incomplete_reason` | ввод и проверка черновика |
| `StockEntry` | прямой `item` и те же значения | неизменяемый исторический снимок |
| `StockBalance` | прямой `item` и те же значения в ключе проекции | остаток и подсказки |

Поставщик `warehouse.series` выполняет `distinct` по видимым проводкам и
остаткам выбранной позиции. Он не создаёт запись при поиске или выборе.

Ключ проекции:
`department + warehouse + location + item + series_key + expires_on + funding_source`.

При расхождении срока у одной нормализованной серии:

- новая штатная операция блокируется понятным сообщением;
- импорт создаёт issue с исходными значениями;
- исправление выполняет контролёр через корректирующую операцию, а не изменение
  проведённой проводки.

## 7. Режим перемещения

### 7.1 Клиентский сценарий

После включения режима в таблице появляются флажок и поле количества. Поле
доступно только выбранной строке. Панель действий показывает число строк и сумму
в единицах только там, где единицы совместимы.

`Переместить` открывает правую панель с:

- кратким списком выбранных остатков;
- автодополнением склада назначения;
- автоматически выбранным адресом приёмки;
- одним дополнительным полем адреса, только если однозначного default нет;
- кнопкой `Сохранить перемещение`.

`Warehouse.default_receiving_location` ссылается только на собственный активный
адрес `available`. Он заполняется миграцией лишь при единственном допустимом
адресе и редактируется администратором склада. Неоднозначный адрес по умолчанию не
угадывается.

### 7.2 Серверная команда

Команда принимает идентификаторы проекций и количества, но не доверяет им. В
транзакции она:

1. повторно разрешает строки через scoped selector;
2. блокирует остатки в стабильном порядке;
3. проверяет количество, подразделение и назначение адресов;
4. создаёт многострочный `StockDocument(RELOCATION)`;
5. сразу проводит документ;
6. возвращает идентификатор документа и событие обновления списка.

Частичное проведение запрещено: либо перемещены все выбранные строки, либо ни
одна. Отдельного подтверждения после кнопки сохранения нет.

## 8. Предлагаемые HTTP-границы

Точные имена допускается уточнить без изменения контракта:

- `GET /ui/autocomplete/<provider>/` — общий транспорт вариантов;
- `GET|POST /warehouse/documents/new/panel/`;
- `GET|POST /warehouse/documents/<id>/edit/panel/` только для черновика;
- `GET /warehouse/documents/<id>/panel/`;
- `GET /warehouse/stock/` — фильтруемый список;
- `POST /warehouse/relocations/panel/` — подготовка панели по выбранным строкам;
- `POST /warehouse/relocations/` — атомарное создание и проведение.

POST возвращает HTML формы при ошибке. Успех использует согласованные
`HX-Trigger`: `warehouseDocumentsChanged`, `warehouseStockChanged`,
`rightPanelClose`.

## 9. Права

Новые возможности не расширяют существующие роли:

- просмотр вариантов использует тот же scope, что целевой список;
- создание и редактирование черновика требует `warehouse_operate_scope`;
- списание, корректировка и сторно требуют `warehouse_adjust_scope`;
- быстрый режим перемещения требует операционного scope на подразделение;
- каталог, склады, адреса и профили сохраняют административные capabilities.

Autocomplete никогда не возвращает недоступные, архивные или непригодные для
операции значения.

## 10. Портальный охват автодополнения

До приёмки составляется файл-матрица со всеми пользовательскими формами:

- `accounts`, `core`, `settings_center`;
- `inventory`, `workorders`, `waiting_list`, `warehouse`;
- `filehub`, `memory`, `analytics`, пользовательские формы `ai`;
- `notifications`, если в форме есть растущие бизнес-связи.

Для каждого поля фиксируются тип, поставщик, зависимый контекст, scope,
минимальная строка, резервное поведение и тест. Административный Django UI не
считается основным пользовательским интерфейсом, но его собственные безопасные
виджеты не удаляются.

## 11. Критерии готовности

- нет пользовательского экрана регистрации серии;
- в основных формах нет нативного `select`, загружающего растущий справочник;
- документ с несколькими строками создаётся и исправляется в правой панели;
- поля другой операции не показываются;
- серия допускает новый текст и предлагает существующие значения;
- перемещение выполняется из отфильтрованного списка и создаёт один проведённый
  документ;
- отчёты имеют видимые фильтры и пользовательские столбцы;
- количество форматируется по точности единицы;
- desktop и ширина 390 px не имеют обрезанных обязательных действий;
- security, миграционная сверка, concurrency и e2e проходят согласно workflow.
