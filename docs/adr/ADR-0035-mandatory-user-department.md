# ADR-0035: Обязательное подразделение пользователя

- Статус: Accepted
- Дата: 2026-08-05

## Контекст

`User.department` участвует в ограничении `department_branch`, но исторически
допускал `NULL`. В локальной PostgreSQL-базе 17 из 24 пользователей не имеют
подразделения. Требуется сделать связь обязательной без случайного расширения
доступа к заявкам.

Корневое подразделение-агрегатор «Вологодская областная больница №3» нельзя
использовать как автоматическое значение для старых пользователей: его ветка
может охватывать значительную часть организации.

## Решение

1. `User.department` становится `null=False`, `blank=False`, `on_delete=PROTECT`.
2. Data migration создаёт под корневым агрегатором дочернее подразделение
   «Не назначено — требуется уточнение» и переносит туда пользователей с `NULL`.
3. Карантинное подразделение не предлагается как допустимый выбор в формах
   создания и изменения учётной записи. Администратор обязан выбрать реальное
   подразделение.
4. Программное создание пользователя без подразделения сохраняется для AD,
   служебных команд и тестовых контуров, но модель назначает такой записи
   карантинное подразделение. Это fail-closed поведение: ветка не содержит
   рабочих подразделений и не расширяет видимость заявок.
5. В списке и карточке доступа карантинное назначение показывается явным
   предупреждением.

## Рассмотренные альтернативы

### Назначить всем корневой агрегатор

Отклонено: для `department_branch` это может расширить доступ до всей ветки.

### Остановить миграцию при наличии `NULL`

Отклонено: безопасно, но блокирует автоматическое развёртывание и не даёт
администратору интерфейсной очереди на исправление данных.

### Оставить `NULL`, проверять только форму

Отклонено: другие пути создания пользователей сохраняют несогласованные данные,
а инвариант не обеспечивается базой.

## Последствия

- подразделение нельзя удалить, пока на него ссылается пользователь;
- существующие нераспределённые пользователи не получают дополнительного доступа,
  но требуют ручной классификации;
- AD/Remote User может создать пользователя до настройки OU-маппинга, однако
  такой пользователь останется в карантинной ветке;
- миграция должна проверяться на SQLite и PostgreSQL;
- операционная документация должна описывать очередь пользователей в карантине.
