# Архитектура проектной вики с агентом и CROW

Основной агент ведёт тематические статьи в Markdown. Навык задаёт ему правила работы со знаниями. CROW помогает искать статьи, классифицировать изменения, обрабатывать исходные документы, выявлять противоречия и поддерживать структуру вики. Для функций, которые CROW уже предоставляет в удобном для агента виде, достаточно штатного вызова. Целевой формат статей — Open Knowledge Format (OKF) v0.3; чтение прежних v0.2 сохраняется. Фактическая версия записи конкретного проекта зависит от совместимости подключённых инструментов.

**Редакция концепции: 26 ноября 2026 года, уточнение OKF v0.3.** Возможности сверены с [CROW 1.0.5](https://github.com/crow-hq/llm-wiki-v2/tree/v1.0.5). Установленную версию и подключённые операции каждый проект фиксирует отдельно. Переход CROW с 1.0.1 на 1.0.5 не меняет роли. Сам CROW 1.0.5 ещё использует OKF v0.2; переименование версии в индексе не делает его писателем v0.3. Нормативный ориентир: [OKF v0.3](https://github.com/open-knowledge-format/open-knowledge-format/blob/527e81aff55992be21507e97004286789126f88c/SPEC.md), [объявление от 18 ноября](https://cloud.google.com/blog/products/data-analytics/introducing-okf-v0-3).

## Роли и границы

| Компонент | За что отвечает |
| --- | --- |
| Основной агент | Понимает контекст работы, читает статьи и первоисточники, решает, что изменилось в знаниях. Готовит и проверяет законченный набор правок, включая связанные статьи, ссылки и индекс затронутого раздела. Одно расследование может уточнить несколько статей. |
| Навык работы с вики | Определяет, когда искать знания, что заслуживает записи и как проверять статьи. В проекте к нему добавляют путь к вики, доступные инструменты и способ сослаться на источник. |
| CROW | Ищет статьи, принимает исходные документы, предоставляет классификатор, указывает на возможные расхождения, предлагает и выполняет переносы. Работает с тем же набором статей, который редактирует агент. |
| Адаптер, если нужен | Делает конкретную возможность доступной агенту. Например, превращает типизированный запрос к Python-классификатору в одну операцию агента. Его можно заменить, сохранив файлы вики и правила навыка. |

Для запуска достаточно одного агента с навыком, файлового редактора и штатной поставки CROW. Отдельный сервис публикации в этой схеме не требуется. Если модель классификации недоступна, агент продолжает работу через поиск BM25, чтение и прямую редактуру.

## Способ подключения CROW

| Условия проекта | Подключение |
| --- | --- |
| Агенту доступен весь выбранный корпус; достаточно штатных операций | Штатный MCP CROW над каталогом вики совместимой с ним версии. Клиент может запускать его через stdio; изменяющие операции для v0.3 допустимы только после проверки совместимости. Агент читает найденные страницы и редактирует Markdown обычным редактором проекта. |
| Нужна отдельная классификация правки или проект ограничивает набор доступных статей, источники либо порядок записи | Тонкий адаптер к нужным Python-компонентам CROW. Он принимает только допущенные проектом данные и возвращает результат конкретной операции. Штатные операции, для которых адаптация не нужна, остаются доступными напрямую в разрешённой области. |

Оба варианта используют один канон статей и одни правила авторства. Для v0.3 нативный доступ CROW к записи открывается только после проверок из раздела о совместимости ниже; доступ к поиску/классификатору по уже прочитанным допущенным статьям не требует изменения формата движка. Наличие MCP-инструмента `remember` не меняет выбор пути: подготовленный агентом набор статей сохраняется напрямую; штатная обработка CROW применяется к исходному материалу, который ещё нужно разобрать. Это правило закрепляется в навыке проекта рядом с описанием доступных инструментов.

В 1.0.3–1.0.4 исправлен первый запуск MCP без сохранённых настроек и создание пустой вики. При отсутствии настроек CROW передаёт модельные запросы клиенту; существующая конфигурация сохраняет свой приоритет. Режимы `client` и `hybrid` существовали уже в 1.0.1. В `hybrid` модель клиента пишет, а настроенный классификатор принимает решения, но маршрутизацией, слиянием и записью по-прежнему управляет CROW. Этот режим можно использовать для штатной обработки исходников независимо от прямой авторской редактуры. [Запуск MCP](https://github.com/crow-hq/llm-wiki-v2/releases/tag/v1.0.3) · [Пустая вики](https://github.com/crow-hq/llm-wiki-v2/releases/tag/v1.0.4) · [Модели клиента](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.5/docs/wiki/memory.md#which-models-do-the-work)

Если проект ограничивает доступ, он проверяет права до передачи текста CROW или модели. Параметр `where` фильтрует заметки по полям и не является проверкой прав. Аннотация MCP `openWorldHint: false` описывает область действия инструментов; она не обеспечивает разграничение доступа или локальное выполнение модели. [Ограничения MCP](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.5/docs/wiki/memory.md#more-than-one-wiki) · [Аннотации 1.0.5](https://github.com/crow-hq/llm-wiki-v2/releases/tag/v1.0.5)

## Два пути в одну вики

**Агент уже исследовал вопрос.** Он ищет существующие объяснения, открывает полные тексты и при необходимости переходит по ссылкам за пределы поисковой выдачи. Затем правит нужные файлы обычным редактором проекта. Уточнение существующей темы попадает в соответствующий раздел. Самостоятельный вопрос может получить новую статью. Если сведения уже описаны, агент завершает задачу без записи. Отправлять готовую статью в `remember` или `ingest` означало бы поручить CROW повторный синтез и выбор места для уже адресованной правки.

**Поступил исходный документ.** Например, вышла новая редакция инструкции, которую агент ещё не разбирал. Документ передают в штатный `Wiki.ingest`. Для повторного импорта полезно передать устойчивый идентификатор и версию источника через `Origin`. CROW сохраняет подготовленный исходник, выбирает тему и создаёт либо дополняет заметку. При обычном импорте текста CROW формирует одного основного кандидата. Если документ меняет несколько самостоятельных тем, агент может дочитать оригинал и уточнить остальные статьи напрямую. При настройке синхронизации входную папку с документами держат отдельно от выходной вики.

## Правила для навыка автора

Этот раздел можно перенести в инструкции агента. Достаточно указать местоположение вики и принятый в проекте способ сохранения.

1. Перед существенной работой найди прежние решения по теме. Открой подходящие статьи и проверь, для какой версии или ситуации они написаны.
2. Пока у тебя есть контекст задачи, сформулируй вопрос следующего читателя. Что он сможет понять, проверить или сделать благодаря новому знанию? Статус выполнения и ход сеанса оставь в задаче. Частный, воспроизводимый вывод стоит сохранить с явным условием применимости.
3. Найди все темы, ответ в которых изменился. Используй поиск, ссылки и при необходимости классификатор. Можно выбрать статью за пределами предложенного списка. Перед заменой целого раздела дочитай его и сохрани прежние выводы, которые по-прежнему верны.
4. Запиши вывод своими словами и приложи проверяемое основание — версию инструкции, тест, измерение или конкретный фрагмент источника. Обозначь, где вывод проверен и что остаётся гипотезой. Добавляй ссылку на соседнюю статью, когда она помогает применить вывод.
5. Перечитай результат глазами участника, который не видел задачу. Проверь весь набор своих правок, основания и переходы. При пересечении с чужой правкой изучи diff и необходимый текущий контекст, сохрани чужие изменения и согласуй смысл. Полное повторное чтение нужно лишь при существенной переработке или нехватке контекста. Если правки нельзя совместить, сообщи о конфликте и сохрани обе версии. Чужие незавершённые изменения оставь их владельцу. Если повторное наблюдение ничего не добавило, оставь вики без изменений.

**Пример.** Сообщение «повторно загрузили файл, проверка прошла» остаётся в журнале задачи. Если тест установил, что повтор безопасен только при сохранении внешнего идентификатора, а инструкция предлагает создать новый, меняются две статьи. В «Повторной загрузке» агент добавляет условие и ссылку на тест. В «Идентификаторах» исправляет правило для повторной отправки. Следующий участник найдёт ответ независимо от того, с какой темы начнёт поиск.

## Параллельная работа авторов

Для параллельной работы принята проверка конкретных статей. Полные Markdown-статьи и их история в Git остаются каноном. Агенты готовят правки вне общей блокировки, в своих разрешённых рабочих областях или в памяти. Исходный Git SHA задаёт снимок для чтения и сравнения. Автор указывает изменяемые, создаваемые и удаляемые пути, а также статьи-основания, от которых зависит правка, даже если их текст не меняется. Версии должны соответствовать фактически прочитанным файлам: используется согласованный снимок либо учитывается прочитанная ревизия каждой статьи отдельно.

Перед фиксацией под общей блокировкой записи проверяются права и версии этих файлов целиком, включая метаданные. Изменение других статей не мешает принять подготовленные правки поверх текущего дерева Git с сохранением уже зафиксированных изменений. Если изменился значимый файл, операция возвращает конфликт: автор либо уполномоченный агент с целью правки и основаниями изучает diff и нужный контекст, согласует содержание. Полное повторное чтение требуется лишь при существенной переработке или недостатке контекста. Простая замена исходного SHA без учёта изменений не разрешает конфликт. Гарантия свежести оснований распространяется на явно указанные статьи.

Для создания проверяется, что новый путь по-прежнему свободен и ID не занят. При переносе проверяются старый и новый пути, сохраняется ID. Перед переносом или удалением входящие ссылки проверяются по текущему дереву; статьи, требующие исправления ссылок, включаются в проверяемый набор. Недоступные или изменившиеся статьи нельзя молча перезаписать.

Индексы затронутых разделов и `log.md` актуализируются из текущего дерева под той же блокировкой с сохранением уже принятых записей. После проверок, до освобождения блокировки, хост фиксирует один коммит только с изменениями завершённой операции, не захватывая чужие незавершённые правки. При пустом результате коммита нет. Объединение файлов не подтверждает совместимость утверждений: смысловые расхождения автор разрешает по источникам согласно правилам выше.

### Внешние авторы без CROW

В доверенном проектном корпусе достаточно отдельной рабочей копии Git, навыка автора, `git grep` и чтения Markdown. Агент готовит обычный diff, фиксирует свои изменения и применяет штатный процесс слияния проекта без принудительной перезаписи общей ветки. Перед слиянием сверяет изменения затронутых статей; если Git объединяет непересекающиеся строки, автор всё равно учитывает значимые изменившиеся условия. Нет необходимости регистрировать каждый прочитанный файл или вызывать модель перед каждым коммитом. При управляемом доступе через хост сохраняются проверки прав и оснований; прямой Git-доступ разрешён только участникам, которым допустимо видеть весь репозиторий и его историю. Обычный `merge` не обеспечивает проверку актуальности всех смысловых зависимостей.

### Фоновая проверка смысла

Отдельно от механической защиты записи полезен необязательный периодический аудит: изменившиеся статьи сопоставляются с ограниченным набором релевантных разрешённых соседей. Проверки CROW/decision-модели дают замечания с версиями статей, а не обязательный барьер или автоматическое переписывание. Сравнение по запросу остаётся доступным. Исправление выполняет уполномоченный автор по источникам обычной правкой. Недоступность модели не блокирует чтение или запись; аудит не гарантирует обнаружения всех противоречий и не заменяет защиту от потери текста.

## Инструменты CROW и основания для адаптера

| Задача | Штатная возможность CROW 1.0.5 | Что делает агент или адаптер |
| --- | --- | --- |
| Найти и прочитать | `Wiki.search` или MCP-инструмент `search` находит кандидатов по содержанию. MCP-инструмент `read_note(path)` возвращает полный текст. Для обычного поиска BM25 модель не нужна. | Агент может сразу пользоваться MCP или читать найденный Markdown с диска. |
| Классифицировать предлагаемую правку | Python-класс `llmw2.Classifier` предоставляет отдельные вызовы `choice`, `nouls` и `ask`. Готовой MCP-команды для классификации произвольной правки в этой версии нет. | Если нужна отдельная операция, адаптер передаёт формулировку вывода и фрагменты найденных статей. Например, предлагает для каждой статьи варианты «уже описано», «дополняет», «возможное противоречие» и «данных недостаточно». Возвращает подсказку без записи. При неоднозначном результате агент дочитывает источники. |
| Обработать исходный материал | `Wiki.ingest` принимает документ и его происхождение. MCP-инструмент `remember(text, title?)` запускает штатную обработку текста. | Источник можно передать напрямую. Адаптер полезен, если проекту нужно получить конкретную версию из внешней системы или подготовить документ в читаемом виде. |
| Найти и устранить противоречие | При подготовке ответа по нескольким заметкам штатная проверка `ask/conflict` может указать расходящиеся утверждения. Для новой версии одного источника предусмотрено обновление при выполнении условий CROW. | Для явной проверки двух фрагментов можно вызвать классификатор через тот же адаптер. Агент сравнивает версии, даты действия и область применения. Если обе нормы верны в разных условиях, уточняет обе статьи. Если источник подтверждает замену, исправляет действующую норму. Когда оснований мало, сохраняет обе позиции и открытый вопрос. |
| Перестроить вики | `Wiki.audit_routes(apply=False)` с настроенным классификатором предлагает переносы. `move_note` перемещает заметку в существующий раздел и обновляет ссылки. | Для переноса агент может вызвать штатную команду, если она совместима с версией формата и не теряет метаданные, ссылки и заменяющие страницы; иначе применяет обычную авторскую правку. Для смыслового разделения или объединения он сам редактирует тексты, распределяет основания и проверяет входящие ссылки. |

## Описания инструментов для агента

Описание каждой доступной операции указывает, что она делает, когда нужна, что возвращает, какие данные изменяет и при каких условиях отказывает. Это часть интерфейса агента: навык задаёт общий порядок работы, а описание помогает выбрать действие в конкретный момент. Такой подход принят в [MCP CROW 1.0.5](https://github.com/crow-hq/llm-wiki-v2/releases/tag/v1.0.5).

| Операция | Что должно быть понятно из описания |
| --- | --- |
| Поиск | Возвращает кандидатов в разрешённой области. Для правки агент затем открывает полную статью и проверяет основания. |
| Чтение | Возвращает текст; сведения о версии, нужные для последующей записи, агент получает средствами проекта. Переход по ссылке требует такой же проверки доступности, как поиск. |
| Классификация или сравнение | Возвращает отношение между утверждениями и доступную оценку модели. Ничего не записывает. Неуверенность или недоступность модели позволяют продолжить чтение и редактуру без подсказки. |
| Прямая редактура | Сохраняет подготовленные агентом статьи выбранным в проекте способом. Описание объясняет проверку исходной версии, последствия удаления, фиксацию изменений и поведение при конфликте или повторе операции. |
| Импорт или перестройка | Явно обозначает, что запускает модельную обработку либо меняет файлы и ссылки. `rebuild` восстанавливает из исходников и не служит способом сохранить авторскую правку. |

Конкретные имена и параметры берутся из доступных средств проекта. Эта таблица не требует отдельного сервиса записи или нового набора команд, если штатные инструменты уже выполняют нужную работу.

## Профиль OKF v0.3

Профиль — правила применения формата проектом, а не ещё один движок. [Спецификация §3–§13](https://github.com/open-knowledge-format/open-knowledge-format/blob/527e81aff55992be21507e97004286789126f88c/SPEC.md) сохраняет Markdown и YAML, не вводит обязательную БД, схему типов, онтологию или API. Два несовместимых изменения относительно v0.2: разрешение относительных полей-путей и учёт только актуальных подтверждений. Дополнительно появились замена устаревшей статьи, метаданные раздела и гарантированный префикс расширений. Остальные уточнения учитываются в простом чтении и записи.

### Статус, доверие и актуальность

Это три независимых признака:

- `status` (отсутствует → `stable`): действующее знание. `draft` — незавершённый материал, `deprecated` — исторический. Неизвестное значение не считается действующим; сохраняется как есть. `active` остаётся внутренним термином приложения. Обычная статья не требует человеческого согласования.
- `generated: {by, at}` фиксирует реального автора/производителя и время последнего смыслового изменения. При создании или смысловой правке обновляется; перенос без изменения смысла, форматирование, исправление технических ссылок и добавление подтверждения время не меняют. Если нельзя надёжно отличить смысловую правку от косметической, безопаснее считать её смысловой. Не нужен отдельный LLM для этой проверки.
- `verified` — список событий независимой проверки, каждое имеет `by` и `at`. Один объект также читается как список. При редактуре **сохранять историю**, а не удалять прежнее подтверждение: по §5.3 учитываются только события с `verified.at >= generated.at`; если `generated` отсутствует, стандарт учитывает валидные события. Нет актуальных событий — `unverified`; есть только нечеловеческие — `machine-confirmed`; есть актуальное `human:<id>` — `human-reviewed`. Если дата генерации указана некорректно, нельзя повышать доверие к непроверенной редакции. Метки доверия вычисляются при чтении, а не записываются повторно как канон.
- `stale_after` задаётся только при известной дате пересмотра; на этой дате и позднее требуется проверка, а не автоматическое признание текста ложным. Отсутствие срока означает, что срок не задан, а не доказательство актуальности. Некорректный срок не считать свежим. Даты RFC 3339 с часовым смещением или полная дата (00:00 UTC); для времени генерации и проверки использовать точный timestamp с зоной. Учитывать изменение времени даже без нового Git-коммита.

Пример: сотрудник проверил инструкцию 10 ноября. Агент уточнил смысл 20 ноября. Событие 10 ноября остаётся в YAML, но текущая редакция больше не human-reviewed. Повторная независимая проверка 21 ноября возвращает соответствующий уровень доверия без перегенерации статьи.

Сам автор не выдаёт факт написания, Git-коммит, сравнение CROW или успешный структурный lint за независимую проверку. Проект с доверенными идентичностями подтверждает события по своему механизму; произвольный `human:` из YAML не является аутентификацией. При необходимости отдельно показывать заявленное и подтверждённое доверие. Право чтения, проверка действительности источника и смысловая достоверность не выводятся из OKF trust tier. Наличие противоречия, даты или высокого tier не заменяет сравнение условий и полномочий источников. [§5.2–5.5, §7](https://github.com/open-knowledge-format/open-knowledge-format/blob/527e81aff55992be21507e97004286789126f88c/SPEC.md#52-trust-generated-and-verified).

### Источники, ссылки и переносы

`sources` — стандартный список оснований, а не обязательное копирование статьи или всего исходника в raw. Для конкретных утверждений по мере пользы применять устойчивый `sources[].id` и сноску `[^source-id]`. `resource` у источника — разрешённый URI, путь либо указание охвата; не выдумывать дату, статистику использования или авторство. Версия, хеш и другие дополнительные сведения источника при необходимости хранятся в его расширениях. Фактический доступ к источникам обеспечивает проект. Существующее хранение raw и независимое восстановление канона не меняются.

Единое разрешение путей (§6): URI со схемой — абсолютный URI; `/...` — от корня bundle; остальные — от каталога содержащего файла. Для полей путей v0.2/без версии возможен поиск от корня только если относительная цель отсутствует; в v0.3 этого обхода нет. Для Git-агентов в теле предпочтительны относительные Markdown-ссылки; для внутрибандловых YAML-путей удобно использовать начальный `/`. URI-кодирование, фрагменты и регистр учитывать единообразно. Не обращаться к локальным файлам за границей bundle и не исполнять/загружать внешний ресурс автоматически. Ссылка на ещё не созданную статью не делает OKF невалидным; отмечать её как неполноту, а не повод пересобрать или отклонить весь корпус. Проверка удаления существующей цели и защита недоступных данных остаются. Связь в тексте или поле пути образует направленное ребро, не родительскую связь; иерархия — каталоги. Обязательный типизированный граф не вводится.

OKF определяет ID понятия через путь. При наличии устойчивого ID приложения или CROW сохранять его у продолжающейся темы. Для **замены** держать прежнюю статью с `status: deprecated` и, когда есть действующий преемник, `superseded_by: /path/to/new.md`. Для **переноса/переименования** оставлять по старому адресу короткую deprecated-страницу-переадресацию, когда адрес нужен для ссылок или внешних потребителей; действующая статья сохраняет свои ID и подтверждения, у заглушки не дублировать этот ID. В простой вики можно обновить все ссылки, если доказано, что старый адрес больше не нужен. Новая тема и замена другой темы не означают тождество их ID. В обычной выдаче возвращать разрешённого текущего преемника; не показывать старое правило как действующее. Не переходить по циклам, отсутствующим, закрытым или внешним целям; отсутствие перехода обозначить без раскрытия недоступных сведений. Это не механизм расширения доступа.

### Формат и метаданные раздела

Раздел может иметь корневой `index.md` с `okf_version: "0.3"`, `title`, `description` и при известном разрешении на использование `license`. Описание помогает внешнему агенту выбрать раздел до чтения корпуса. Лицензия контента не является ACL и не наследуется из лицензии CROW. При генерации навигации сохранять весь корневой frontmatter. В индексах подкаталогов и `log.md` frontmatter не допускается; даты журнала — YYYY-MM-DD. Не создавать второй журнал поверх Git только из-за формата.

YAML 1.2 core, уникальные ключи, UTF-8, обычный Markdown с таблицами GFM и сносками. `type` — единственное обязательное поле стандарта; неизвестные типы допустимы. README, AGENTS, SKILL без `type` не являются понятиями; обычные assets и скрытые файлы не включаются в поиск как статьи. Проект может индексировать только свой профиль (например Note) и требовать основания для своей авторской записи, но это не требования OKF. Отсутствующие/пустые необязательные поля и одиночные значения вместо списков нормализуются при чтении без переписывания файлов; одиночный тег с запятой не делить автоматически. Некорректный YAML и дубликаты ключей диагностируются отдельно. Незнакомые ключи сохранять рекурсивно, включая элементы источников и проверок, и не пересериализовывать без необходимости. Новые собственные поля именовать `x-<producer>-<name>`; существующие ID и поля совместимости не переименовывать массово. Расширение не может само выдавать права.

### Совместимость и инструменты

Проверка [CROW 1.0.5](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.5/src/llmw2/bundle/store.py): `write_index` формирует корневой YAML заново с 0.2; при `update_note` целиком заменяется `generated`; штатный поиск не учитывает текущий trust/status. Поэтому **нельзя** считать его полноценным потребителем/писателем 0.3. До подтверждения безопасной записи использовать прямого автора и чтение/поиск по допущенным текстам; нативные импорт, перенос и консолидация в 0.3 выполняются лишь при совместимом адаптере/версии либо исследуются в изолированной копии. Не держать две канонические вики и не форкать CROW ради версии метаданных.

Для перехода сначала научить потребителя читать обе версии и корректно показывать доверие; проверить запись, сохранение метаданных и ссылки; затем на копии перенести неоднозначные legacy пути и изменить версию корня одним проверенным Git-изменением. Не выполнять CROW rebuild и не придумывать прошлые события проверки. При наличии только тестовой вики новый корпус можно создать заново после готовности writer. Резервное восстановление по Git остаётся прежним.

Официальные [okf-generate и okf-consume](https://github.com/open-knowledge-format/open-knowledge-format/tree/527e81aff55992be21507e97004286789126f88c/skills) дают полезные переносимые правила написания и чтения, в том числе для внешних Git-агентов без CROW. Заимствовать формат, основания, историю проверки и переходы, а не обязательную вторую процедуру записи. Не копировать безусловную остановку на плане из N файлов или автоматический запуск executor/attester. Нормативный текст важнее навыка (например, подсказка миграции предлагает разделять теги с запятыми, хотя §11.2 считает такой scalar одним тегом). При расхождениях источников не выбирать автоматически более новый/популярный/высокоранговый текст. Attested Computation существовал уже в 0.2; пригоден как будущий формат описания санкционированного расчёта. Включать его исполнение только через отдельно разрешённые детерминированные инструменты, не произвольный код из вики. Протокол исполнения/песочница по-прежнему вне OKF 0.3. Никаких новых runtime-сервисов, обязательной онтологии, validity window или графовой БД для этого обновления.

## Защита авторских статей при обслуживании

Поисковые индексы, реестры и другие производные данные восстанавливаются из зафиксированных статей Note. Такая сверка не генерирует текст статей и не меняет канон. Отсутствие `raw` у напрямую написанной статьи не мешает её чтению, индексированию или восстановлению сохранённой редакции из Git.

**Риск пересборки из источников.** В CROW 1.0.5 `rebuild()` сначала вызывает очистку хранилища, затем повторно обрабатывает переданные исходники. `purge()` удаляет затронутые заметки и может заново синтезировать их по оставшимся источникам. Эти операции способны потерять авторские уточнения, которых нет в исходниках. Они меняют сам канон и не являются обслуживанием поискового индекса. [Реализация CROW](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.5/src/llmw2/wiki.py)

`rebuild`, очистка хранилища и удаление с пересинтезом исключаются из обычных фоновых задач и стандартного набора инструментов автора. Эксперименты с ними выполняются в отдельной копии: результат сравнивают с сохранённым Git-снимком, не подменяя рабочий канон. Нужные изменения затем вносят обычной авторской правкой с проверкой затронутых статей.

Резервная копия сохраняет статьи и их Git-историю. При использовании нативных `raw`, `.archive` и невоспроизводимых служебных данных их копируют отдельно с соответствующими правами. Восстановление возвращает сохранённые статьи, после чего заново строятся производные данные. Переимпорт исходников не заменяет резервную копию авторского текста; создавать дубликат каждой статьи в `raw` не требуется.

## Обновления и заменяемость

Точка интеграции — открытый пакет `llmwiki2` с Python API или его штатным MCP. Настольное приложение может быть отдельным клиентом, но не является обязательной частью концепции. Проект закрепляет проверенную версию поставки и обновляет её вместе с проверкой реально используемых операций. Публичные документированные интерфейсы имеют гарантии совместимости с 1.0.0; внутренние классы в эти гарантии не входят. [Границы совместимости](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.5/docs/library/index.md#compatibility)

В частности, `Wiki.search` работает с вики, а отдельного публичного поиска по переданному списку допущенных страниц в 1.0.5 нет. Если проекту необходим такой вход, адаптер может изолировать применение внутреннего `llmw2.search.NoteSearch` с точной фиксацией версии и проверкой границ корпуса. При появлении публичного аналога заменяется только эта часть адаптера. Его отсутствие не требует форка CROW или нового формата знаний.

Исправления 1.0.2 удаляют YAML-метаданные из создаваемого тела заметки при `llm.note_steps` и уточняют язык ответа небольшой генерирующей модели. Исходник и его хеш не меняются; ранее импортированные статьи автоматически не переписываются. Русский язык пока отсутствует во встроенном детекторе этой подсказки. Эти исправления учитываются при выборе штатного импорта и ответов CROW; качество тематических статей и работу на языке проекта проверяют на своих примерах. [Изменения 1.0.2](https://github.com/crow-hq/llm-wiki-v2/releases/tag/v1.0.2) · [Детектор языка](https://github.com/crow-hq/llm-wiki-v2/blob/v1.0.5/src/llmw2/agents/lexical.py#L25-L51)

## Просмотр и редактирование пользователями

Кандидат для проверки готового пользовательского интерфейса — [Inkeep OpenKnowledge](https://github.com/inkeep/open-knowledge). README проекта описывает WYSIWYG-редактор Markdown, desktop-приложение (Windows, macOS, Linux), web UI, навигацию по файлам, поиск, граф связей и необязательную Git/GitHub-синхронизацию. Это кандидат именно на роль редактора-просмотрщика той же вики, а не замена CROW, Git-канона или навыка автора.

Начать с просмотра и редактирования изолированной копии OKF 0.2/0.3. Проверить сохранность YAML (включая неизвестные вложенные поля, verified, generated, sources и корневой index.md), сносок и ссылок, а также отсутствие неожиданных изменений при простом открытии/сохранении. В многопользовательском профиле чтение и запись допускаются только в разрешённом корпусе с принятым порядком фиксации версий; встроенные синхронизация, MCP и AI-операции не должны обходить эти границы. Удобство для нетехнических пользователей, режим размещения и условия GPL-3.0-or-later проверить отдельно. Выбор редактора не является условием работы системы знаний.

## Подключение к другому проекту

1. Выберите каталог и дайте агенту штатные средства чтения и редактирования. Для нового тестового корпуса достаточно создать пустую вики в формате OKF. Для существующего корпуса сначала проверьте на копии нескольких статей, распознаёт ли CROW метаданные, пути и ссылки.
2. Подключите поиск к тому же каталогу. CROW 1.0.5 непосредственно обнаруживает новый файл Note в тематической папке и видит изменение его текста при следующем чтении вне пакетного импорта. Повторно импортировать страницу ради поиска не требуется. При прямой правке сохраняйте ID, источники и незнакомые поля. При создании или переносе обновляйте индексы затронутых папок, ссылки и запись о правке в корневом `log.md`. Штатная проверка `Wiki.check()` обнаруживает пропущенную строку в индексе. Сам журнал от файловой правки не пополняется.
3. Следуйте принятому в проекте порядку сохранения и [проверки параллельных правок](#параллельная-работа-авторов). При управляемом исполнении агент оставляет законченные правки в рабочей копии, а коммит делает хост после проверки. При обычной работе с Git проект определяет, кто фиксирует результат. Хост включает только изменения завершённой операции. При пустой правке коммита нет. Согласуйте прямую запись с импортёром, если оба работают с общими файлами. Если у проекта есть собственный реестр или отдельный поисковый индекс, после коммита сверьте его с конкретной ревизией Git (SHA), включая новые, переименованные и удалённые страницы. Для самого CROW такая регистрация не нужна.
4. На одном примере проверьте, что новый вывод по двум темам меняет обе статьи и находится другим агентом, а повтор известного факта оставляет файлы без изменений. Проверьте прямую правку с последующим импортом близкого документа. Резервная копия должна содержать написанные агентом статьи. `rebuild` собирает вики заново из исходников и может потерять авторский текст, которого там нет.
5. При обновлении CROW повторите проверки подключённых операций. Для собственного адаптера отдельно проверьте версии API и ограничение входного корпуса. Если используются MCP, импорт или модельные ответы, проверьте их первый запуск, обработку исходников и качество на языке проекта. Подключение новой функции CROW учитывается отдельно от обновления зависимости.
