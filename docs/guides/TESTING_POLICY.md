# Политика тестирования

Статус: active.

Дата: 2026-07-30.

## Назначение

Политика определяет достаточный уровень проверки при минимальном числе повторных запусков. Полный набор остается контрольной точкой, но не используется как единственный инструмент обратной связи.

Связанные документы:

- `AGENTS.md`;
- `docs/guides/TEST_ACCELERATION.md`;
- `pytest.ini`;
- `scripts/e2e/playwright.config.ts`;
- профильные ADR и планы.

## Ступени проверки

### 1. Дешевые проверки

```bash
.venv/bin/python manage.py check
.venv/bin/python -m py_compile <changed-python-files>
git diff --check
```

### 2. Модульные тесты

Для изменения кода обязательны модульные тесты затронутого поведения. Такой тест не использует базу, браузер, сеть или внешний сервис и отмечается `@pytest.mark.unit`.

```bash
make test-unit
make test-fast TEST_SCOPE=services/agent_runtime/tests/test_normalization.py
```

### 3. Интеграционные тесты

Нужны для связки view/service/model, tool gateway, контрактов, памяти, индекса, аудита или нескольких runtime-компонентов. Такие тесты отмечаются `@pytest.mark.integration`.

```bash
make test-integration TEST_SCOPE=apps.ai.tests
```

### 4. E2E

Крупный блок разработки должен иметь один основной сквозной сценарий через HTTP/UI/API или management command. Он проверяет пользовательский результат, а не повторяет все ветви модульных тестов.

```bash
npm run test:e2e:smoke
npm run test:e2e -- --grep @ai
```

Временные сценарии, логи и браузерные артефакты хранятся только в `.local/`.

### 5. Контрольный прогон

```bash
make test
```

Команда использует чистую тестовую базу и реальные миграции. Она обязательна перед приемкой крупной или рискованной работы. Для короткого цикла используется `make test-fast`, который переиспользует базу в `.local/`.

## Матрица обязательных проверок

| Изменение | Минимум |
| --- | --- |
| Локальная функция, валидатор, форматирование | `check`, целевой `unit` |
| Django model/service/policy/view | `check`, целевые unit и integration |
| AI tool или task type | `apps.ai` unit/integration, runtime wrapper, contracts |
| Agent runtime, prompt, tools или MCP | `services.agent_runtime`, gateway integration |
| `contracts/` | `make contracts`, тесты потребителей |
| Память, ingestion, FTS/vector | memory unit/integration и профильный command e2e |
| Права, privacy, секреты | отрицательные сценарии, audit, fail-closed; полный прогон |
| UI, шаблон, браузерный мост | Django view и тематический Playwright e2e |
| Deployment/runtime command | dry-run, документация, отсутствие секретов |
| Только документация | просмотр ссылок; `make gen-struct` при изменении структуры |

## Правила тестового кода

- Общие неизменяемые данные `TestCase` создаются через `setUpTestData`.
- Тест без базы наследуется от `SimpleTestCase`.
- Реальные внешние сервисы заменяются детерминированными заглушками.
- Нельзя делать тесты зависимыми от порядка, общей изменяемой фикстуры или локальных секретов.
- Миграции не отключаются в контрольном прогоне.
- Настоящее криптографическое хеширование проверяется отдельным узким тестом; остальные тесты используют быстрый test hasher.
- Новый дорогой сценарий отмечается `slow`, а работа с общим процессным или файловым состоянием — `serial`.

## Независимая проверка

Не следует создавать проверочного агента только для запуска одной заранее известной детерминированной команды. Такую команду выполняет основной агент или CI: отдельная модель не добавляет независимого знания, но расходует токены и усложняет работу с общим деревом.

Субагент рекомендуется, когда есть отдельная содержательная работа:

- проектирование сложного теста;
- оценка достаточности покрытия и поиск пропущенных сценариев;
- исследование независимой подсистемы;
- диагностика неочевидного или нестабильного падения;
- проверка security, privacy, contracts или архитектурных рисков;
- комплексная матрица из множества простых проверок, которую дешевле выполнить отдельной моделью.

Последний вариант включает, например, перебор ролей и прав, HTTP-маршрутов, конфигураций, браузерных состояний, контрактов и журналов. Для него можно использовать дешевую модель, если действия однозначны, не требуют опасных изменений и имеют проверяемый структурированный результат.

Проверяющий:

- получает цель, read scope, матрицу действий, критерии приемки и формат отчета;
- не меняет код и состояние Git;
- не применяет `stash`, `restore`, `reset`, `clean` или переключение ветки;
- запускает только проверки, необходимые для порученного анализа или матрицы;
- сообщает выполненные действия, результат, первое значимое падение и остаточный риск;
- хранит подробный вывод и артефакты в `.local/`.

Основной агент отвечает за итоговую интерпретацию, воспроизводит существенные отклонения и не принимает отчет дешевой модели без проверки выводов. Основной и проверочный агенты не должны дублировать полный прогон. Для малой низкорисковой правки отдельный проверяющий не нужен.

## AI-сценарии

- Бизнес-действия проверяются через tool gateway, service layer и audit.
- Поток LLM в браузерном e2e можно мокировать.
- Реальный LLM допускается только в явно выделенном eval или ручном сценарии.
- Write-tools проверяют confirmation flow, отказ, повторное подтверждение и истечение токена.
- Найденные документы и память не должны исполняться как инструкции модели.

## CI

- Незавершенные запуски одной ветки отменяются через `concurrency`.
- pip и npm используют lock-файлы и кэш.
- Pull request: полный набор один раз на Python 3.11, модульная проверка совместимости на Python 3.12, без расчета покрытия.
- `main`: полный набор на Python 3.11 и 3.12; покрытие рассчитывается только на 3.11.
- Браузерный `@smoke` запускается после успешного основного набора в `main`.

## Финальный отчет

Указать:

- какие тесты добавлены или изменены;
- команды и фактический результат;
- что не запускалось и почему;
- обновленные документы;
- остаточный риск.
